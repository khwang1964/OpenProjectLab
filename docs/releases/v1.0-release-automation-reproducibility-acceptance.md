## 1. Purpose

This document records the Step 8.8 acceptance evidence for the v1.0
release-automation and reproducibility boundary.

Step 8.8 does not publish `v1.0.0-rc.1` and does not replace Step 8.9
Full Release-readiness Verification or Step 8.10 RC Acceptance. Its
responsibility is to make the maintainer release process explicit,
automated where practical, fail-closed, artifact-backed, and
reproducibly verifiable.

The release identity is treated as one coherent relationship:

```text
Version
    ↕
Commit SHA
    ↕
Git Tag
    ↕
Release Artifact
    ↕
GitHub Release
```

---

## 2. Acceptance Scope

Step 8.8 acceptance covers:

- canonical release version resolution;
- release commit SHA and deterministic tag identity;
- version / tag / artifact metadata consistency;
- clean release-artifact enumeration;
- wheel / sdist metadata validation;
- checksum generation and mutation detection;
- verification-before-publication workflow behavior;
- GitHub Release tag / asset consistency;
- wheel-backed installed-user verification;
- semantic reproducibility verification;
- maintainer release runbook, abort rules, correction rules, and
  post-release verification;
- completion-state regression, coverage, and local quality evidence.

Step 8.8 intentionally does **not** claim byte-for-byte reproducible
builds unless separately demonstrated. Semantic reproducibility is the
required v1.0 contract.

---

## 3. Architecture Acceptance

The Step 8.8 implementation preserves the Milestone 8 architecture:

```text
Frozen v1.0 contracts
        ↓
Release identity validation
        ↓
Artifact build / metadata / checksum verification
        ↓
Wheel-backed installed-user verification
        ↓
Semantic reproducibility verification
        ↓
GitHub Release consistency verification
        ↓
Publication only after verification
```

The release path does not introduce a second package/version authority
and does not widen the Step 8.2 frozen public API surface.

Verification logic remains separable from irreversible publication
side effects where practical. Release publication must fail closed when
identity, artifact, checksum, installed-user, or release-state
verification fails.

## 5. Artifact and Installed-user Acceptance

The release process uses current built artifacts rather than treating a
source checkout as equivalent release evidence.

Required behavior includes:

- clean artifact-output state before build;
- rejection of stale or unexpected artifacts;
- metadata agreement with canonical release identity;
- checksum coverage for release artifacts;
- checksum failure after artifact mutation;
- isolated installation from the current wheel;
- `OPL_TEST_WHEEL` (or equivalent release input) resolving to the
  current built wheel;
- installed-user smoke verification using packaged runtime resources.

This preserves the package-resource and clean-install guarantees
accepted in Step 8.4 and reused by the executable First 15 Minutes
workflow from Step 8.5.

---

## 6. GitHub Release Consistency Acceptance

The release automation requires the GitHub Release state to agree with
the verified release identity:

```text
canonical version
        ==
tag version
        ==
artifact version

approved release SHA
        ==
tag target

expected tag
        ==
GitHub Release tag

verified artifact set
        ==
published release assets
```

A conflicting existing tag or release state must not be silently
rewritten. Publication cannot precede verification.

---

## 7. Reproducibility Acceptance

Step 8.8 requires **semantic reproducibility**.

A rebuild must preserve the release contract sufficiently to demonstrate
that the rebuilt package:

- resolves to the same release identity;
- has contract-equivalent package metadata;
- contains the required runtime resources;
- remains installable;
- preserves the verified installed-user behavior.

Byte-identical archives are a stronger property and are not claimed by
this acceptance record.

---

## 8. Maintainer Documentation Acceptance

The maintainer release process documents the operational path needed to
prepare and verify a release, including:

- prerequisites;
- clean starting-state checks;
- release version / SHA / tag verification;
- artifact build and verification;
- checksum handling;
- installed-user verification;
- semantic reproducibility verification;
- draft / publish sequencing;
- abort conditions;
- tag correction rules;
- published-release correction rules;
- post-release verification;
- evidence recording.

This satisfies Documentation First while the repository-owned checks
satisfy Automation First.

reproducibly verifiable.

integrated verification across the complete v1.0 release candidate
state, including the representative installed-user E2E and all final
release-readiness checks.

pre-approve Step 8.10 RC Acceptance.

## 13. Code Review Checklist

### Architecture

- [x] Release identity remains one coherent version / SHA / tag /
      artifact / GitHub Release tuple.
- [x] No duplicate version authority is introduced.
- [x] Verification occurs before irreversible publication.
- [x] Step 8.8 does not absorb Step 8.9 or Step 8.10 ownership.

### Artifacts

- [x] Release build starts from a clean output state.
- [x] Stale artifacts cannot be selected.
- [x] Artifact metadata agrees with canonical version identity.
- [x] Checksums cover the exact release artifact set.
- [x] Artifact mutation is detected.

### Installed-user Verification

- [x] The current built wheel is used.
- [x] Clean-install verification is isolated from the source checkout.
- [x] Required packaged runtime resources are exercised.
- [x] `OPL_TEST_WHEEL` cannot silently resolve to a stale wheel.

### GitHub Release

- [x] Expected tag matches the canonical version.
- [x] Tag target matches the approved release SHA.
- [x] GitHub Release tag matches the expected tag.
- [x] Published assets match the verified artifact set.
- [x] Conflicting existing state fails closed.

### Reproducibility

- [x] Semantic reproducibility is automated.
- [x] Rebuilt metadata is contract-equivalent.
- [x] Rebuilt wheel remains installable.
- [x] Byte-for-byte reproducibility is not claimed without evidence.

### Security / Workflow

- [x] Verification does not require publication credentials.
- [x] Publication permissions are minimal.
- [x] Untrusted pull-request execution cannot publish a release.
- [x] Failed verification blocks publication.

### Tests and Documentation

- [x] Maintainer runbook matches the implemented automation.
- [x] `docs/roadmap.md`, `docs/HISTORY.md`, and `CHANGELOG.md` reflect the

- [x] Post-merge consistency is verified before Step 8.8 is closed.

# Final Principle

> A release is not reproducible because a maintainer remembers the
> procedure. It is reproducible when identity, artifacts, verification,
> and publication are governed by explicit contracts, automation, and
> recorded evidence.
