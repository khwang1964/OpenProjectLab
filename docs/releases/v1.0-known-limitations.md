## 1. Purpose

This document records known limitations and deferred capabilities for the
OpenProjectLab v1.0 release.

The goal is to make the release boundary explicit so users and maintainers
can distinguish:

```text
Supported
Experimental
Known Limitation
Deferred
```

A known limitation is not automatically a defect and a Deferred capability
is not automatically missing functionality. Both are intentional release
governance states when documented clearly.

---

## 2. Classification Rules

### Known Limitation

Use **Known Limitation** when:

- the capability is within the v1.0 supported product boundary;
- the implementation is usable;
- a constraint or edge case is known;
- the limitation is accepted for v1.0;
- the limitation does not invalidate the core supported workflow.

A known limitation should identify mitigation or workaround when available.

### Experimental

Use **Experimental** when:

- the capability exists;
- it may be useful;
- support evidence or compatibility commitment is incomplete;
- it is not part of the full Stable v1.0 support promise.

### Deferred

Use **Deferred** when:

- the capability is intentionally outside v1.0 scope;
- no v1.0 support commitment is made;
- absence does not block v1.0 acceptance;
- future implementation belongs to v1.1+ or another explicitly planned
  release.

---

## 3. General v1.0 Boundary

OpenProjectLab v1.0 prioritizes:

- deterministic local workflows;
- Stable Generator and Plugin contracts;
- structured Courseware generation;
- provider-independent AI contracts;
- deterministic Marketplace core contracts;
- package-owned runtime resources;
- clean built-wheel installation;
- bilingual User Manuals;
- compatibility/deprecation governance;
- release-readiness automation.

It does not attempt to complete every capability described by long-term
architecture documents.

---

## 4. Environment Support Limitation

### Exact Python and OS Matrix Must Be Evidence-Based

**Classification:** Known Limitation / release-documentation constraint

The v1.0 support matrix must not claim Python versions or operating systems
that are not explicitly verified by CI or release testing.

Step 8.7 now records the exact v1.0 environment evidence in the companion
support matrix:

- Ubuntu (`ubuntu-latest`) with Python 3.14 is Supported through GitHub
  Actions CI;
- Windows with Python 3.14.5 is Supported for the explicitly verified
  maintainer-owned, wheel-backed Step 8.6 release workflow, which completed
  `1648 passed, 1 deselected` with `90.55%` total coverage;
- no unverified Python-version range is advertised;
- no operating system is marked Supported merely because the code is
  portable Python;
- the Windows claim is not generalized to every Windows edition or
  configuration;
- macOS and other unverified environments remain outside the v1.0 support
  commitment until explicit evidence exists.

### Mitigation

Use only environment combinations listed as Supported in
`docs/reference/support-matrix.md`. Other Python/OS combinations may work,
but they are unverified and carry no v1.0 support commitment.

## 5. Live AI Provider Operation

**Classification:** Experimental / Optional Operational Verification

The provider-independent AI core is deterministic and testable without a
live provider.

The concrete OpenAI adapter has deterministic no-network coverage, while
live provider verification remains opt-in.

Limitations of live-provider operation include dependence on:

- external credentials;
- provider network availability;
- third-party API stability;
- external service policy;
- potential usage cost;
- provider-specific rate/availability constraints.

### Mitigation

Use deterministic provider-independent tests and `FakeAIProvider` for core
verification. Treat live-provider testing as optional operational
verification rather than a core v1.0 acceptance requirement.

## 6. AI Capabilities Deferred Beyond v1.0

**Classification:** Deferred

The following remain outside the v1.0 supported core commitment:

- AI Refactoring Assistant;
- AI CLI;
- provider marketplace / pluginized provider discovery;
- AI evaluation framework;
- provenance / usage accounting;
- caching;
- streaming;
- tool calling.

These are v1.1+ candidates unless explicitly promoted later.

---

## 7. Marketplace Remote Service

**Classification:** Deferred

v1.0 supports deterministic Marketplace core contracts, not a full remote
Marketplace service.

Deferred capabilities include:

- remote Marketplace service;
- Community Repository hosting;
- Marketplace CLI;
- real package-manager integration;
- automatic Plugin / Generator activation;
- artifact signing;
- publisher identity;
- sandbox / trust enforcement;
- general dependency solving;
- lock-file / cache policy;
- ratings / reviews;
- monetization / payment;
- AI Provider Marketplace.

### Impact

The v1.0 Marketplace should be understood as a deterministic artifact and
installation contract foundation, not as a hosted commercial/community
marketplace product.

---

## 8. Plugin Distribution Limitations

### Remote Distribution

**Classification:** Deferred

The Stable v1 plugin boundary covers the SDK and canonical Entry Point
runtime, not a remote plugin distribution service.

### Dependency Resolution

**Classification:** Deferred

v1.0 does not promise a general-purpose dependency solver for Plugins or
Marketplace artifacts.

### Trust / Signing

**Classification:** Deferred

Artifact signing, publisher identity, sandboxing, and trust-policy
enforcement are not part of the v1.0 supported contract.

---

## 9. Courseware Assessment Limitations

### Grading / Scoring Runtime

**Classification:** Deferred

Quiz and Assignment generation are supported as deterministic authored
content generation.

v1.0 does not provide:

- grading runtime;
- scoring engine;
- rubric execution;
- submission backend;
- LMS integration.

### QuestionBank / Randomization

**Classification:** Deferred

Quiz generation does not imply:

- question-bank management;
- randomized question selection;
- randomized choice ordering;
- adaptive assessment.

---

## 10. Slides Output Limitation

**Classification:** Known Limitation / Deferred Renderer Capability

The supported Slides Generator produces deterministic Markdown source:

```text
<target>/slides.md
```

v1.0 does not provide built-in:

- PPTX rendering;
- PDF rendering;
- HTML slide-deck rendering.

### Mitigation

Use the generated Markdown source as the canonical v1.0 artifact and apply
an external renderer outside the core OPL support boundary when needed.

---

## 11. Website Publishing Limitation

**Classification:** Known Limitation / Deferred Hosting Capability

The Website Generator produces deterministic static HTML under:

```text
<target>/site/
```

v1.0 does not provide:

- hosting;
- deployment;
- CMS;
- analytics;
- dynamic server runtime;
- generalized asset pipeline;
- automatic Markdown-to-site conversion beyond the implemented generator
  behavior.

### Mitigation

Deploy generated static output using an external hosting/deployment system.

---

## 12. Courseware Composition Transaction Limitation

**Classification:** Known Limitation

Courseware Composition uses deterministic sequential execution and
fail-fast behavior.

It intentionally does **not** promise generalized cross-Generator rollback.

If an earlier Generator succeeds and a later Generator fails, v1.0 does not
claim an automatic composition-wide transaction rollback.

### Rationale

The architecture preserves existing Generator / Filesystem boundaries
rather than inventing a generalized transaction system during v1.0
stabilization.

### Mitigation

Use dry-run where appropriate and rely on existing per-generator /
filesystem safety semantics.

---

## 13. Exact Error Text Is Not a Stable Contract

**Classification:** Known Limitation / Compatibility Boundary

Public exception categories and failure semantics may be Stable where
frozen by Step 8.2.

Exact human-readable error-message text is not Stable unless explicitly
classified.

### Impact

Tests and integrations should depend on documented exception categories or
structured behavior rather than exact prose.

---

## 14. Internal Module Paths Are Not Supported APIs

**Classification:** Known Limitation / Compatibility Boundary

Repository visibility or Python importability does not make an Internal
module part of the Stable public contract.

Only explicit Stable public façades, such as the reviewed `generator.sdk`
surface, receive the full v1 compatibility guarantee.

### Mitigation

Third-party code should use documented Stable public access paths.

---

## 15. Editable-Install-Only Behavior Is Not a Release Guarantee

**Classification:** Known Limitation / Packaging Boundary

v1.0 installed-user claims are based on built artifacts and clean
installation.

A workflow that only succeeds because of:

- editable installation;
- repository `PYTHONPATH`;
- source-tree-only resources;
- untracked local files;

is not a supported installed-user workflow.

### Mitigation

Validate release behavior against the built wheel.

---

## 16. Network Independence of Core CI

**Classification:** Known Limitation / Deliberate Constraint

Normal core verification is designed to remain deterministic and not
depend on:

- live AI providers;
- public network availability;
- paid external accounts;
- remote Marketplace services.

This means some operational integrations are intentionally not exercised by
normal CI.

### Mitigation

Use explicit opt-in operational tests for external-service verification
without weakening deterministic core acceptance.

---

## 17. Documentation Language Boundary

**Classification:** Known Limitation

v1.0 formally maintains:

```text
English
Traditional Chinese (Taiwan)
```

Other language editions are not part of the v1.0 maintained documentation
commitment.

### Mitigation

Use the English or zh-TW User Manual as the canonical supported
documentation.

## 18. Release Automation Not Yet Owned by Step 8.7

**Classification:** Deferred to Step 8.8

Step 8.7 documents support and limitations.

It does not define the complete maintainer release process or enforce the
full consistency chain:

```text
Version
  ↕
Commit SHA
  ↕
Git Tag
  ↕
Release Artifact
  ↕
GitHub Release
```

That responsibility belongs to Step 8.8 --- Release Automation &
Reproducibility.

## 19. Unsupported Assumptions

The following assumptions must not be made from v1.0 documentation alone:

- every modern Python version is supported;
- every desktop/server OS is supported;
- every Internal module is public API;
- every long-term architecture proposal is implemented;
- every Marketplace capability is available remotely;
- live AI is required for core functionality;
- successful source checkout implies successful built-package behavior;
- deprecation permits removal during v1.x;
- a generated static artifact implies deployment/hosting support.
