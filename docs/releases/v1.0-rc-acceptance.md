# OpenProjectLab v1.0 RC Acceptance

> **Status:** Accepted
> **Milestone:** 8 — v1.0 Stabilization & Release Readiness
> **Step:** 8.10 — RC Acceptance
> **Date:** 2026-08-19
> **Predecessor:** Step 8.9 — Full Release-readiness Verification — Accepted
> **Target RC:** `v1.0.0-rc.1`
> **Successor:** v1.0.0 GA Acceptance

---

## 1. Purpose

This document is the governing design and acceptance contract for
OpenProjectLab Milestone 8 Step 8.10.

Step 8.10 answers one release-level question:

> Can the verified OpenProjectLab v1.0 repository state be materialized as
> `v1.0.0-rc.1`, with source, version, artifacts, checksums, installation
> behavior, documentation, tag, and GitHub Release identity forming one
> coherent and auditable Release Candidate?

Step 8.9 established that the repository was ready to enter RC Acceptance.
Step 8.10 owns the actual RC acceptance boundary.

Step 8.10 does not repeat Step 8.9 merely to obtain another passing test run.
It consumes the accepted Step 8.9 state and verifies that an actual RC
identity can be created and accepted without weakening any v1.0 contract.

---

## 2. Governing Decision

RC Acceptance is fail-closed.

`v1.0.0-rc.1` may be accepted only when every required gate describes the
same release candidate:

```text
Accepted Step 8.9 repository state
        ↓
Canonical RC version
        ↓
Approved source commit
        ↓
Fresh wheel + sdist
        ↓
Artifact checksums
        ↓
Artifact-backed verification
        ↓
RC tag identity
        ↓
GitHub Release identity
        ↓
RC acceptance evidence
```

No individual passing gate compensates for failure, missing evidence, stale
artifacts, or identity disagreement in another required gate.

---

## 3. Scope

Step 8.10 owns:

- defining the canonical first RC identity as `v1.0.0-rc.1`;
- binding the RC to one approved source commit;
- verifying canonical package version and distribution metadata;
- building a fresh wheel and source distribution from the approved source;
- verifying the canonical artifact set and checksums;
- running required artifact-backed release-readiness verification;
- validating clean installation and representative installed-user behavior;
- validating documentation and First 15 Minutes behavior against the RC wheel;
- validating public-contract, compatibility, support, and known-limitations
  consistency at the RC boundary;
- validating tag, source commit, artifact, and GitHub Release identity;
- recording CI, merge, synchronization, and post-merge evidence;
- deciding whether `v1.0.0-rc.1` is formally Accepted.

---

## 4. Explicit Non-goals

Step 8.10 does not:

- declare `v1.0.0` GA Accepted;
- create new v1.0 product capabilities;
- expand the frozen Stable public surface;
- expand the support matrix without new evidence and formal review;
- remove or weaken known limitations to simplify release;
- absorb deferred v1.1+ work;
- accept source-checkout-only success as installed-user evidence;
- treat skipped required artifact-backed tests as passing RC evidence;
- silently reuse stale artifacts;
- rewrite an existing release tag to point at another commit;
- replace an already-published RC artifact under the same identity;
- claim byte-for-byte reproducibility unless that stronger property is
  explicitly demonstrated.

---

## 5. Authoritative Inputs

Step 8.10 consumes, but does not replace, these authorities:

| Authority | Step 8.10 responsibility |
|---|---|
| Step 8.2 public-contract freeze | Preserve the accepted Stable surface |
| Step 8.4 packaging / installation | Preserve artifact and clean-install contracts |
| Step 8.5 bilingual user manuals | Preserve EN / zh-TW behavior and onboarding |
| Step 8.6 compatibility / deprecation policy | Preserve compatibility promises |
| Step 8.7 support matrix / known limitations | Preserve evidence-backed support claims |
| Step 8.8 release automation / reproducibility | Reuse canonical release identity and artifact rules |
| Step 8.9 full release readiness | Require formal acceptance before RC materialization |

If two accepted authorities disagree, Step 8.10 must fail until the
contradiction is corrected through the normal reviewed process.

## 6. RC Identity Contract

The first v1.0 Release Candidate identity is:

```text
v1.0.0-rc.1
```

The RC identity must bind the following values:

```text
RC version
    == canonical project/package version

Approved source commit
    == release-source commit

Tag target commit
    == approved source commit

Wheel metadata version
    == RC version

Source-distribution metadata version
    == RC version

Artifact checksum manifest
    == exact published artifact bytes

Installed-user test artifact
    == verified RC wheel

GitHub Release tag
    == RC tag

GitHub Release artifacts
    == verified artifact set
```

Any unexplained mismatch is an RC blocker.

---

## 7. Version Rules

The RC must use the canonical prerelease version corresponding to:

```text
1.0.0rc1
```

for Python package metadata where PEP 440 normalization applies, while the
human-facing release/tag identity remains:

```text
v1.0.0-rc.1
```

Automation must compare identities using the repository's accepted canonical
version rules rather than naïve string equality where normalized package
metadata is expected.

No `v1.0.0` GA version may be introduced as part of RC acceptance.

---

## 8. Source Commit Contract

The RC must be bound to one immutable approved commit.

Required evidence must identify:

- full commit SHA;
- branch / merge provenance where relevant;
- clean repository state used for the RC build;
- relationship between the acceptance PR and the selected source commit;
- tag target commit;
- release-source commit used by artifact verification.

The source commit must already contain all changes required for the RC.
Publication must not depend on uncommitted or local-only files.

---

## 9. Artifact Contract

The RC artifact set must be built from a clean artifact-output directory.

Required artifacts:

```text
wheel
source distribution
checksum manifest
```

Verification must reject:

- missing required artifacts;
- stale artifacts from an earlier build;
- duplicate release candidates;
- unexpected extra distributions;
- version mismatch;
- metadata mismatch;
- checksum mismatch;
- artifact bytes that differ from those used by installed-user verification.

The exact accepted artifact naming rules remain governed by the Step 8.8
release automation contract.

---

## 10. Artifact-backed Verification

The RC verification run must use the actual current RC artifacts.

Required artifact-backed evidence includes:

- wheel metadata verification;
- source-distribution metadata verification;
- checksum verification;
- clean installation;
- packaged resources;
- console entry point;
- First 15 Minutes installed-user workflow;
- representative installed-user E2E;
- integrated package / release identity verification.

Required artifact-backed tests must not be accepted as skipped because an
artifact environment variable was omitted.

---

## 11. Documentation and User-facing Contract

Before RC acceptance, documentation must still agree with actual RC behavior.

Verification must cover:

- English / zh-TW structure parity;
- functional parity;
- installation instructions;
- First 15 Minutes workflow;
- CLI commands and examples;
- generators, Courseware, Plugins, AI, and Marketplace behavior;
- compatibility and deprecation statements;
- support matrix;
- known limitations;
- release status language.

Documentation must describe the candidate as an RC, not as a GA release.

---

## 12. Compatibility, Support, and Limitation Boundary

RC status does not relax v1.0 compatibility governance.

Step 8.10 must preserve:

- Step 8.2 Stable / Candidate / Experimental / Internal classifications;
- Step 8.6 compatibility and deprecation rules;
- Step 8.7 evidence-backed Supported environments;
- Step 8.7 Known Limitation and Deferred classifications.

An RC defect may justify a correctness fix, but not silent scope expansion.

---

## 13. Allowed RC Changes

Once RC validation begins, changes should be limited to:

- release blockers;
- correctness defects;
- compatibility defects;
- installation / packaging defects;
- security defects;
- documentation correctness fixes;
- release/test automation defects.

Any proposed change outside these classes requires explicit review against the
Milestone 8 feature-freeze boundary and should normally move to v1.1+.

Every RC correction invalidates prior evidence affected by that correction and
requires the relevant gates to be re-run.

---

## 14. Tag Contract

The canonical RC tag is:

```text
v1.0.0-rc.1
```

The tag must:

- identify exactly one approved source commit;
- match the RC version policy;
- never be moved after publication;
- not exist before the repository is ready for the controlled RC creation
  sequence;
- be verified after creation;
- remain consistent with the GitHub Release.

If an already-published RC is defective, create a new RC identity such as
`v1.0.0-rc.2`; do not retarget `v1.0.0-rc.1`.

---

## 15. GitHub Release Contract

The RC GitHub Release must:

- use the canonical RC tag;
- be marked as a prerelease where supported by the release workflow;
- identify the approved source commit through the tag;
- contain the verified canonical artifact set;
- publish the same artifact bytes whose checksums and installed-user behavior
  were verified;
- include or reference user-facing release notes, support information, and
  known limitations;
- avoid language that declares v1.0.0 GA acceptance.

Publication credentials are delivery concerns; deterministic local and CI
verification must remain possible without real publication credentials.

## 19. Failure Classification

| Class | Meaning | Required response |
|---|---|---|
| RC blocker | Required v1.0 or RC contract is violated | Fix and re-run affected gates |
| Identity mismatch | Version, commit, tag, artifact, checksum, or release disagree | Stop publication / acceptance |
| Evidence gap | Behavior may be correct but required proof is missing | Produce deterministic evidence |
| Documentation defect | User-facing claim disagrees with RC behavior | Correct and re-verify |
| Unsupported expansion | Claim exceeds accepted support evidence | Remove or formally reclassify |
| Deferred improvement | Useful but not required for RC correctness | Record for v1.1+ |

No RC blocker may be reclassified as Deferred merely to complete Step 8.10.

---

## 20. RC vs GA Boundary

RC Acceptance and GA Acceptance are separate decisions.

RC Acceptance means:

> `v1.0.0-rc.1` is a coherent, verified, publishable Release Candidate whose
> release identity and user-facing behavior satisfy the v1.0 RC contract.

RC Acceptance does not mean:

> `v1.0.0` is GA Accepted.

GA requires a later independent decision after RC validation.

The GA gate must evaluate actual RC experience and any RC-period corrections
before creating `v1.0.0`.

---

## 21. Automation Contract

Step 8.10 automation must be:

- deterministic;
- fail-closed;
- artifact-backed where artifacts are required;
- explicit about missing prerequisites;
- independent of accidental source-checkout imports;
- safe against stale artifact selection;
- non-destructive during ordinary PR verification;
- unable to publish from ordinary pull-request jobs;
- auditable through exact commit / artifact / checksum identity.

Release mutation actions such as tag or GitHub Release creation must be
separated from read-only verification and protected by the accepted release
workflow.

---

## 22. Test Strategy

The Step 8.10 contract test should verify at minimum:

- the governing RC document exists;
- metadata identifies Step 8.10;
- Step 8.9 is the Accepted predecessor;
- target RC is exactly `v1.0.0-rc.1`;
- RC Acceptance and GA Acceptance are explicitly separate;
- the first RC tag identity is fixed;
- source / tag / artifact / checksum / GitHub Release identity is required;
- artifact-backed evidence cannot be replaced by source-only evidence;
- required artifact-backed skips are not acceptable final evidence;
- no GA pre-approval is present;
- Step 8.9 remains Accepted in the roadmap;
- Step 8.10 is not already marked Accepted while this governing record is
  still in progress.

Tests should verify stable contract language and metadata, not volatile prose
formatting or future evidence values.
