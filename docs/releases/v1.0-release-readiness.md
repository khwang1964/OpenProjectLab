# OpenProjectLab v1.0 Release Readiness

> **Status:** Accepted
> **Milestone:** 8 — v1.0 Stabilization & Release Readiness
> **Target Release:** OpenProjectLab v1.0.0
> **Baseline Date:** 2026-08-17
> **Previous Milestone:** Milestone 7 — Marketplace
> **Purpose:** Define the final pre-v1.0 stabilization scope, release gates, public contract boundaries, documentation requirements, compatibility policy, automation requirements, and RC acceptance criteria.

---

## 1. Purpose

Milestone 8 is the final engineering milestone before the first stable OpenProjectLab release.

The objective is not to introduce another major product capability.

The objective is to establish that the capabilities already implemented across the preceding milestones are sufficiently:

- stable;
- documented;
- testable;
- installable;
- compatible;
- supportable;
- reproducible;
- maintainable;
- ready for a public `v1.0.0` compatibility commitment.

The Milestone 8 transition is therefore:

```text
Feature Development
        ↓
Contract Audit
        ↓
Stabilization
        ↓
Release Hardening
        ↓
Release Candidate
        ↓
v1.0.0
```

Milestone 8 follows the existing OpenProjectLab engineering principles:

```text
Design First
    ↓
Documentation First
    ↓
Automation First
    ↓
Testing First
    ↓
Review
    ↓
Release
```

## 3. Milestone 8 Objective

Milestone 8 answers one primary question:

> **Which OpenProjectLab capabilities are ready to become stable v1.0 contracts?**

This requires explicit classification of:

- Public API;
- CLI behavior;
- Plugin SDK;
- Generator contracts;
- Courseware contracts;
- AI contracts;
- Marketplace contracts;
- configuration;
- filesystem behavior;
- error behavior;
- generated artifacts;
- installation and packaging;
- documentation;
- automation;
- supported environments.

The result must establish a documented v1.0 compatibility boundary.

---

## 4. Feature Freeze

Milestone 8 operates under a **feature-freeze mindset**.

A change may be accepted during stabilization when it is necessary for:

- correctness;
- security;
- compatibility;
- reliability;
- installation;
- packaging;
- documentation correctness;
- test completeness;
- deterministic behavior;
- release automation;
- supportability;
- release-blocking usability.

A change should normally be deferred when it introduces:

- a new major workflow;
- a new platform subsystem;
- a new public API unrelated to release correctness;
- a major new Marketplace capability;
- a new AI capability;
- a new Generator family;
- a major new Plugin mechanism;
- another execution lifecycle;
- significant scope that is not required for v1.0 readiness.

Non-blocking improvements discovered during Milestone 8 belong in the v1.1 backlog.

# 8.1 — Release Readiness Baseline

## 6. Purpose

- deferred capabilities;
- required documentation;
- automation expectations;
- acceptance sequence.

No production behavior should be changed merely to complete Step 8.1.

---

## 7. Contract Classification

Every important externally visible capability should be classified using one of the following states.

### Stable

A capability intended to become part of the v1.0 compatibility commitment.

A Stable contract must have:

- documented behavior;
- defined ownership;
- deterministic tests;
- compatibility expectations;
- no unresolved critical ambiguity;
- release-quality documentation.

Breaking a Stable contract after v1.0 normally requires:

- a deprecation path; or
- a future major release.

---

### Candidate

A capability currently implemented and potentially suitable for Stable status, but requiring audit before v1.0 freeze.

Candidate is the normal starting classification for implemented but not yet formally frozen behavior.

---

### Experimental

A capability available in v1.0 but intentionally excluded from the full compatibility guarantee.

Experimental behavior must be:

- explicitly documented as Experimental;
- clearly separated from Stable behavior;
- safe to use within documented constraints;
- excluded from accidental compatibility promises.

---

### Internal

Implementation detail not intended as a public compatibility contract.

Internal code may evolve without a public compatibility promise, provided Stable behavior remains unchanged.

---

### Deferred

A capability intentionally excluded from v1.0 scope.

Deferred work must not block v1.0 unless a later release-readiness decision explicitly promotes it into scope.

# 8.2 — Public Contract Audit & Freeze

## 9. Objective

Step 8.2 identifies every interface that users, third-party developers, automation, generated projects, or external integrations may reasonably depend on.

The audit must distinguish:

```text
Public Contract
Experimental Contract
Internal Implementation
```

The goal is to eliminate ambiguity before v1.0.

---

## 10. Public Contract Audit Areas

The audit must cover at least:

```text
CLI
Generator lifecycle
Generator request / plan / result models
generator.sdk
Plugin SDK
Plugin Entry Point
Plugin validation
Plugin registration
Course / Week Domain
Built-in Generators
Courseware Composition
AI provider-independent contracts
Marketplace artifact contracts
Configuration
Exceptions
Filesystem-visible semantics
Generated artifact structure
Installation entry points
```

For every public contract, answer:

- What is its canonical import path?
- What is its canonical name?
- Which fields are stable?
- Which behavior is guaranteed?
- Which validation rules are stable?
- Which output ordering is stable?
- Which exception types are public?
- Which filesystem layouts are public?
- Which CLI syntax is stable?
- Which behavior is explicitly not guaranteed?
- What can be changed in v1.x?
- What would require v2.0?

---

## 11. Freeze Rule

A contract may transition to Stable only when:

```text
Implementation exists
        ↓
Tests define behavior
        ↓
Documentation describes behavior
        ↓
Compatibility implications understood
        ↓
No unresolved release-blocking ambiguity
        ↓
Stable
```

No contract is Stable merely because a class or function is importable.

---

## 12. Public SDK Discipline

`generator.sdk` must remain intentionally small.

Milestone 8 must verify:

- every export is deliberate;
- no implementation detail is accidentally exported;
- existing documented exports have tests;
- public symbol removal is treated as compatibility-sensitive;
- Marketplace does not accidentally expand the SDK;
- individual Generator implementations do not introduce unrelated SDK surface.

# 8.3 — Reliability / Regression Hardening

## 13. Objective

Step 8.3 verifies that existing capabilities behave reliably across representative success and failure paths.

This is not a feature-expansion phase.

The focus is:

- regressions;
- edge cases;
- failure isolation;
- deterministic behavior;
- side-effect safety;
- error clarity;
- cleanup;
- idempotency where already promised;
- contract consistency.

---

## 14. Regression Baseline

Milestone 8 begins from:

```text
1315 passed, 1 deselected
89.89% total coverage
67.0% required coverage
```

Every stabilization change must preserve or improve the release baseline.

The historical Milestone 7 baseline must not automatically be reused as Milestone 8 final acceptance evidence.

Final Milestone 8 evidence must be collected from the completed stabilization branch.

---

## 15. Required Hardening Areas

At minimum:

### Generator Framework

- canonical lifecycle;
- validation before side effects;
- deterministic plans;
- dry-run semantics;
- overwrite behavior;
- failure propagation;
- stable result aggregation.

### Plugin System

- discovery;
- validation;
- Entry Point behavior;
- duplicate handling;
- transactional registration;
- installed third-party example path.

### Courseware

- Domain invariants;
- deterministic Week ordering;
- material Generator contracts;
- composition ordering;
- representative E2E.

### AI

- invalid responses fail before filesystem mutation;
- Fake provider determinism;
- provider-specific implementation remains behind provider-independent boundary;
- normal test suite remains network-independent;
- missing credential behavior remains safe.

### Marketplace

- exact coordinate semantics;
- deterministic lookup;
- integrity mismatch before installation;
- no partial installation state;
- Template Package path safety;
- no accidental Plugin activation or Generator execution.

### Filesystem

Only actual implemented filesystem guarantees should become release requirements.

Proposed filesystem capabilities must not be silently treated as already implemented.

### Errors

Only actual implemented exception/CLI behavior should become Stable.

Proposed structured error codes, debug mode, classified exit codes, or expanded exception hierarchies must not be overclaimed.

At minimum, evaluate:

- Entry Points;
- Generator lifecycle;
- configuration;
- generated artifact contracts;
- Marketplace artifact contracts;
- public exceptions;
- Courseware Domain.

---

## 26. Semantic Versioning Intent

The release policy should follow the practical meaning:

```text
1.0.x
    bug fixes
    security fixes
    documentation corrections
    compatible reliability fixes

1.x
    backward-compatible capabilities
    compatible API evolution

2.0
    intentional breaking public-contract changes
```

Actual versioning behavior must be documented before GA.

---

## 27. Deprecation Policy

Stable public contracts must not disappear unexpectedly.

The deprecation lifecycle should follow:

```text
Stable
   ↓
Deprecated
   ↓
Warning + Migration Guidance
   ↓
Compatibility Window
   ↓
Removal in an allowed future release
```

The final policy must define:

- what counts as deprecation;
- how users are warned;
- minimum migration expectations;
- documentation requirements;
- test requirements;
- when removal is allowed.

## 42. Release Candidate Policy

After `v1.0.0-rc.1`, changes should normally be restricted to:

- release blockers;
- correctness defects;
- compatibility defects;
- installation defects;
- security defects;
- documentation errors;
- test defects that hide release risk;

```text

      ↓

        ↓

        ↓
final verification
        ↓
v1.0.0
```

Milestone 8 therefore remains the final pre-v1.0 engineering milestone.

A new feature milestone must not be inserted between Milestone 8 and v1.0 merely to continue feature development.

Post-release verification is operational closure, not a new feature milestone.

## 45. v1.0.x

The `v1.0.x` line is primarily for:

- security fixes;
- documentation corrections;
- compatibility-preserving reliability fixes.

## 46. v1.1+

Non-blocking improvements discovered during stabilization should move into a v1.1 backlog.

Potential examples include:

- advanced filesystem transactions;
- expanded structured errors;
- additional Marketplace capabilities;
- additional AI capabilities;
- plugin developer tooling;
- documentation tooling;
- expanded platform support;
- UX improvements.

Deferred work should not silently migrate back into the v1.0 release scope.

## 48. ADR Policy

Milestone 8 does not automatically require a new ADR for every release-readiness task.

Create a new ADR only when stabilization introduces or formalizes a significant architectural decision, such as:

# Milestone 8 Acceptance Principle

Milestone 8 should not measure success by the number of new features added.

Success means that a user can install, understand, execute, extend, and upgrade OpenProjectLab using documented Stable contracts with predictable behavior.

The release-readiness principle is:

```text
Do not add what v1.0 does not need.
Audit what v1.0 already has.
Stabilize what v1.0 promises.
Document what v1.0 supports.
Automate what v1.0 must verify.
Release only what v1.0 can maintain.
```
