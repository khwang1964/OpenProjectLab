# OpenProjectLab v1.0 GA Build / Artifact Identity

> **Status:** Design / Contract Definition — In Progress
> **Milestone:** v1.0 GA Acceptance
> **Step:** GA.3 — GA Version / Artifact Identity
> **Date:** 2026-08-20
> **Predecessor:** GA.1 — GA Acceptance Baseline / RC Evidence Review — Completed
> **Accepted RC:** `v1.0.0-rc.1`
> **Target GA:** `v1.0.0`
> **Canonical GA package version:** `1.0.0`

---

## 1. Purpose

GA.3 defines the stable v1.0 package/version/artifact identity that must exist
before artifact-backed GA verification can begin.

This step owns the controlled transition from the accepted RC package version:

```text
1.0.0rc1
```

to the stable package version:

```text
1.0.0
```

GA.3 does not create the `v1.0.0` tag, does not publish a GitHub Release, and
does not formally accept GA.

---

## 2. Governing Decision

GA.3 is fail-closed.

The stable GA identity is valid only when all of the following agree:

```text
Canonical project version
        ↓
Expected GA tag
        ↓
Fresh wheel metadata
        ↓
Fresh sdist metadata
        ↓
Exact artifact-set membership
        ↓
SHA-256 manifest
        ↓
Release-source commit identity
```

Any unexplained mismatch blocks GA progression.

---

## 3. Canonical Stable Identity

The canonical Python package version is:

```text
1.0.0
```

The canonical human-facing GA tag is:

```text
v1.0.0
```

Required mapping:

```text
1.0.0
    ↕
v1.0.0
```

The existing RC mapping must remain valid:

```text
1.0.0rc1
    ↕
v1.0.0-rc.1
```

GA support must not break RC identity normalization.

---

## 4. Stable GitHub Release Classification

The expected GA GitHub Release classification is:

```text
draft       true before publication validation
prerelease  false
```

The stable release must never be classified as an RC/prerelease.

GA.3 verifies the stable classification contract but does not publish the
Release.

---

## 5. Version-transition Contract

The repository may transition to:

```text
project.version = 1.0.0
```

only after GA.1 blocker disposition has passed.

The version change must be reviewed and must preserve:

- frozen v1.0 public contracts;
- compatibility/deprecation policy;
- support matrix;
- known limitations;
- release automation semantics;
- RC release identity compatibility.

The version transition must not implicitly create or authorize the stable tag.

---

## 6. Fresh Build Requirement

GA artifacts must be freshly built after the repository version becomes
`1.0.0`.

The artifact output directory must be clean before build.

Required distribution artifacts:

```text
openprojectlab-1.0.0-py3-none-any.whl
openprojectlab-1.0.0.tar.gz
```

No RC artifact may satisfy GA.3.

Explicitly rejected examples include:

```text
openprojectlab-1.0.0rc1-py3-none-any.whl
openprojectlab-1.0.0rc1.tar.gz
```

---

## 7. Exact Artifact-set Contract

The GA distribution set must contain exactly one wheel and exactly one sdist.

No duplicate, stale, or unrelated distribution may be accepted.

The checksum manifest must describe exactly the GA wheel and GA sdist bytes.

Required publication set:

```text
openprojectlab-1.0.0-py3-none-any.whl
openprojectlab-1.0.0.tar.gz
SHA256SUMS.txt
```

The checksum manifest itself is not included in the manifest's wheel/sdist
coverage requirement.

---

## 8. Metadata Contract

Wheel metadata version must equal:

```text
1.0.0
```

Source-distribution metadata version must equal:

```text
1.0.0
```

A distribution named as GA but containing `1.0.0rc1` metadata is invalid.

A distribution with correct metadata but stale bytes from another source
commit is also invalid.

---

## 9. SHA-256 Contract

GA.3 requires SHA-256 digests for the exact fresh wheel and sdist bytes.

The generated manifest must:

- contain one entry for the wheel;
- contain one entry for the sdist;
- contain no stale RC artifact entry;
- contain no unexpected distribution entry;
- match recomputed SHA-256 digests exactly;
- be written without a UTF-8 BOM.

Any checksum mismatch is a GA blocker.

---

## 10. Release-source Commit Binding

GA.3 evidence must bind the fresh artifacts to the exact source commit from
which they were built.

The approved GA source commit must:

- be a full Git SHA;
- be reachable from synchronized `main`;
- contain the stable `1.0.0` version transition;
- be the source of the GA wheel and sdist;
- later become the exact target of `v1.0.0`.

The GA tag must not be created during this step.

---

## 11. RC Identity Preservation

GA.3 must not alter the accepted RC publication identity.

The existing RC remains:

```text
Package version
    1.0.0rc1

Tag
    v1.0.0-rc.1

Published RC source SHA
    b5958edbbf0e3279ed74fa0e3aee13e893c5dfc8
```

The RC tag must remain immutable.

The GA source commit is a new stable-release source identity and may differ
from the RC source commit.

---

## 12. Required GA.3 Verification

GA.3 focused verification must prove:

```text
canonical project version == 1.0.0
expected_release_tag("1.0.0") == "v1.0.0"
expected_release_tag("1.0.0rc1") == "v1.0.0-rc.1"
stable GitHub Release prerelease == false
fresh wheel filename is canonical
fresh sdist filename is canonical
wheel metadata version == 1.0.0
sdist metadata version == 1.0.0
artifact set is exact
SHA256SUMS.txt covers exact wheel + sdist bytes
no RC artifact is accepted as GA
release-source commit is explicit
```

---

## 13. Required Build Commands

The intended local completion sequence is:

```text
clean dist/build metadata
        ↓
python -m build
        ↓
python -m twine check dist/*
        ↓
verify exact wheel/sdist set
        ↓
generate SHA256SUMS.txt
        ↓
verify manifest against recomputed digests
        ↓
run focused GA.3 tests
```

Actual completion evidence must be recorded from execution, not pre-filled.

---

## 14. GA.3 Non-goals

GA.3 does not:

- create `v1.0.0`;
- push `v1.0.0`;
- create a GitHub Release;
- upload GA artifacts;
- run final installed-user GA acceptance;
- claim GA publication identity;
- claim formal GA Acceptance.

These belong to later gates.

---

## 15. Failure Classification

| Failure | Meaning | Response |
|---|---|---|
| Version mismatch | repository/artifact version is not `1.0.0` | stop |
| Tag mapping mismatch | stable/RC mapping is wrong | stop |
| RC artifact reuse | GA build uses rc1 artifact | rebuild |
| Metadata mismatch | filename/version metadata disagree | stop |
| Artifact-set mismatch | missing/extra/duplicate distributions | stop |
| Checksum mismatch | manifest != exact artifact bytes | stop |
| Source identity mismatch | artifacts not bound to approved GA SHA | rebuild |
| Release classification mismatch | stable spec marked prerelease | stop |

---

## 16. Automation Contract

`tests/release_readiness/test_v1_ga_build_artifact_identity.py` must verify:

- GA.3 design exists;
- current canonical version is `1.0.0` once the version transition is applied;
- stable tag mapping is `v1.0.0`;
- RC tag mapping remains `v1.0.0-rc.1`;
- stable GitHub Release spec is non-prerelease;
- expected GA filenames are fixed;
- RC filenames are rejected by GA artifact-set checks;
- checksum coverage is exact;
- release-source commit binding is required;
- `v1.0.0` tag creation remains unauthorized in this step;
- formal GA Acceptance remains Not Accepted.
