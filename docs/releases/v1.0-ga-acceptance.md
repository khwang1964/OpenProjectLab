# OpenProjectLab v1.0 GA Acceptance

> **Status:** Design / Contract Definition — In Progress
> **Milestone:** v1.0 GA Acceptance
> **Step:** GA — General Availability Acceptance
> **Date:** 2026-08-20
> **Predecessor:** Step 8.10 — RC Acceptance — Accepted

> **Target GA:** `v1.0.0`

---

## 1. Purpose

This document is the governing design and acceptance contract for
OpenProjectLab `v1.0.0` General Availability.

GA Acceptance answers one release-level question:

> After the accepted `v1.0.0-rc.1` validation period, is there sufficient
> evidence to declare OpenProjectLab `v1.0.0` stable for General Availability
> without weakening the accepted v1.0 public, compatibility, support,
> documentation, packaging, or release contracts?

GA Acceptance is not an automatic consequence of RC Acceptance.

The accepted RC proves that one release candidate is coherent and publishable.
GA Acceptance additionally requires evidence that no unresolved GA blocker
remains after actual RC validation and any accepted RC-period corrections.

---

## 2. Governing Decision

GA Acceptance is fail-closed.

`v1.0.0` may be accepted only when all required evidence describes the same
stable release:

```text
Accepted v1.0.0-rc.1
        ↓
RC validation / observation evidence
        ↓
GA blocker review
        ↓
Approved GA source commit
        ↓
Canonical GA version = 1.0.0
        ↓
Fresh GA wheel + sdist
        ↓
GA checksum manifest
        ↓
Artifact-backed GA verification
        ↓
Full regression / local quality gates
        ↓
Required GitHub Actions / CI
        ↓
GA tag = v1.0.0
        ↓
GitHub Release = stable / non-prerelease
        ↓
Formal GA acceptance evidence
```

No individual passing gate compensates for missing, stale, contradictory, or
unverified evidence elsewhere in the chain.

---

## 3. Accepted Prerequisite

The GA process requires formal completion of Step 8.10 RC Acceptance.

Required prerequisite:

```text
Step 8.10 RC Acceptance --- Accepted
Accepted RC --- v1.0.0-rc.1
```

The accepted RC publication identity remains immutable.

GA work must not:

- retarget `v1.0.0-rc.1`;
- replace published RC artifact bytes;
- rewrite RC checksums;
- mutate the published RC GitHub Release into a GA Release.

GA creates a new stable identity.

---

## 4. RC Evidence Review

Before any GA version or tag mutation, maintainers must review actual RC-period
evidence.

The review must identify:

- defects discovered after RC publication;
- packaging or installation failures;
- compatibility regressions;
- documentation correctness issues;
- support-matrix contradictions;
- security defects;
- release automation defects;
- user-facing behavioral regressions;
- known limitations requiring reclassification;
- whether any accepted correction changed source or artifact evidence.

The GA decision must distinguish:

```text
GA blocker
    must be fixed before GA

GA correction
    accepted correctness/documentation/release fix requiring affected gates
    to be re-run

Post-GA patch candidate
    may be deferred to v1.0.x only if GA correctness is not compromised

v1.1+ deferred improvement
    outside v1.0 GA scope
```

A GA blocker must not be reclassified merely to complete the release.

---

## 5. Explicit Non-goals

GA Acceptance does not:

- add new v1.0 product capabilities;
- expand the frozen Stable public surface without formal compatibility review;
- silently expand the support matrix;
- hide or weaken accepted known limitations;
- absorb deferred v1.1+ scope;
- treat RC success as sufficient evidence without GA review;
- reuse stale RC artifacts as GA artifacts;
- treat skipped required artifact-backed tests as passing GA evidence;
- claim byte-for-byte reproducibility unless separately demonstrated;
- modify the immutable `v1.0.0-rc.1` publication identity.

## 7. GA Source Provenance

GA must bind to one approved immutable source commit.

The approved GA source commit:

- may differ from the RC publication source commit;
- must include all accepted RC-period corrections;
- must be a full Git SHA;
- must be reachable from synchronized `main`;
- must be the exact source used for final GA artifacts;
- must be the exact target of `v1.0.0`.

The GA acceptance process must explicitly record the relationship among:

```text
RC publication source commit
RC terminal acceptance commit
GA approved source commit
GA tag target commit
```

These values must not be conflated.

---

## 8. Version Transition Contract

The repository may transition from:

```text
1.0.0rc1
```

to:

```text
1.0.0
```

only after the GA baseline / RC evidence review and governing contract
automation pass.

The version transition must:

- occur through reviewed source changes;
- update the canonical package version;
- preserve all Stable v1.0 public contracts;
- preserve intended compatibility/deprecation policy;
- remain consistent with release automation;
- not create the GA tag or Release prematurely.

---

## 9. Fresh GA Artifact Contract

GA artifacts must be freshly built from the approved GA source commit.

Required distribution artifacts:

```text
openprojectlab-1.0.0-py3-none-any.whl
openprojectlab-1.0.0.tar.gz
SHA256SUMS.txt
```

The artifact output directory must be clean before the final GA build.

Verification must reject:

- RC artifacts such as `1.0.0rc1`;
- stale GA artifacts from an earlier source commit;
- duplicate wheels or sdists;
- unexpected extra distributions;
- metadata version mismatch;
- checksum mismatch;
- artifact bytes not used by installed-user verification.

---

## 10. Artifact-backed GA Verification

The actual GA wheel must back all required installed-user checks.

Required evidence includes:

- wheel metadata;
- sdist metadata;
- checksum manifest;
- clean installation;
- installed distribution version;
- source-checkout isolation;
- installed `opl` entry point;
- packaged runtime resources;
- First 15 Minutes workflow;
- representative installed-user E2E;
- integrated package / release identity;
- documentation behavior against the GA wheel.

Required artifact-backed tests must have zero required skips.

---

## 11. Public Contract and Compatibility Boundary

GA must preserve all accepted v1.0 release authorities, including:

- Step 8.2 Stable public-contract freeze;
- Step 8.5 bilingual User Manual parity;
- Step 8.6 compatibility and deprecation policy;
- Step 8.7 support matrix and known limitations;
- Step 8.8 release automation / reproducibility;
- Step 8.9 release-readiness acceptance;
- Step 8.10 RC acceptance.

A GA correction may fix behavior required by these contracts, but must not
silently expand them.

---

## 12. Documentation Boundary

Before GA Acceptance, documentation must describe the release as GA and remain
consistent with actual behavior.

Required review includes:

- installation;
- Quick Start / First 15 Minutes;
- configuration;
- CLI;
- generators;
- Courseware;
- Plugins;
- AI integration;
- Marketplace;
- architecture / concepts;
- troubleshooting;
- compatibility / deprecation policy;
- support matrix;
- known limitations;
- release-status wording;
- EN / zh-TW structure and functional parity.

Any remaining RC-only wording that incorrectly describes the GA state must be
corrected through reviewed documentation changes.

---

## 13. Support and Known-limitations Boundary

GA must not make unsupported environment claims.

The support matrix remains evidence-backed.

Known limitations must:

- remain visible;
- be accurate for GA;
- distinguish Supported / Experimental / Deferred where applicable;
- identify any GA-relevant caveat discovered during RC validation.

A known limitation is not automatically a GA blocker if it is already within
the accepted v1.0 contract and does not invalidate the release promise.

## 14. GA Acceptance Lifecycle

The recommended fail-closed lifecycle is:

```text
GA.1  GA Acceptance Baseline / RC Evidence Review
```

These labels may be refined through reviewed changes, but none of the
responsibilities may be omitted.

## 20. GA.6 — GitHub Actions / CI

Required GitHub Actions jobs must pass on the actual GA acceptance branch / PR.

## 21. GA.7 — GA Creation / Publication Identity

GA publication must be draft-first.

Expected GitHub Release identity:

```text
tag              v1.0.0
target commit    <approved GA source SHA>
draft            true before final validation
prerelease       false
```

The draft must contain exactly:

```text
openprojectlab-1.0.0-py3-none-any.whl
openprojectlab-1.0.0.tar.gz
SHA256SUMS.txt
```

Before publication, validate:

- tag target;
- target commit;
- exact assets;
- checksums;
- stable/non-prerelease classification;
- release title / notes;
- known-limitations / support references.

After publication, re-read GitHub state and verify the final identity.

---

## 22. GA Tag Immutability

The canonical GA tag is:

```text
v1.0.0
```

After publication:

- do not force-move the tag;
- do not replace wheel bytes;
- do not replace sdist bytes;
- do not replace checksum identity under the same release;
- do not mutate the GA Release to point at another source commit.

If a published GA defect is discovered, correct it through an appropriate
subsequent release such as `v1.0.1`, not by rewriting `v1.0.0`.

## 25. Failure Classification

| Class | Meaning | Required response |
|---|---|---|
| GA blocker | Stable v1.0 promise is violated | Fix before GA |
| Identity mismatch | Version/source/tag/artifact/release disagree | Stop GA |
| RC evidence gap | RC validation evidence is insufficient | Produce evidence |
| Artifact evidence gap | GA artifact proof is missing | Rebuild / re-run |
| Documentation defect | GA docs disagree with behavior | Correct / re-verify |
| Unsupported expansion | Support/public claim exceeds accepted evidence | Remove or review |
| Patch candidate | Non-blocking post-GA correctness fix | Consider v1.0.x |
| Deferred improvement | Outside stable v1.0 scope | Keep for v1.1+ |

---

## 26. Automation and Safety Rules

GA automation must be:

- deterministic;
- fail-closed;
- artifact-backed where artifacts are required;
- explicit about missing prerequisites;
- safe against stale artifact selection;
- safe against RC/GA identity confusion;
- non-destructive in ordinary verification;
- unable to publish from ordinary PR CI;
- auditable through exact SHA / version / tag / checksum identity.

Release mutation must remain separate from read-only verification.
