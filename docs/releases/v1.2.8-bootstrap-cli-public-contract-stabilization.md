# OpenProjectLab v1.2.8 Bootstrap CLI Public Contract Stabilization

> **Status:** Accepted --- Terminally Closed
> **Predecessor:** v1.2.7 Bootstrap CLI/runtime wiring --- Accepted / Completed
> **Implementation:** Not Started

## Objective

Define the public contract that may promote the minimum v1.2.7 experimental
Bootstrap CLI/runtime wiring into a stable, supportable interface. This slice
defines observable behavior before any production stabilization work begins.

## Public command boundary

``` text
Command surface --- bootstrap only
Current experimental opt-in --- preserved during design
Legacy no-opt-in behavior --- unchanged
Stable public option names --- Proposed, not yet accepted
Programmatic SDK exposure --- Deferred
Advanced lifecycle controls --- Deferred
```

No design statement silently removes the experimental boundary. Promotion to a
stable interface requires a later, separately reviewed implementation slice.

## Invocation and parsing contract

- CLI parsing is side-effect free.
- Unknown options and missing required values fail before runtime invocation.
- User input is normalized exactly once into an immutable runtime request.
- Equivalent normalized inputs produce equivalent runtime requests.
- Validation is explicit; it is never inferred from unrelated flags.

## Exit status contract

``` text
Successful requested operation --- exit 0
Usage or parser error --- exit 2
Runtime execution failure --- exit 1
Validation findings that fail the request --- exit 1
Internal check execution failure --- exit 1, fail closed
Success-shaped partial result --- Forbidden
```

The final implementation must expose one terminal status. A failed apply or
validation phase must not be rewritten as success merely because earlier
planning or inspection completed.

## Output-channel contract

``` text
Requested result / deterministic summary --- stdout
Usage errors and operational diagnostics --- stderr
Ordering --- deterministic and lifecycle-defined
Machine-readable JSON output --- Deferred
Secrets and raw exception internals --- Forbidden
```

Text output is the only candidate public format in this slice. Exact prose may
evolve, but phase identity, terminal status, and failed-check identity must
remain observable and deterministically ordered.

## Validation failure semantics

Validation inspects the completed lifecycle result and produces ordered
findings. Invalid state is a finding; check execution failure is a fail-closed
operational error. Validation must not call apply, must not repair filesystem state, and validation failure does not imply automatic rollback.

## Compatibility and safety

- Existing invocations without the experimental opt-in keep their v1.2.7 behavior.
- Filesystem mutation remains owned by the established apply executor.
- Dry-run remains inspection-only.
- Validation remains inspection-only.
- No repair, implicit retry, automatic rollback, or hidden fallback is added.
- Public SDK, JSON output, plugins, remote execution, and advanced lifecycle
  orchestration remain outside this slice.
