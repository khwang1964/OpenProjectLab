## 1. Purpose

This document defines the design boundary within which OpenProjectLab may add
Marketplace and AI command-line workflows during v1.1. It preserves the
accepted v1.0 command-line contract and establishes common rules for later
command-specific contracts.

This slice is design and automation only. It does not add a production
`marketplace` or `ai` command, accept either command-specific contract, or
provide implementation evidence for a later delivery slice.

## 2. Governing Sources

The design is governed by:

- `docs/releases/v1.1-planning-baseline.md`;
- `docs/releases/v1.0-public-contract-audit.md`;
- `docs/releases/v1.0-compatibility-deprecation-policy.md`;
- `generator/cli/main.py` as the production parser and dispatch source;
- `tests/integration/test_v1_cli_public_contract.py` as the executable v1
  compatibility freeze;
- the English and Traditional Chinese (Taiwan) CLI user-manual chapters.

Historical documentation or proposed syntax cannot override the production
parser or the accepted v1 tests.

## 3. Preserved v1.0 Stable Surface

The following installed entry point remains Stable:

``` text
opl = generator.cli.main:main
```

The reviewed v1 command inventory remains valid:

``` text
assignment
bootstrap
course
lab
list
quiz
slides
upgrade
website
week
```

The legacy `opl --list` compatibility path remains valid and aligned with
`opl list`. Existing required arguments, structured JSON input options,
generation options, default behavior, and accepted artifact semantics remain
compatible. In particular, generation commands retain the reviewed
`--dry-run`, `--force`, and `--no-manifest` controls.

v1.1 may add commands and options, but it must not remove, rename, silently
reinterpret, or make an existing valid v1 command line invalid. Any future
deprecation must follow the accepted compatibility and deprecation policy.

## 4. Additive v1.1 Command Families

The names below are reserved for dedicated later contracts:

``` text
opl marketplace ...
opl ai ...
```

They are command-family identities, not implemented syntax. Their
subcommands, arguments, output schemas, and operational behavior must be
defined by their dedicated slices:

- v1.1.3 --- Marketplace CLI Contract;
- v1.1.5 --- AI CLI Contract.

Production registration is prohibited during v1.1.2. Marketplace
implementation belongs to v1.1.4 and AI implementation belongs to v1.1.6,
after the corresponding contract has been reviewed and accepted.

## 5. Common Command-shape Rules

Each later command-specific contract must record:

- canonical command and subcommand names;
- positional arguments and whether each is required;
- long option names, types, defaults, repeatability, and conflicts;
- input encoding and structured-file schema boundaries;
- deterministic ordering rules;
- dry-run or other side-effect controls where applicable;
- stdout, stderr, and process-exit behavior;
- filesystem, credential, and network boundaries;
- Stable, Experimental, Internal, and Deferred classifications;
- bilingual user-documentation obligations;
- migration behavior for any interaction with v1 syntax.

Aliases are not Stable merely because argparse can support them. Short
options, environment variables, configuration keys, and machine-readable
formats require explicit review before becoming public contracts.

## 6. Exit-code Contract

The currently verified common behavior is deliberately narrow:

| Exit | Meaning | Contract state |
| ---: | --- | --- |
| `0` | Successful reviewed operation | Stable |
| `2` | argparse usage failure or a production-handled validation/runtime/filesystem failure | Stable, broad category only |

No finer taxonomy is claimed by this design. Exact human-readable error text
is not Stable unless a later contract explicitly freezes it.

Later command-specific contracts may define additional exit codes only when
production behavior, focused tests, documentation, and backward-compatibility
review are supplied together. They must not redefine an existing successful
v1 invocation as failure.

## 7. stdout and stderr

The common stream boundary is:

- successful human-readable results are written to stdout;
- argparse diagnostics and handled operational errors are written to stderr;
- successful core workflows must not require parsing stderr;
- failures must not report a successful result on stdout after a side effect
  boundary has failed.

Human-readable wording, spacing, and localization are not byte-for-byte Stable
unless separately frozen. Semantic identities and any explicitly accepted
machine-readable schema are compatibility-sensitive.

## 8. Machine-readable Output

v1.1.2 does not claim a production `--json` option or a Stable JSON output
schema. A later command contract may propose machine-readable output only if
it defines:

- an explicit opt-in option;
- UTF-8 encoding and one unambiguous document boundary;
- schema versioning or compatible additive evolution rules;
- deterministic field and collection semantics;
- stdout reserved for the document and diagnostics reserved for stderr;
- tests covering success, empty results, and failures.

Human-readable output must not be relabelled as a machine-readable contract.

## 9. Side-effect and Failure Boundary

All new CLI workflows must validate command shape, structured inputs,
coordinates or requests, and required local preconditions before irreversible
side effects. Failure must not leave partial Marketplace installation,
partially generated Courseware, mutated Plugin/Generator registration, or a
success record that was not earned.

`--dry-run`, when a later contract exposes it, means validation and planned
result reporting without production filesystem mutation. It must not imply
remote access or live-provider invocation.

## 10. Marketplace CLI Boundary

The future Marketplace command may compose existing deterministic local
contracts for listing, inspection, exact-coordinate lookup, acquisition,
SHA-256 integrity verification, and deterministic installation results.

It must not imply:

- a remote Marketplace or Community Repository service;
- dependency solving or package-manager behavior;
- automatic Plugin or Generator activation;
- signing, publisher trust, sandboxing, ratings, payment, or monetization;
- Marketplace-driven execution;
- AI Provider Marketplace behavior.

Distribution, validation, acquisition, integrity verification, installation,
activation, and execution remain separate responsibilities.

## 11. AI CLI Boundary

The future AI command may compose provider-independent request, structured
response validation, and Courseware-generation application services.

Normal tests and required CI must remain deterministic, credential-free, and
network-independent, using the fake-provider boundary. Live-provider use
remains Experimental and opt-in. Provider SDK types, credentials, paid-account
requirements, streaming, and tool calling must not leak into the Stable CLI
contract.

## 12. Documentation and Verification

Before either new command becomes an accepted user-facing capability, it
requires:

- a dedicated contract accepted before implementation;
- focused parser, dispatch, success, failure, and no-partial-side-effect tests;
- preservation of `tests/integration/test_v1_cli_public_contract.py`;
- English and Traditional Chinese (Taiwan) functional documentation parity;
- representative installed-wheel behavior;
- deterministic core CI without network or credentials;
- CHANGELOG, HISTORY, and Roadmap alignment;
- full regression, coverage, local quality gates, and required CI evidence.

Test counts, coverage, PR numbers, commit identities, and CI outcomes must be
recorded only after the corresponding evidence exists.

## 13. Acceptance Gates

v1.1.2 may be accepted only when:

- this design and its fail-closed automation are reviewed;
- the v1 command inventory and compatibility test remain preserved;
- `marketplace` and `ai` remain absent from the production parser;
- both later CLI implementations remain Not Started;
- focused tests, full regression, coverage, and local quality gates pass;
- required CI passes;
- the governing PR is squash merged;
- `main` is synchronized and post-merge consistency is verified;
- Roadmap, HISTORY, and CHANGELOG reach the same terminal state.

Acceptance of v1.1.2 does not accept v1.1.3 or any implementation slice.

## 14. Code Review Checklist

### Compatibility

- [ ] The installed `opl` entry point and reviewed v1 commands remain valid.
- [ ] Legacy `opl --list` remains compatible.
- [ ] Existing required arguments and generation controls remain valid.
- [ ] No accidental Stable option, alias, output schema, or exit code is added.

### Scope

- [ ] `marketplace` and `ai` are design-only reserved command families.
- [ ] Remote Marketplace and automatic activation remain Deferred.
- [ ] Live AI remains Experimental, opt-in, and outside core verification.
- [ ] No Marketplace or AI implementation evidence is fabricated.

### Quality

- [ ] Common streams, exit behavior, and side-effect rules are explicit.
- [ ] Dedicated later contracts are required before implementation.
- [ ] EN/zh-TW parity and installed-artifact verification remain required.
- [ ] Roadmap, HISTORY, and CHANGELOG agree on the current state.
