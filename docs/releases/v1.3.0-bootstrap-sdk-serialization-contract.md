# OpenProjectLab v1.3.0 Bootstrap SDK Serialization Contract

> **Status:** Accepted --- Terminally Closed
> **Predecessor:** v1.2.9 Bootstrap SDK Runtime --- Accepted / Completed

## Goal

Define a versioned, deterministic JSON interchange contract for bootstrap SDK requests,
results, and evidence without making deserialization an execution path.

## Proposed public surface

The proposed module is `generator.sdk.bootstrap_serialization`.

```text
BootstrapSchemaVersion
BootstrapSerializationError
serialize_bootstrap_request
deserialize_bootstrap_request
serialize_bootstrap_result
deserialize_bootstrap_result
```

The initial schema identifier is `opl.bootstrap/1.0`. Existing `generator.sdk` root
exports and `generator.sdk.bootstrap_runtime` remain source compatible.

## Envelope and canonical encoding

Every document contains exactly these envelope fields:

```text
schema
document_type
payload
```

`document_type` is exactly `bootstrap-request` or `bootstrap-result`. Encoding uses
UTF-8 JSON, sorted object keys, compact separators, no insignificant whitespace, and
rejects NaN or Infinity. Repeated serialization of equal contract values produces
byte-for-byte identical text.

Array order is authoritative for plan steps, expected effects, completed apply steps,
executed check identities, findings, and completed failure evidence. Object key order
has no semantic meaning. Path fields are lexical Unicode strings using forward slashes;
deserialization must not resolve, canonicalize, access, or test filesystem paths.

## Strict decoding and round-trip

Unknown schema identifiers, unknown document types, duplicate JSON object keys, unknown contract fields, missing required fields, invalid enum values, non-finite numbers, and
wrong JSON types fail closed as `BootstrapSerializationError`.

Supported request and result values round-trip without losing modes, normalized inputs,
ordered plan/effect/apply/validation evidence, validity, or absent-phase distinction.
Decoded values are immutable typed DTOs suitable for inspection; callers explicitly
construct or invoke runtime operations separately.

## Safety boundary

Deserialization must not call `run_bootstrap`, plan, preview, apply, or validate. It must
not touch filesystem state, import plugins, emit stdout/stderr, derive process exit codes,
perform network access, repair state, retry, or roll back.

Serialization never accepts arbitrary Python object hooks or executable type metadata.

## Deferred boundaries

Binary formats, CBOR/MessagePack, streaming documents, schema migration, digital signing,
encryption, compression, remote execution, asynchronous transport, plugin-defined payload extensions, and automatic repair/retry/rollback remain deferred.
