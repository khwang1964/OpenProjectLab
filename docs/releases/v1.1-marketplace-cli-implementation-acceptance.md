## 2. Accepted Implementation Scope

The candidate contains exactly this production command family:

``` text
opl marketplace versions IDENTITY --catalog FILE [--json]
opl marketplace inspect COORDINATE --catalog FILE [--json]
opl marketplace verify COORDINATE --catalog FILE --payload-root DIR [--json]
opl marketplace install COORDINATE --catalog FILE --payload-root DIR [--dry-run] [--json]
```

Acceptance covers:

- exact `namespace/name` identities and
  `namespace/name@MAJOR.MINOR.PATCH` coordinates;
- one explicit UTF-8 local catalog using schema version 1;
- deterministic exact lookup and version ordering;
- payload-root containment, regular-file acquisition, and SHA-256 integrity;
- verification before installation and no partial installer state;
- process-local, non-persistent, non-activating installation;
- deterministic human and schema-version-1 JSON rendering;
- stdout for success, stderr for diagnostics, and the accepted `0`/`2` exit
  boundary;
- functionally equivalent English and Traditional Chinese (Taiwan) manuals;
- the preserved v1 Stable CLI surface plus the reviewed additive
  `marketplace` family.

There is no `opl marketplace list` command.

## 3. Preserved and Deferred Boundaries

Formal acceptance does not add or claim:

- remote catalog or payload access and implicit network fallback;
- signing, trust roots, provenance, or publisher verification;
- dependency resolution or automatic dependency installation;
- ratings, reviews, payments, or monetization;
- persistent installation, activation, or runtime plugin loading;
- automatic project mutation;
- AI CLI commands or AI-mediated Marketplace behavior.

The canonical executable use-case demo remains a later additive extension and
is not required to prove this accepted deterministic-local command contract.

## 6. Acceptance Blockers

Acceptance is blocked by any of the following:

- a command inventory other than `versions`, `inspect`, `verify`, and
  `install`;
- regression of any v1 Stable command;
- unsafe catalog or payload path handling;
- integrity verification after installation begins;
- partial installer state after a handled failure;
- nondeterministic JSON or mixed success/diagnostic streams;
- claims that process-local installation activates or persists artifacts;
- undocumented divergence between EN and zh-TW manuals;
- failed regression, coverage, quality, packaging, or required CI gates;
- an unmerged acceptance PR, unsynchronized `main`, or missing post-merge
  verification;
- fabricated test, coverage, PR, CI, commit, artifact, tag, or release
  evidence.
