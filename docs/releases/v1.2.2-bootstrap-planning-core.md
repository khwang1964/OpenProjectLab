## 1. Purpose

This document defines the Design First contract for the first concrete
Bootstrap Framework implementation slice: the planning core.

The goal is to establish a deterministic, inspectable, mutation-free planning
pipeline before any dry-run or apply execution behavior is implemented.

The lifecycle is:

``` text
v1.2.1 Bootstrap Framework Design Baseline --- Accepted
        ↓
v1.2.2 Bootstrap Planning Core --- In Progress
        ↓
planning-core contract accepted
        ↓
planning-core implementation may begin
```

No production planning-core implementation is authorized by this document.

## 2. Scope

v1.2.2 is limited to the minimum planning-domain and orchestration contracts
required to construct a `BootstrapPlan`.

In scope:

- `BootstrapPlan`
- `BootstrapStep`
- `BootstrapPlanner`
- deterministic step ordering
- deterministic equivalent-plan behavior
- explicit expected-effect representation
- GeneratorRegistry reuse
- existing generator lifecycle preservation
- mutation-free planning

Out of scope:

- dry-run execution
- apply execution
- validation runtime
- checkpoint / resume
- generalized rollback
- Stable Bootstrap CLI syntax
- plugin activation
- implicit network access
- committed filesystem mutation

## 3. Core Contracts

### 3.1 BootstrapStep

`BootstrapStep` represents one logical planning step.

A step should expose:

- stable step identity;
- referenced generator identity or accepted service identity;
- normalized planning inputs;
- deterministic ordering position or equivalent ordering key;
- expected outputs or expected filesystem effects;
- whether the later apply phase may mutate state.

At v1.2.2, a `BootstrapStep` is descriptive only.

It must not:

- execute a generator;
- mutate the filesystem;
- activate a plugin;
- perform network I/O.

### 3.2 BootstrapPlan

`BootstrapPlan` is the deterministic, inspectable result of planning.

A plan should contain:

- normalized bootstrap intent;
- ordered `BootstrapStep` entries;
- deterministic expected effects;
- traceability or reproducibility metadata sufficient for tests;
- a stable equivalence basis for equivalent supported inputs.

A plan must be safe to construct repeatedly without side effects.

### 3.3 BootstrapPlanner

`BootstrapPlanner` is the planning service boundary.

Its responsibility is:

``` text
bootstrap intent
      ↓
normalize inputs
      ↓
resolve accepted generator identities
      ↓
construct ordered BootstrapStep values
      ↓
compute deterministic expected effects
      ↓
return BootstrapPlan
```

The planner must not cross into execution.

## 4. Deterministic Planning Semantics

Equivalent supported inputs and equivalent relevant repository state should
produce equivalent `BootstrapPlan` values.

Determinism includes:

- stable step ordering;
- stable normalized input representation;
- stable expected-effect ordering;
- stable generator identity resolution;
- stable plan equivalence semantics.

The design does not require a cryptographic plan hash in v1.2.2.

If a plan identity token is introduced later, its canonicalization rules must be
designed separately.

## 5. GeneratorRegistry Reuse

The planning core should reuse the existing GeneratorRegistry or accepted
generator-resolution boundary.

The planner may:

- validate that referenced generators exist;
- resolve generator identities;
- derive planning metadata from accepted generator contracts.

The planner must not:

- create an alternative generator registry;
- instantiate and execute generators as part of planning;
- implicitly activate plugins;
- mutate global generator configuration.

## 6. Generator Lifecycle Preservation

The existing generator lifecycle remains authoritative.

v1.2.2 planning must not call the mutation/execution portion of a generator
lifecycle.

Planning may depend on metadata or contract information needed to describe a
future step, but it must not convert planning into hidden execution.

## 7. Filesystem Boundary

Planning is mutation-free.

The planning core must not:

- create files or directories;
- modify files;
- delete files;
- create backups;
- write manifests;
- write checkpoints;
- invoke a filesystem commit operation.

Planning may compute expected filesystem effects as data only.

``` text
Filesystem Mutation --- Forbidden
```

## 8. Network and Plugin Boundary

The planning core must not introduce hidden external behavior.

``` text
Network Access --- Forbidden
Plugin Activation --- Forbidden
```

If future planning requires remote discovery or plugin-aware behavior, that
must be introduced through a separate accepted design contract.

## 9. Equivalent-Plan Behavior

Equivalent supported planning inputs should produce equivalent plans.

The exact Python equality or serialization representation is not fixed by this
design baseline.

However, executable tests must be able to prove:

- equivalent input produces equivalent ordered steps;
- equivalent input produces equivalent expected effects;
- repeated planning does not produce nondeterministic ordering.

## 10. Expected Effects

Expected effects are descriptive planning data.

They may represent later apply-phase intentions such as:

- create file;
- update file;
- create directory;
- generate artifact.

At v1.2.2 they are not execution commands.

The planning core must keep expected-effect representation separate from
filesystem mutation.

## 11. Explicit Non-goals

v1.2.2 does not approve:

``` text
dry-run execution --- Not Started
apply execution --- Not Started
validation runtime --- Not Started
checkpoint / resume --- Deferred
generalized rollback --- Deferred
CLI Boundary --- Not Accepted
Plugin Activation --- Forbidden
Network Access --- Forbidden
Filesystem Mutation --- Forbidden
```

It also does not approve:

- a second generator lifecycle;
- a second filesystem mutation pipeline;
- a new Stable public CLI surface;
- remote Bootstrap planning;
- automatic plugin discovery/activation;
- generalized dependency resolution.

## 12. Implementation Sequence

After this design is accepted, implementation should proceed in small slices:

``` text
1. minimum BootstrapStep model
2. minimum BootstrapPlan model
3. BootstrapPlanner input normalization
4. GeneratorRegistry-backed resolution
5. deterministic step construction
6. deterministic expected-effect construction
7. equivalence / reproducibility tests
8. integration with existing Bootstrap entry points only after contract review
```

No dry-run or apply implementation belongs in this sequence.

## 13. Test Strategy

Executable contract coverage must prove:

- design remains fail closed before acceptance;
- `BootstrapStep`, `BootstrapPlan`, and `BootstrapPlanner` are explicitly defined;
- planning is mutation-free;
- planning does not execute generators;
- planning does not use network access;
- planning does not activate plugins;
- existing GeneratorRegistry is reused;
- existing generator lifecycle remains authoritative;
- deterministic ordering is required;
- equivalent-plan behavior is required;
- dry-run and apply remain Not Started;
- checkpoint/resume remains Deferred;
- CLI Boundary remains Not Accepted;
- v1.2 implementation remains Not Started until design acceptance.
