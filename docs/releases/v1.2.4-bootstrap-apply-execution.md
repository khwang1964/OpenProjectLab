# OpenProjectLab v1.2.4 Bootstrap Apply Execution

> **Status:** Accepted --- Terminally Closed
> **Predecessor:** v1.2.3 Dry-run Execution Preview --- Accepted / Implemented
> **Target Slice:** v1.2.4 --- Bootstrap Apply Execution
> **Production Implementation:** Not Started

## 1. Purpose

This document defines the Design First contract for the explicit committed
mutation phase of the Bootstrap Framework.

``` text
BootstrapPlan
    ↓
BootstrapApplyExecutor.apply(plan)
    ↓
ordered existing Generator lifecycle execution
    ↓
existing filesystem abstraction
    ↓
BootstrapApplyResult
```

No production apply runtime is authorized by this document.

## 2. Scope

In scope:

- `BootstrapApplyStepResult`;
- `BootstrapApplyResult`;
- `BootstrapApplyExecutor`;
- an internal Bootstrap-step-to-existing-Generator execution adapter;
- authoritative `BootstrapPlan` reuse;
- deterministic sequential execution;
- existing `BaseGenerator.run(GenerateRequest)` lifecycle reuse;
- existing filesystem abstraction reuse;
- observable fail-fast partial-state evidence.

Out of scope:

- direct execution of `ExpectedEffect` values;
- a second generator lifecycle or mutation pipeline;
- generalized rollback or transaction-wide atomicity;
- checkpoint / resume;
- parallel execution;
- validation runtime;
- network access or implicit plugin activation;
- Stable Bootstrap CLI syntax;
- public SDK expansion.

## 3. Core Contracts

### 3.1 BootstrapApplyStepResult

`BootstrapApplyStepResult` is immutable evidence for one successfully
completed Bootstrap step. It records stable step and generator identity plus
the existing `GenerationResult` returned by the authoritative Generator
lifecycle.

It is evidence, not an alternative write-result or manifest model.

### 3.2 BootstrapApplyResult

`BootstrapApplyResult` is immutable ordered evidence for a successful apply.
It contains completed step results in authoritative plan order.

A success result is returned only after every step completes. It must not hide
or relabel a failure as success.

### 3.3 BootstrapApplyExecutor

`BootstrapApplyExecutor.apply(plan)` consumes an existing immutable
`BootstrapPlan`, executes steps sequentially, and returns
`BootstrapApplyResult`.

The executor coordinates existing boundaries. It must not contain generator
business logic, render templates, or write files directly.

### 3.4 Bootstrap Step Execution Adapter

An internal injected adapter maps each `BootstrapStep` and authoritative plan
context into the existing Generator execution boundary.

The adapter must ultimately delegate through:

``` text
GeneratorRegistry resolution
    ↓
existing generator instance
    ↓
BaseGenerator.run(GenerateRequest)
    ↓
validate_request → plan → execute
```

The adapter is not a new public SDK contract and must not activate plugins
implicitly.

## 4. Authoritative Plan Boundary

The accepted `BootstrapPlan` remains authoritative. Apply must:

- preserve step order;
- use stable step and generator identities;
- avoid hidden re-planning;
- reject unsupported or inconsistent plan data before reporting success;
- leave the input plan unchanged.

``` text
Input BootstrapPlan --- Immutable / Authoritative
```

## 5. Expected-effect Boundary

`ExpectedEffect` remains descriptive preview/planning data.

Apply must not translate expected-effect kinds into direct filesystem
commands. Committed mutation occurs only through existing Generator execution
and the existing filesystem abstraction.

``` text
ExpectedEffect Direct Execution --- Forbidden
```

## 6. Execution Semantics

Apply is explicit, ordered, and sequential.

- each step starts only after the previous step succeeds;
- each generator executes at most once for one apply invocation;
- completed result ordering matches `BootstrapPlan.steps` ordering;
- empty plans succeed with an empty immutable result;
- no implicit dry-run-to-apply fallback exists;
- no parallel execution is introduced.

## 7. Filesystem and Generator Boundaries

``` text
Generator Lifecycle --- Reused
Filesystem Abstraction --- Reused
Parallel Mutation Pipeline --- Forbidden
Direct Filesystem Writes by BootstrapApplyExecutor --- Forbidden
```

Existing generator write policies, atomic single-file writes, manifests, and
generator-specific behavior remain authoritative. v1.2.4 does not promise
transaction-wide atomicity.

## 8. Failure and Partial-state Semantics

Apply stops at the first non-recoverable step failure.

The failure boundary must expose:

- completed step results in order;
- failed step identity;
- the originating failure as explicit cause/evidence;
- the fact that later steps were not executed.

Successful earlier mutations remain observable and are not automatically
rolled back.

``` text
Fail-fast --- Required
Later-step Execution after Failure --- Forbidden
Automatic Rollback --- Not Guaranteed
Transaction-wide Atomicity --- Not Claimed
```

A dedicated internal `BootstrapApplyError` may carry partial execution
evidence. Its public stability is not accepted by this design slice.

## 9. Network, Plugin, and Compatibility Boundaries

``` text
Implicit Network Access --- Forbidden
Implicit Plugin Activation --- Forbidden
Stable v1.x Generator Contracts --- Preserved
Public SDK Expansion --- Forbidden
```

Only already composed and accepted generator/registry boundaries may be used.

## 11. Test Strategy

Executable design contracts must prove:

- the accepted/implemented v1.2.3 slice is the predecessor;
- apply contracts are explicit and implementation remains absent;
- `BootstrapPlan` is immutable and authoritative;
- plan order is preserved and execution is sequential;
- existing Generator lifecycle and filesystem abstraction are reused;
- expected effects are never executed directly;
- fail-fast partial-state semantics are explicit;
- later steps do not run after failure;
- rollback and transaction-wide atomicity are not claimed;
- network, plugin, CLI, validation, and SDK surfaces remain closed.
