# OpenProjectLab v1.0 Packaging / Installation / Distribution

> **Status:** Accepted
> **Milestone:** 8 — v1.0 Stabilization & Release Readiness
> **Step:** 8.4 — Packaging / Installation / Distribution
> **Target Release:** OpenProjectLab v1.0.0
> **Depends On:** Step 8.3 — Reliability / Regression Hardening

---

## 1. Purpose

Step 8.4 proves that OpenProjectLab works as an installed Python distribution,
not merely from a repository checkout or editable development environment.

The release boundary is:

```text
source tree
    ↓
build wheel + sdist
    ↓
inspect distribution metadata and contents
    ↓
install wheel into an isolated environment
    ↓
run installed CLI
    ↓
resolve installed runtime resources
    ↓
generate a representative artifact
```

A v1.0 release is not packaging-ready until this workflow is reproducible
without depending on repository-only paths.

---

## 2. Current Packaging Audit

The current project metadata declares:

```text
distribution: openprojectlab
current development version: 0.6.0
Python: >=3.12
console script: opl = generator.cli.main:main
runtime dependencies:
    Jinja2>=3.1
    PyYAML>=6.0
```

Setuptools package discovery currently includes only:

```text
generator
generator.*
```

and explicitly excludes repository-level `templates` / `templates.*`.

At the same time, the current CLI derives default configuration, template, and
output roots from the source-layout project root. Built-in Generators also
require a template root at runtime.

Therefore Step 8.4 treats packaged runtime resources as an explicit
release-readiness risk. The tests introduced with this document are expected to
expose that risk before production packaging code is changed.

---

## 3. Design Principles

### 3.1 Installed-user truth

Packaging acceptance is based on the installed artifact, not on what happens to
work from the source checkout.

Tests must distinguish:

```text
source-tree success
≠
wheel success
≠
clean-install success
```

### 3.2 Package-owned runtime resources

Runtime templates and other required immutable assets must be owned by the
installed Python distribution.

The preferred architecture is conceptually:

```text
generator/
    resources/
        templates/
            bootstrap/
            course/
            week/
            lab/
            assignment/
            quiz/
            slides/
            website/
```

with runtime lookup through package-resource semantics such as
`importlib.resources`, rather than assuming a repository-level `templates/`
directory exists next to the installed package.

This document does not freeze that exact internal directory layout. It freezes
the observable requirement: a clean wheel installation must be able to resolve
all required built-in runtime templates without access to the repository.

### 3.3 No editable-install dependency

Acceptance must not rely on:

```text
pip install -e .
PYTHONPATH=<repository>
current working directory == repository root
repository-level templates/
repository-level config/
repository-level courses/
```

### 3.4 Distribution metadata is part of release behavior

The built artifact must preserve:

- distribution name;
- distribution version;
- supported Python requirement;
- runtime dependencies;
- console entry point;
- license / README metadata required by the build configuration.

### 3.5 Build and install verification must be automated

The final Step 8.4 workflow must be suitable for CI and repeatable from a clean
checkout.

## 4. v1.0 Packaging Contract

### 4.1 Build contract

The repository must support:

```text
python -m build
```

and produce both:

```text
wheel
sdist
```

without modifying tracked source files.

### 4.2 Wheel metadata contract

The wheel must expose the declared distribution metadata and include the
`generator` package.

The wheel must not accidentally package repository-only development trees such
as:

```text
tests/
docs/
examples/
courses/
website/
scripts/
```

unless a later explicit release decision changes that boundary.

### 4.3 Console-script contract

The installed distribution must expose:

```text
opl
```

mapped to:

```text
generator.cli.main:main
```

The command must be executable from an isolated environment.

### 4.4 Runtime-resource contract

Every built-in Generator that requires a shipped template must be able to
resolve that template from the installed distribution.

At minimum, the installed resource contract must cover the built-in template
families used by the v1.0 CLI:

```text
bootstrap
course
week
lab
assignment
quiz
slides
website
```

The contract is about availability and runtime resolution, not about freezing a
private package-resource directory name.

### 4.5 Clean-install contract

A wheel must be installable into a newly created virtual environment.

After installation, without repository import paths, the following must work:

```text
import generator
opl list
representative built-in generation
```

The representative generation must produce a real user-visible artifact.

### 4.6 Dependency contract

Runtime dependencies needed by installed workflows must be declared in package
metadata. Test, documentation, build, and release tooling must remain optional
development dependencies.

### 4.7 Version contract

Step 8.4 records the current metadata version but does not prematurely change it
to `1.0.0`.

The final v1.0 version transition belongs to release closeout after packaging,
installation, documentation, and final acceptance are complete.

## 5. Contract Test Strategy

Step 8.4 starts with three test layers.

### 5.1 Build artifact contract

```text
tests/packaging/test_v1_build_artifact_contract.py
```

Responsibilities:

- inspect `pyproject.toml`;
- freeze distribution identity and entry point;
- verify runtime dependencies are declared;
- verify package discovery owns the `generator` namespace;
- record that repository-level templates are not currently package-owned;
- inspect a built wheel when one is supplied to the test.

### 5.2 Installed resource contract

```text
tests/packaging/test_v1_installed_resources_contract.py
```

Responsibilities:

- define required built-in template families;
- verify package-owned resource discovery exists;
- verify required templates can be resolved without repository fallback;
- prevent future reintroduction of repository-root coupling.

This slice is expected to fail until the package-resource architecture is
implemented.

### 5.3 Clean-install smoke contract

```text
tests/packaging/test_v1_clean_install_smoke.py
```

Responsibilities:

- consume an explicitly supplied wheel;
- create a temporary isolated virtual environment;
- install the wheel;
- import the installed package from outside the repository;
- execute `opl list`;
- execute representative generation;
- verify the generated artifact exists.

The test intentionally does not build the wheel itself. Build and clean-install
are separate observable stages so failures remain diagnosable.

## 6. Test Execution Modes

Fast repository tests may run without a prebuilt artifact.

Artifact-dependent tests use:

```text
OPL_TEST_WHEEL=<absolute path to .whl>
```

When the variable is absent, artifact-only tests may skip rather than silently
building or installing from the source tree.

Recommended local sequence:

```text
python -m build
twine check dist/*
$env:OPL_TEST_WHEEL = (Resolve-Path dist\openprojectlab-*.whl).Path
python -m pytest tests\packaging -v --no-cov
```

A CI packaging job must supply the built wheel and must not accept skipped
artifact tests as final Step 8.4 evidence.

---

## 7. Expected Initial Failure

The first Step 8.4 contract run may expose an installed-resource failure.

That failure is useful evidence if it demonstrates:

```text
repository checkout
    has templates/

wheel installation
    lacks package-owned templates
```

The correct response is not to weaken the test or point the installed CLI back
at the source repository.

The production fix must establish an installed-resource architecture.

---

## 8. Production Fix Boundary

A Step 8.4 production fix may change:

- package-owned resource layout;
- template-root resolution;
- setuptools package-data configuration;
- CLI default resource resolution;
- build / packaging CI.

It must not unnecessarily change:

- frozen v1.0 CLI command names;
- Generator public contracts;
- Plugin SDK public contracts;
- Marketplace public contracts;
- AI public contracts;
- Courseware domain contracts.

---

## 9. Acceptance Gates

Step 8.4 is not Accepted until all of the following are green:

```text
python -m build
twine check dist/*
wheel metadata/content inspection
clean wheel installation
installed import
installed opl list
installed representative generation
packaging contract tests
full pytest regression
coverage >= 67.0%
git diff --check
ruff check .
ruff format --check .
pre-commit run --all-files
GitHub Actions / CI
```

Final evidence must record the actual wheel filename, version, packaging test
count, full regression count, coverage, and CI result.

---

## 10. Automation / CI Requirements

Before Step 8.4 closes, CI should automate the release-artifact path:

```text
checkout
→ build wheel + sdist
→ twine check
→ install wheel in isolated environment
→ run installed-user smoke tests
→ retain normal quality / regression gates
```

The packaging job must test the artifact it built, not an editable installation.

> OpenProjectLab v1.0 is packaging-ready only when the artifact users install
