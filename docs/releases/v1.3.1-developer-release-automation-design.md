# v1.3.1 Developer / Release Automation — Design Baseline

> Status: Accepted — Terminally Closed

## Predecessor

v1.3.0 Bootstrap SDK Serialization — Accepted / Completed.

## Objective

Define a deterministic, fail-closed maintainer automation boundary that collects
release evidence and detects lifecycle-document drift before acceptance records
are committed. This is a Design First slice; production implementation remains
Not Started.

## Proposed public boundary

No new end-user CLI or `generator.sdk` surface is proposed. The first
implementation is maintainer-facing repository automation.

## Evidence model

An evidence snapshot must identify:

- repository and branch;
- candidate commit SHA;
- pull request number and state when available;
- required CI check names and conclusions;
- focused and full-regression passed, failed, skipped, and deselected counts;
- coverage percentage and configured threshold;
- post-merge synchronized-main verification when it has actually occurred.

Missing, ambiguous, stale, or contradictory evidence fails closed. Evidence
must never be synthesized from a planned future state.

## Lifecycle consistency contract

The automation compares the governing acceptance record with
`docs/roadmap.md`, `docs/HISTORY.md`, and `CHANGELOG.md`. A lifecycle status may
advance only when all required evidence exists and every document expresses the
same non-final or final state.

## Two-PR acceptance boundary

PR 1 may create a Pending acceptance record and must leave synchronized-main
and post-merge gates Pending. Only after PR 1 is merged and verified may a
separate PR 2 record Accepted / Completed closure evidence.

## Determinism and safety

- stable field and check ordering;
- read-only collection before an explicitly requested write;
- exact repository, branch, commit, and PR identity checks;
- no force push, merge, tag, release, publication, or branch deletion;
- no credential capture or serialization;
- no weakening or bypassing failed gates.

## Deferred

- automatic pull-request merge;
- tag, GitHub Release, or package publication;
- generalized workflow orchestration outside OPL;
- checkpoint/resume for Bootstrap execution;
- serialization schema migration;
- end-user CLI or public SDK expansion.

## Test strategy

- executable documentation contract for scope and safety markers;
- fail-closed fixtures for missing and contradictory evidence;
- deterministic ordering tests;
- two-PR state-transition tests;
- no-network unit tests with injected repository and CI evidence;
- representative integration against temporary repository fixtures.

## Documentation plan

- architecture boundary;
- maintainer workflow reference in the implementation slice;
- roadmap, HISTORY, and CHANGELOG lifecycle alignment;
- acceptance record maintained separately from this design baseline.

## Code Review Checklist

- [ ] Design remains maintainer-facing with no accidental public SDK expansion.
- [ ] Evidence is current, exact, reproducible, and never inferred as passed.
- [ ] Pending and Accepted / Completed states cannot be conflated.
- [ ] Two-PR acceptance and explicit merge authorization remain enforced.
- [ ] Operations are deterministic and fail closed.
- [ ] Destructive Git, release, and publication actions remain out of scope.
- [ ] Architecture, tests, documentation, and implementation boundaries align.
