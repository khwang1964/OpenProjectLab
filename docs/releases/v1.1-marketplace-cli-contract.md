## 1. Purpose

This document defines the proposed Marketplace command-line contract for
OpenProjectLab v1.1. It maps the accepted deterministic Marketplace domain
boundaries into an additive local CLI without changing the reviewed v1 command
surface or creating a remote Marketplace, package manager, activation system,
or second execution framework.

This slice is contract design and fail-closed automation only. The production
parser must not register `marketplace` until v1.1.4 implementation work begins
under an accepted version of this contract.

## 2. Governing Sources

The contract is grounded in:

- `docs/releases/v1.1-planning-baseline.md`;
- `docs/releases/v1.1-cli-public-contract.md`;
- `docs/releases/v1.1-cli-public-contract-acceptance.md`;
- the frozen v1 Marketplace public-contract tests;
- `ArtifactIdentity`, `ArtifactVersion`, and `ArtifactCoordinate`;
- `MarketplaceArtifact` metadata and compatibility contracts;
- `MarketplaceRepository.find()` and `available_versions()`;
- `ArtifactAcquirer.acquire()`;
- `verify_integrity()` and SHA-256 integrity metadata;
- `ArtifactInstaller.install()` and `ArtifactInstallationResult`;
- the representative local Repository → Acquisition → Integrity →
  Installation E2E.

Historical proposals cannot override these production boundaries.

## 3. Preserved v1 and v1.1.2 Boundaries

All reviewed v1 commands remain valid. The installed `opl` entry point,
legacy `opl --list`, existing generation arguments/options, broad `0`/`2`
exit behavior, and stdout/stderr rules remain preserved.

The Marketplace command family is additive:

``` text
opl marketplace ...
```

It must not reinterpret the existing Generator `list` command or add
`marketplace` to built-in Generator output.

## 4. Production Capability Audit

The current production Marketplace provides:

- immutable `namespace/name@MAJOR.MINOR.PATCH` coordinates;
- exact-coordinate repository lookup;
- deterministic ascending version lookup for one identity;
- acquisition returning exact bytes without verification or installation;
- SHA-256 integrity verification;
- deterministic installation result and process-local installed state;
- failure-before-installation when lookup, acquisition, or integrity fails;
- no filesystem persistence in the representative E2E.

The current repository does not expose global artifact enumeration. Therefore
this contract does not invent `opl marketplace list` or a list-all repository
API. The reviewed version-enumeration command is `versions <identity>`.

## 5. Proposed Command Inventory

The exact v1.1.3 Marketplace command shapes are:

``` text
opl marketplace versions IDENTITY --catalog FILE [--json]
opl marketplace inspect COORDINATE --catalog FILE [--json]
opl marketplace verify COORDINATE --catalog FILE --payload-root DIR [--json]
opl marketplace install COORDINATE --catalog FILE --payload-root DIR
    [--dry-run] [--json]
```

No aliases or short options are part of the contract.

### 5.1 Identity

`IDENTITY` uses exactly:

``` text
namespace/name
```

Both components follow `ArtifactIdentity` validation and must not contain path
semantics.

### 5.2 Coordinate

`COORDINATE` uses exactly:

``` text
namespace/name@MAJOR.MINOR.PATCH
```

The version follows canonical `ArtifactVersion` syntax. Missing, partial,
pre-release, build-metadata, or non-canonical versions are rejected.

## 6. Local Catalog Contract

`--catalog FILE` is required for every Marketplace subcommand. It names a
UTF-8 JSON document with this minimum schema:

``` json
{
  "schema_version": 1,
  "artifacts": [
    {
      "schema_version": 1,
      "namespace": "community",
      "name": "modern-java-templates",
      "version": "1.0.0",
      "artifact_type": "template",
      "description": "Modern Java templates",
      "compatibility": ">=1.0,<2.0",
      "distribution": {
        "kind": "file",
        "reference": "community/modern-java-templates-1.0.0.pkg"
      },
      "integrity": {
        "algorithm": "sha256",
        "digest": "<64 hexadecimal digits>"
      }
    }
  ]
}
```

Rules:

- catalog `schema_version` must be integer `1`;
- `artifacts` must be an array;
- each entry must construct the existing Marketplace domain models;
- duplicate exact coordinates are rejected;
- catalog order does not determine output order;
- unknown required semantics are rejected rather than silently ignored;
- malformed JSON, wrong types, and invalid domain values fail before
  acquisition or installation.

The catalog is a CLI adapter input. It does not add its loader or raw JSON
objects to `generator.sdk` or to the Marketplace domain public exports.

## 7. Payload Resolution and Safety

`verify` and `install` require `--payload-root DIR`. For the v1.1 CLI adapter,
the selected artifact must have `distribution.kind == "file"`.

`distribution.reference` is resolved beneath `payload-root` and must be a safe
relative path. Absolute paths, drive-prefixed paths, traversal (`..`), empty
segments with path semantics, and any resolved path escaping the payload root
are rejected before bytes are read.

The adapter reads payload bytes locally and supplies them to the existing
acquisition/integrity/installation composition. No network fallback exists.

## 8. Subcommand Semantics

### 8.1 `versions`

`versions IDENTITY` constructs `ArtifactIdentity` and calls the repository
version lookup. Output is deterministic ascending semantic-version order.
An unknown identity produces a successful empty result, matching
`available_versions()`.

This command does not acquire payloads or mutate installation state.

### 8.2 `inspect`

`inspect COORDINATE` performs exact repository lookup and reports reviewed
artifact metadata. It does not acquire, verify, install, activate, or execute
the artifact.

### 8.3 `verify`

`verify COORDINATE` performs, in order:

``` text
exact repository lookup
    ↓
local payload acquisition
    ↓
SHA-256 integrity verification
```

It does not call the installer. A missing artifact, missing payload, unsafe
payload reference, unsupported distribution kind, or integrity mismatch fails
without installation state.

### 8.4 `install`

`install COORDINATE` performs:

``` text
exact repository lookup
    ↓
local payload acquisition
    ↓
SHA-256 integrity verification
    ↓
deterministic installation result
```

Installation in v1.1.3 means the existing `ArtifactInstaller` contract:
validated bytes recorded by the selected installer without activation. It
does not promise persistence across CLI processes, filesystem package
installation, entry-point discovery, Plugin/Generator registration, or
execution.

`--dry-run` completes lookup, acquisition, and integrity verification but does
not call `install()`. It reports the planned coordinate and payload size.

## 9. Output Contract

Human-readable success output is written to stdout. Diagnostics are written to
stderr. Exact human wording, spacing, and localization are not byte-for-byte
Stable.

`--json` is an explicit opt-in machine-readable contract. It writes exactly
one UTF-8 JSON object to stdout and no human preamble. Diagnostics remain on
stderr.

Common JSON fields:

``` text
schema_version --- integer 1
command        --- "versions" | "inspect" | "verify" | "install"
```

Command results:

``` json
{"schema_version":1,"command":"versions","identity":"community/name","versions":["1.0.0"]}
{"schema_version":1,"command":"inspect","coordinate":"community/name@1.0.0","artifact":{}}
{"schema_version":1,"command":"verify","coordinate":"community/name@1.0.0","verified":true,"algorithm":"sha256","digest":"...","payload_size":123}
{"schema_version":1,"command":"install","coordinate":"community/name@1.0.0","status":"installed","payload_size":123,"dry_run":false}
```

The `inspect.artifact` object uses the catalog artifact fields defined in
Section 6 in canonical form. Collections use deterministic order. Additive
fields may be introduced compatibly, but required fields cannot be removed or
semantically redefined within v1.x.

## 10. Exit and Error Contract

This slice preserves the accepted broad CLI behavior:

| Exit | Meaning |
| ---: | --- |
| `0` | Successful command, including an empty `versions` result |
| `2` | Usage, parsing, catalog, lookup, acquisition, integrity, installation, filesystem, or other handled operational failure |

No finer Stable exit taxonomy is introduced. Failed JSON-mode operations do
not emit a success JSON document to stdout. Exact diagnostic text is not
Stable.

## 11. Failure-before-side-effect Rules

Before `install()` is called, the adapter must complete:

- CLI and coordinate parsing;
- catalog loading and domain validation;
- duplicate-coordinate rejection;
- exact artifact lookup;
- payload-root containment validation;
- payload acquisition;
- SHA-256 verification.

Failure in any earlier step leaves installer state unchanged. Duplicate
installation must not replace existing payload bytes. `verify`, `inspect`,
`versions`, and `install --dry-run` never call the installer.

## 12. Explicit Non-goals

The following remain Deferred:

- remote Marketplace or Community Repository hosting;
- HTTP/network acquisition or implicit network fallback;
- generalized package-manager integration;
- persistent cross-process installation registry;
- automatic Plugin or Generator activation;
- entry-point discovery or Generator execution;
- dependency resolution, lock files, or cache policy;
- signing, publisher identity, sandboxing, or trust enforcement;
- ratings, reviews, payment, monetization, or AI Provider Marketplace.

`verify` proves content integrity against declared SHA-256 metadata; it does not
prove authenticity, publisher trust, or safety.

## 13. Implementation Boundary

v1.1.4 may add:

- a parser branch for the exact command inventory above;
- internal identity/coordinate parsing helpers;
- an internal local-catalog adapter;
- an internal safe local-payload acquirer;
- orchestration reusing the existing repository, integrity, and installer
  boundaries;
- human and JSON renderers;
- focused parser, integration, failure-path, and no-partial-state tests.

It must not change the v1 Marketplace domain contracts merely to simplify CLI
implementation, expand `generator.sdk`, or introduce a second Marketplace
execution model.
