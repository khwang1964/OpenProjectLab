## Purpose

Define the Design First contract for Bootstrap Framework maturity without
introducing a second generator lifecycle or filesystem mutation pipeline.

## Core Contracts

### BootstrapPlan
Deterministic, inspectable planning result. It identifies ordered steps,
expected filesystem operations, validations, and reproducibility metadata.

### BootstrapStep
One logical orchestration step. It reuses an existing generator or Stable
service boundary and must not bypass the existing generator lifecycle.

### BootstrapResult
Observable execution result including completed/skipped steps, failures,
filesystem effect summary, validation result, and traceability information.

## Execution Semantics

### plan
Pure planning operation:
- no filesystem mutation
- no generator execution
- no implicit network access
- deterministic for equivalent inputs and state
- returns BootstrapPlan

### dry-run
Execution preview:
- no committed filesystem mutation
- reports expected filesystem effects
- must not silently fall back to apply

### apply
Explicit mutation phase:
- consumes a BootstrapPlan
- executes steps in defined order
- uses existing generator/filesystem abstractions
- records observable results
- stops according to documented failure semantics

## Filesystem Boundary

The framework must reuse the existing filesystem abstraction and must not:
- introduce a second transactional mutation engine
- bypass generator mutation contracts
- mutate during planning
- hide writes behind validation

## Generator Composition Boundary

Bootstrap orchestration composes existing generators. It may sequence them,
pass explicit inputs, collect outcomes, and expose diagnostics. It must not
duplicate generator business logic, replace lifecycle hooks, create an
alternative generator registry, or implicitly activate plugins.

## Failure Semantics

- planning failures produce no mutation
- dry-run failures produce no committed mutation
- apply stops at the first non-recoverable step failure
- previous successful mutations are not automatically rolled back
- generalized rollback is explicitly out of scope

## Validation Semantics

Validation occurs after apply or independently. It must inspect state, avoid
hidden repair/mutation, and produce explicit evidence.

Validation failure does not imply automatic rollback.

## Checkpoint / Resume Boundary

Checkpoint/resume is not part of the initial v1.2.1 implementation contract.

``` text
Checkpoint / Resume --- Deferred
```

## CLI Boundary

No new CLI command is accepted by this design baseline yet. Any examples such
as `opl bootstrap plan`, `opl bootstrap --dry-run`, or `opl bootstrap apply`
are illustrative only.

``` text
CLI Boundary --- Not Accepted
```

## Compatibility

v1.2.1 must remain backward compatible with Stable v1.x behavior and preserve
existing generator contracts, bootstrap entry points, deterministic local
behavior, filesystem abstraction, and plugin activation boundaries.

## Explicit Non-goals

- second filesystem mutation pipeline
- second generator lifecycle
- generalized transaction rollback
- checkpoint/resume implementation
- remote bootstrap orchestration
- silent network access
- automatic plugin activation
- AI-driven arbitrary repository mutation
- generalized dependency resolution
- new Stable CLI syntax
- implementation before design acceptance

## Test Strategy

Executable contract coverage must verify mutation-free plan/dry-run,
deterministic ordering and plan identity, existing lifecycle reuse,
fail-closed failure handling, inspection-only validation, deferred resume,
and non-preaccepted CLI syntax.

## Code Review Checklist

- [ ] BootstrapPlan is deterministic and inspectable.
- [ ] BootstrapStep reuses existing generator lifecycle.
- [ ] BootstrapResult exposes execution evidence.
- [ ] plan and dry-run are mutation-free.
- [ ] apply uses the existing filesystem abstraction.
- [ ] no parallel mutation pipeline exists.
- [ ] failure semantics are explicit.
- [ ] generalized rollback is not implied.
- [ ] validation does not mutate state.
- [ ] checkpoint/resume remains Deferred.
- [ ] Stable v1.x behavior remains backward compatible.
- [ ] no Stable CLI syntax is preaccepted.
- [ ] implementation remains Not Started.
