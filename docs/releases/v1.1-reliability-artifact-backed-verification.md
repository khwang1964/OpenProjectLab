# OpenProjectLab v1.1 Reliability / Artifact-backed Verification

> **Status:** Design / Contract Definition --- In Progress
> **Target Release:** OpenProjectLab v1.1.0
> **Phase:** v1.1.8 --- Reliability / Artifact-backed Verification
> **Date:** 2026-08-25
> **Predecessor:** v1.1.7 Documentation / EN-zh-TW Parity --- Accepted
> **Formal v1.1 Acceptance:** Not Accepted

------------------------------------------------------------------------

## 1. Purpose

This slice verifies the v1.1 release candidate from built distribution
artifacts rather than only from a source checkout.

The release candidate must preserve one traceable identity:

``` text
Canonical Project Version
    ↓
Candidate Source Commit
    ↓
Built Wheel + sdist
    ↓
Artifact Metadata
    ↓
Checksum Manifest
    ↓
Clean Installation
    ↓
Installed `opl` Behavior
```

v1.1.8 reuses the accepted v1.0 release-artifact infrastructure. It does not
create a second packaging or release-identity framework.

## 2. Governing Principles

The artifact-backed gate is fail closed:

``` text
v1.1.7 Documentation / EN-zh-TW Parity --- Accepted
    ↓
fresh candidate source commit selected
    ↓
wheel + sdist built from candidate
    ↓
artifact identity and checksums verified
    ↓
wheel installed into clean environment
    ↓
installed-user CLI verification passes
    ↓
Marketplace installed-user verification passes
    ↓
AI Stable local-response installed-user verification passes
    ↓
First 15 Minutes / onboarding installed-user verification passes
    ↓
full regression + coverage + local quality gates pass
    ↓
PR / CI / merge / synchronized-main / post-merge consistency
    ↓
v1.1.8 Reliability / Artifact-backed Verification --- Accepted
Formal v1.1 Acceptance --- Not Accepted
```

No source-tree-only test substitutes for artifact-backed evidence.

## 3. Reused Artifact Infrastructure

Existing release-readiness infrastructure remains authoritative, including:

``` text
generator.release.artifacts
generator.release.identity
tests/release_readiness/test_v1_integrated_package_release_identity.py
```

The existing environment contract remains reusable:

``` text
OPL_TEST_DIST_DIR
OPL_TEST_WHEEL
OPL_TEST_CHECKSUM_MANIFEST
OPL_RELEASE_COMMIT_SHA
```

v1.1.8 extends verification to the v1.1 candidate. It must not weaken or
duplicate the existing v1 release-artifact model.

## 4. Artifact Identity Contract

The candidate must provide exactly one wheel and one sdist for the canonical
project identity.

Required consistency:

``` text
pyproject project.name
    == wheel METADATA Name
    == sdist PKG-INFO Name

pyproject project.version
    == wheel METADATA Version
    == sdist PKG-INFO Version
    == sdist pyproject project.version
```

The built wheel must preserve the console entry point:

``` text
opl = generator.cli.main:main
```

The checksum manifest must cover exactly the candidate artifact set and every
digest must verify.

## 5. Candidate Source Identity

`OPL_RELEASE_COMMIT_SHA` must identify the exact immutable source commit used to
build the candidate artifacts.

The commit must:

- be a full 40-character SHA;
- resolve to a repository commit;
- remain reachable from the current acceptance history;
- correspond to the candidate whose artifacts are under verification.

Later documentation or acceptance commits may advance `HEAD` without changing
the immutable artifact source identity.

## 6. Clean-install / Installed-user Contract

Artifact-backed verification must exercise a clean environment using the built
wheel, not imports from the source checkout.

At minimum, installed-user verification must cover:

``` text
opl --help
opl list
opl marketplace --help
opl ai --help
```

The installed package must expose the reviewed additive v1.1 families:

``` text
marketplace
ai
```

and preserve the Stable v1 command surface.

## 7. Marketplace Artifact-backed Contract

The installed-user Marketplace path must preserve the accepted deterministic
local-only behavior:

``` text
versions
inspect
verify
install
```

Required properties:

- explicit local catalog input;
- explicit payload root where required;
- deterministic machine-readable output where `--json` is supported;
- fail-closed path containment and integrity verification;
- no remote fallback;
- no automatic activation;
- no partial installer state on pre-install failure.

## 8. AI Artifact-backed Contract

Core artifact-backed acceptance must exercise the Stable AI path only:

``` text
opl ai course
opl ai review
opl ai document
opl ai template
```

The Stable path remains:

``` text
deterministic
local-response
credential-free
network-independent
non-mutating
```

The Experimental live-provider path is not required for core artifact-backed
acceptance and must not make wheel verification depend on credentials, paid
accounts, provider SDKs, or public network availability.

## 9. Documentation / Onboarding Contract

The built artifact must remain compatible with the accepted v1.1.7
documentation contract.

Installed-user verification must reuse the existing executable First 15
Minutes / onboarding authority rather than invent a second onboarding flow.

No release documentation may claim an installed-user capability that the wheel
does not expose.

## 10. Required Local Evidence

Before the v1.1.8 acceptance PR may merge, the candidate requires fresh:

- artifact set verification;
- wheel/sdist metadata verification;
- checksum verification;
- clean-install verification;
- installed `opl` smoke verification;
- Marketplace installed-user verification;
- AI Stable installed-user verification;
- First 15 Minutes / onboarding installed-user verification;
- full regression;
- required coverage;
- `git diff --check`;
- pre-commit;
- required GitHub Actions / CI.

## 11. Explicit Non-goals

v1.1.8 does not:

- publish v1.1;
- create a release tag;
- create a GitHub Release;
- accept Formal v1.1;
- require the Experimental AI provider path;
- require external credentials or network access;
- broaden the support matrix without direct evidence;
- reuse v1.0 artifacts as v1.1 evidence.

## 12. Acceptance Blockers

The slice is blocked by:

- missing wheel or sdist;
- duplicate or stale distribution artifacts;
- metadata/version mismatch;
- checksum mismatch;
- source commit mismatch;
- source-tree leakage into clean-install tests;
- installed CLI surface drift;
- Marketplace behavior drift;
- AI Stable behavior drift;
- onboarding failure;
- regression or coverage failure;
- required CI failure;
- premature Formal v1.1 acceptance.

## 13. Code Review Checklist

### Architecture / identity

- [ ] Existing v1 release-artifact infrastructure is reused.
- [ ] Exactly one wheel and one sdist are verified.
- [ ] Canonical version and artifact metadata agree.
- [ ] Artifact source commit is explicit and immutable.
- [ ] Checksum manifest covers the exact candidate artifacts.

### Installed-user behavior

- [ ] Verification uses the built wheel, not the source checkout.
- [ ] Installed `opl --help` and `opl list` pass.
- [ ] Installed Marketplace CLI surface passes.
- [ ] Installed AI Stable local-response surface passes.
- [ ] Experimental AI provider access is not required.
- [ ] First 15 Minutes / onboarding passes from installed package.

### Reliability / acceptance

- [ ] Full regression passes.
- [ ] Required coverage passes.
- [ ] `git diff --check` passes.
- [ ] pre-commit passes.
- [ ] Required CI passes.
- [ ] v1.0 artifacts are not reused as v1.1 evidence.
- [ ] Formal v1.1 Acceptance remains Not Accepted.

> A v1.1 candidate is not release-ready because source tests pass; it is
> release-ready only when the built artifacts preserve the same verified
> identity and installed-user behavior.
