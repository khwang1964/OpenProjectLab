## 1. Purpose

This document is the governing design and verification contract for
OpenProjectLab Milestone 8 Step 8.9.

Step 8.9 answers one release-level question:

> Is the complete OpenProjectLab v1.0 release-candidate repository state
> internally consistent, artifact-backed, policy-aligned, documented, and
> verified well enough to enter Step 8.10 RC Acceptance?

Step 8.9 integrates the accepted results of Steps 8.1 through 8.8. It does
not redefine their contracts and does not substitute source-checkout success
for installed-user evidence.

---

## 2. Governing Decision

OpenProjectLab v1.0 full release readiness is accepted only when all required
evidence forms one coherent, traceable state:

```text
Accepted release-readiness contracts
        ↓
Repository and policy consistency
        ↓
Documentation and support-claim consistency
        ↓
Verified release artifacts
        ↓
Representative installed-user E2E
        ↓
Full regression and quality gates
        ↓
GitHub Actions / CI
        ↓
Formal Step 8.9 acceptance
```

No individual passing layer compensates for failure in another required
layer. Step 8.9 is fail-closed.

---

## 3. Scope

Step 8.9 owns:

- auditing the formal closure state of Steps 8.1 through 8.8;
- verifying that accepted contracts remain mutually consistent;
- verifying that public-contract, compatibility, support, and limitation
  claims agree;
- verifying English and Traditional Chinese (Taiwan) documentation parity;
- validating the First 15 Minutes workflow from a current built wheel;
- validating wheel and source-distribution release artifacts;
- executing a representative installed-user E2E outside the source checkout;
- executing the complete test suite and coverage gate;
- executing repository quality, documentation, packaging, and release checks;
- recording GitHub Actions / CI and post-merge acceptance evidence;
- deciding whether the repository may enter Step 8.10 RC Acceptance.

---

## 4. Explicit Non-goals

Step 8.9 does not:

- create or publish `v1.0.0-rc.1`;
- create or publish the `v1.0.0` GA release;
- declare RC Acceptance or GA Acceptance;
- change the frozen v1.0 Stable public surface;
- expand the support matrix without new evidence and the required review;
- remove or weaken known limitations;
- introduce new product features;
- absorb deferred v1.1+ work;
- claim byte-for-byte reproducibility when only semantic reproducibility is
  demonstrated;
- require real publication credentials for deterministic verification.

Step 8.10 remains the owner of RC creation and RC Acceptance.

| Step 8.5 bilingual user manuals | Verify structure, functional parity, and executable onboarding |

| Step 8.7 support matrix and known limitations | Verify claims remain evidence-backed and limitations remain visible |
| Step 8.8 release automation and reproducibility | Verify release identity, artifacts, checksums, workflow, and semantic reproducibility |

If two accepted records conflict, Step 8.9 must fail and require correction.

## 6. Verification Architecture

```text
Layer 1 — Closure audit
        ↓
Layer 2 — Contract and policy consistency
        ↓
Layer 3 — Documentation consistency
        ↓
Layer 4 — Artifact and package verification
        ↓
Layer 5 — Installed-user behavior
        ↓
Layer 6 — Regression and quality gates
        ↓
Layer 7 — CI and formal acceptance
```

Each layer produces reviewable evidence. Later layers may depend on earlier
layers, but no layer may silently reinterpret an earlier accepted contract.

## 7. Release-readiness Invariants

The complete v1.0 state must satisfy all of the following:

```text
Frozen public contract
    == documented Stable contract

Compatibility policy
    == actual release behavior

Support matrix
    == tested environment evidence

Known limitations
    == visible user-facing limitations

Canonical version
    == artifact metadata version

Approved commit
    == expected release source identity

Verified artifact set
    == installed-user test input

English manual behavior
    == zh-TW manual behavior

Source-checkout result
    agrees with
installed-artifact result
```

Any unexplained disagreement is a release blocker.

## 8. Step 8.1–8.8 Closure Audit

The closure audit must verify, for every prior Milestone 8 step:

- a governing design or governing record exists;
- an acceptance record exists where required;
- the final status is `Accepted` or the equivalent approved terminal state;
- acceptance PR and CI evidence is recorded where required;
- post-merge consistency evidence is recorded;
- roadmap, HISTORY, and CHANGELOG agree;
- no placeholder such as `<actual result>`, `<PR number>`, or unresolved
  closure `Pending` remains;
- no later document silently weakens an earlier accepted contract.

The audit should be automated with deterministic document-contract tests where
practical. Human-readable records remain the source of acceptance evidence.

---

## 9. Public-contract Consistency

Step 8.2 remains authoritative for the v1.0 Stable public surface.

Step 8.9 must verify:

- SDK exports remain frozen as accepted;
- generator and plugin contracts remain compatible;
- CLI command names and supported behavior remain documented;
- package metadata and console entry points remain consistent;
- Courseware, AI, Marketplace, configuration, filesystem, and public-error
  contracts remain within the accepted boundary;
- Experimental and Internal behavior is not accidentally presented as Stable;
- no release-readiness change creates an undocumented public authority.

Public-contract drift blocks Step 8.9 acceptance.

---

## 10. Compatibility and Deprecation Consistency

Step 8.6 remains authoritative.

Verification must confirm:

- `1.0.x` remains limited to compatibility-preserving fixes;
- backward-compatible `1.x` evolution and intentional `2.0` breaking changes
  remain correctly distinguished;
- Deprecated Stable behavior retains required migration guidance;
- no Stable removal is implied before the next major version except through
  the documented emergency process;
- user-visible compatibility statements agree in English and zh-TW;
- CHANGELOG and release documentation do not contradict the policy.

---

## 11. Support Matrix and Known-limitations Consistency

Step 8.7 remains authoritative for support claims.

Step 8.9 must verify:

- every Supported environment has recorded test evidence;
- successful execution on an unlisted environment does not automatically
  expand support;
- Experimental, Known Limitation, and Deferred classifications remain visible;
- packaging and installed-user results do not overgeneralize OS or Python
  support;
- release notes point users to the authoritative support and limitation
  records;
- deferred Marketplace and AI capabilities remain outside the v1.0 blocker
  boundary unless formally reclassified.

---

## 12. Documentation Verification

Documentation verification must include:

- user-manual structure checks;
- English and Traditional Chinese (Taiwan) chapter parity;
- functional parity for commands, examples, configuration, and workflows;
- installation instructions verified against current artifacts;
- CLI and generator behavior checked against the frozen implementation;
- Plugin, Courseware, AI, and Marketplace documentation checked against
  accepted capabilities and limitations;
- architecture and Concepts chapters checked for current terminology;
- troubleshooting guidance checked for current installation and runtime paths;
- links and canonical document references checked where automation exists;
- release, roadmap, HISTORY, and CHANGELOG status alignment.

Documentation correctness is a release gate, not a non-blocking polish task.

---

## 13. First 15 Minutes Verification

The First 15 Minutes workflow must run as an installed-user smoke test using
the current built wheel.

Required properties:

- `OPL_TEST_WHEEL`, or its canonical replacement, identifies the current wheel;
- installation occurs in an isolated environment;
- execution does not import the source checkout accidentally;
- packaged templates and runtime resources are exercised;
- documented commands produce the documented class of output;
- the workflow is deterministic and does not require network access;
- failures identify whether installation, resources, CLI, or documentation
  expectations diverged.

Skipping the workflow because no wheel was supplied is not acceptable for the
final Step 8.9 evidence run.

---

## 14. Release-artifact Verification

The Step 8.9 build must start from a clean artifact-output directory and
produce the canonical artifact set.

Verification must cover:

- wheel and source-distribution enumeration;
- rejection of stale or unexpected artifacts;
- artifact filename and metadata version consistency;
- required package metadata;
- console entry point;
- packaged resources and templates;
- checksum generation and verification;
- checksum mutation detection;
- clean installation from the current wheel;
- semantic rebuild equivalence;
- absence of source-checkout-only dependencies.

Artifact bytes used by installed-user tests must be the same verified bytes
identified by the release-verification evidence.

---

## 15. Representative Installed-user E2E

Step 8.9 must add or establish one representative artifact-backed E2E that
crosses the major user-facing boundaries without depending on repository
imports.

The E2E must:

1. build or receive the current verified wheel;
2. create an isolated installation environment;
3. install only from the provided artifact and declared dependencies;
4. run from outside the source checkout;
5. exercise the installed console entry point;
6. enumerate available generators or equivalent capabilities;
7. execute a representative Bootstrap Framework generation path;
8. execute representative courseware generation behavior;
9. verify expected files and packaged resources;
10. verify deterministic failure behavior for at least one invalid input;
11. record diagnostics without exposing credentials or requiring publication;
12. cleanly distinguish product failure from test-harness failure.

The exact command sequence must be derived from the accepted CLI and generator
contracts. Step 8.9 must not invent a second user workflow.

## 16. Environment Strategy

The final verification matrix is limited to environments supported by recorded
Step 8.7 evidence.

Required evidence includes:

- the CI-backed supported Ubuntu and Python combination;
- the maintainer-backed supported Windows and Python combination;
- current built-wheel installation evidence;
- explicit labeling of any environment that is not covered.

One environment may provide the formal local completion-state record while CI
provides the complementary supported-environment evidence. Claims must state
which evidence came from which environment.

## 17. Automation Strategy

Automation should be deterministic, composable, and fail-closed.

Preferred structure:

```text
Focused contract tests
        ↓
Documentation and policy tests
        ↓
Artifact build and inspection
        ↓
Wheel-backed installed-user tests
        ↓
Representative installed-user E2E
        ↓
Full regression and coverage
        ↓
GitHub Actions / CI
```

The design should reuse accepted Step 8.2–8.8 test helpers and artifact inputs
rather than duplicate release logic.

Automation must not:

- silently select a stale wheel;
- treat a skipped wheel-backed suite as passing release evidence;
- require GitHub publication credentials for verification;
- make network availability a prerequisite for deterministic tests;
- mutate tags, releases, or published artifacts;
- conceal unsupported-environment execution as Supported evidence.

GitHub Actions must verify the relevant source and artifact-backed paths.

Required CI properties:

- ordinary pull-request checks cannot publish a release;

- required checks must pass before the Step 8.9 acceptance PR is merged;

## 22. Failure Classification

Failures should be classified as:

| Class | Meaning | Required response |
|---|---|---|
| Release blocker | Violates a required v1.0 contract or readiness gate | Fix before Step 8.9 acceptance |
| Evidence gap | Required result may be correct but is not proven | Add deterministic evidence before acceptance |
| Documentation defect | User-facing claim disagrees with verified behavior | Correct and re-verify before acceptance |
| Unsupported expansion | Claim exceeds Step 8.7 evidence | Remove or formally reclassify the claim |
| Deferred improvement | Valuable but not required for v1.0 correctness | Record in v1.1+ backlog |

No release blocker may be reclassified as Deferred merely to close the step.

# Final Principle

> A release candidate is not ready because every component passed once in
> isolation. It is ready to enter acceptance only when contracts, policies,
> documentation, artifacts, installed-user behavior, regression evidence, and
> CI describe the same complete release state.
