# OpenProjectLab v1.0 RC Build / Artifact Identity

> **Status:** Design / Contract Definition — Red Phase
> **Milestone:** 8 — v1.0 Stabilization & Release Readiness
> **Step:** 8.10.4 — RC Build / Artifact Identity
> **Date:** 2026-08-19
> **Predecessor:** Step 8.10.1–8.10.3 — Completed

> **Publication:** Not permitted in this slice

---

## 1. Purpose

Step 8.10.4 establishes the first concrete Release Candidate build identity
for OpenProjectLab v1.0.

This slice answers one question:

> Can one approved source commit produce one fresh, unambiguous RC artifact
> set whose package metadata, filenames, checksums, and human-facing RC
> identity all describe the same candidate?

Step 8.10.4 is a pre-publication build/identity gate.

It does not create a Git tag, publish a GitHub Release, upload artifacts, or
formally accept the RC.

---

## 2. Governing Identity Model

The first RC has two intentionally different but equivalent representations:

```text
Python / package identity
    1.0.0rc1

Human-facing RC identity
    v1.0.0-rc.1
```

The package representation follows Python packaging normalization.

The human-facing representation follows the Step 8.10 governing RC contract.

These values are not compared by naïve string equality. They are related by an
explicit deterministic mapping owned by the release identity layer.

---

## 3. Architecture

```text
pyproject.toml
[project].version = 1.0.0rc1
        │
        ▼
read_canonical_version()
        │
        ├──────────────► package version = 1.0.0rc1
        │
        └──────────────► expected_release_tag()
                              │
                              ▼
                         v1.0.0-rc.1

Approved source commit SHA
        │
        ▼
ReleaseIdentity
        │
        ▼
Fresh build
        │
        ├── openprojectlab-1.0.0rc1-...whl
        └── openprojectlab-1.0.0rc1.tar.gz
        │
        ▼
Artifact-set verification
        │
        ▼
SHA-256 manifest
```

Responsibility boundaries:

- `pyproject.toml` remains the canonical package-version source.
- `generator.release.identity` owns package-version ↔ release-tag mapping.
- `generator.release.artifacts` owns artifact-set, metadata, and checksum
  validation.
- Git owns immutable source commit identity.
- Step 8.10.4 verification is read-only with respect to tags and GitHub
  Releases.
- Publication remains owned by later Step 8.10 gates.

---

## 4. Canonical Package Version Contract

For `v1.0.0-rc.1`, the repository package version must be:

```text
1.0.0rc1
```

The authoritative source remains:

```text
pyproject.toml
[project].version
```

The RC build must not obtain its version from environment-only overrides,
branch names, Git tags, local untracked files, generated temporary metadata,
or CI-only mutation.

The version must be reviewable repository state before the RC build.

---

## 5. Canonical RC Tag Mapping Contract

The release identity layer must map:

```text
1.0.0rc1  →  v1.0.0-rc.1
```

Stable releases remain direct:

```text
1.0.0     →  v1.0.0
1.0.1     →  v1.0.1
```

The mapping must be deterministic and side-effect free.

It must not inspect GitHub, create or move a tag, infer version from a branch,
require network access, or silently accept malformed prerelease syntax.

The accepted tag grammar for this RC is exactly:

```text
v1.0.0-rc.1
```

`v1.0.0rc1` is not the human-facing canonical RC tag.

---

## 6. Source Commit Contract

One RC build is bound to one approved full Git commit SHA.

The commit identity must be a full 40-character lowercase SHA-1 value under
the current repository contract, identify committed repository state, be
recorded before final artifact identity verification, remain the same source
identity for the wheel and sdist, and later become the tag target if the RC
proceeds to publication.

Floating identities are invalid:

```text
HEAD
main
origin/main
release/v1.0
```

Step 8.10.4 validates source identity but does not create the RC tag.

---

## 7. Fresh Build Contract

The RC build must start from an intentionally clean artifact output directory.

Canonical artifact kinds:

```text
wheel
sdist
```

For package version `1.0.0rc1`, expected artifact identities are:

```text
openprojectlab-1.0.0rc1-<wheel-tags>.whl
openprojectlab-1.0.0rc1.tar.gz
```

The exact wheel compatibility tags are build-tool output and are not hard-coded
beyond the existing release artifact contract.

The artifact directory must not contain a stale second wheel or sdist that can
be mistaken for the current RC.

---

## 8. Artifact Metadata Contract

Artifact filenames alone are insufficient.

The wheel must contain distribution metadata identifying:

```text
Name: openprojectlab
Version: 1.0.0rc1
```

The sdist filename must identify the same package version.

Any mismatch between canonical repository version, filename identity, or wheel
metadata is an RC blocker.

---

## 9. Artifact Set Contract

Exactly one wheel and one sdist belong to the RC build set.

The verification layer must reject no wheel, no sdist, multiple wheels,
multiple sdists, wrong project name, wrong version, stale artifacts, unsupported
artifact types when treated as release artifacts, and duplicate artifact paths.

Selection must never fall back to an older distribution.

---

## 10. Checksum Contract

After artifact identity passes, the exact artifact bytes must be bound by
SHA-256.

The checksum manifest must contain exactly the verified release artifact
filenames, contain one SHA-256 digest per artifact, be deterministic in key
ordering, and detect artifact mutation after checksum generation.

The checksum identity belongs to exact bytes, not merely a filename.

---

## 11. Build / Verification Ordering

Required ordering:

```text
Confirm canonical repository version
        ↓
Resolve approved source commit
        ↓
Clean dist output
        ↓
Build wheel + sdist
        ↓
Enumerate artifact set
        ↓
Verify filenames
        ↓
Verify wheel metadata
        ↓
Generate checksum manifest
        ↓
Verify checksum manifest
        ↓
Record Step 8.10.4 evidence
```

Checksum generation before artifact identity verification is not sufficient.

---

## 12. Fail-closed Rules

Step 8.10.4 fails when any of the following is true:

- `[project].version` is not `1.0.0rc1`;
- package version cannot map to `v1.0.0-rc.1`;
- source commit identity is missing or floating;
- artifact output is ambiguous;
- wheel/sdist version does not match the canonical package version;
- wheel METADATA disagrees with the expected project/version;
- checksum coverage is incomplete;
- checksum verification fails;
- artifact identity depends on source-checkout-only imports;
- verification requires a tag or GitHub Release to exist.

A failed build/identity gate does not proceed to publication.

---

## 13. Explicit Non-goals

Step 8.10.4 does not create `v1.0.0-rc.1`, push a Git tag, create a GitHub
Release, upload wheel/sdist assets, mark the RC Accepted, mark v1.0.0 GA
Accepted, run the final artifact-backed installed-user acceptance gate, change
support claims, expand the frozen v1.0 public surface, or add product features.

---

## 14. Required Production Surface

Step 8.10.4 reuses the existing release modules rather than establishing a
second RC-specific release framework.

Expected production authorities:

```text
generator/release/identity.py
generator/release/artifacts.py
pyproject.toml
```

Minimum required behavior:

```text
read_canonical_version(pyproject) -> "1.0.0rc1"

expected_release_tag("1.0.0rc1")
    -> "v1.0.0-rc.1"

ReleaseIdentity(
    version="1.0.0rc1",
    commit_sha=<full-sha>,
    tag="v1.0.0-rc.1",
)

verify_release_artifact_set(
    ...,
    expected_project="openprojectlab",
    expected_version="1.0.0rc1",
)

generate_sha256_manifest(...)
verify_checksum_manifest(...)
```

No new public `generator.sdk` surface is required.

---

## 15. Test Contract

Focused Step 8.10.4 tests must prove:

- the RC build/identity governing document exists;
- canonical package version is exactly `1.0.0rc1`;
- package version resolves through the production canonical-version reader;
- RC tag mapping is exactly `v1.0.0-rc.1`;
- stable tag mapping remains unchanged;
- `ReleaseIdentity` accepts the RC package/tag pair with a full SHA;
- the RC tag mapping remains side-effect free;
- wheel/sdist filenames using `1.0.0rc1` are accepted;
- wheel metadata using `1.0.0rc1` is accepted;
- stale `0.6.0` artifacts are rejected for the RC identity;
- checksum generation and verification bind exact RC artifact bytes;
- artifact mutation is detected;
- no tag or GitHub Release is required by these tests.

The first targeted run is expected to be Red until the implementation slice
updates the canonical version and RC tag mapping.

---

## 16. Expected Red Phase

At design/test introduction time, two known gaps are expected:

```text
pyproject.toml [project].version
    current: 0.6.0
    required: 1.0.0rc1

expected_release_tag("1.0.0rc1")
    current: v1.0.0rc1
    required: v1.0.0-rc.1
```

These failures are intentional Step 8.10.4 implementation requirements.

Artifact-set and checksum primitives are expected to be reused rather than
rewritten.

---

## 17. Implementation Boundary After Red Phase

The minimum implementation slice should be limited to:

1. change the canonical project version to `1.0.0rc1`;
2. make RC tag derivation map PEP 440 RC syntax to the accepted human-facing
   tag syntax;
3. update existing release-identity tests whose old expectation encoded
   `v1.0.0rc1`;
4. keep stable-release tag behavior unchanged;
5. run focused release and Step 8.10.4 tests;
6. build fresh RC artifacts;
7. verify exact artifact/checksum identity.

If additional production changes are needed, they require evidence from a
failing contract test.

---

## 18. Acceptance Evidence for Step 8.10.4

Completion evidence must record actual values for canonical package version,
canonical RC tag mapping, approved source commit SHA, fresh wheel, fresh sdist,
artifact-set verification, wheel metadata verification, SHA-256 manifest,
checksum verification, focused tests, `git diff --check`, and pre-commit.

No future PR, CI, tag, release URL, or acceptance result is pre-filled here.
