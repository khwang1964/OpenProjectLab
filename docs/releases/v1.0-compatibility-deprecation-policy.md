## 1. Purpose

Step 8.6 establishes compatibility and deprecation governance for
OpenProjectLab (OPL) beginning with the frozen v1.0 public-contract
baseline.

Step 8.2 already distinguished repository implementation from public
commitment and classified reviewed contracts as Stable, Experimental,
Internal, or Deferred. Step 8.6 does not reopen that freeze merely to
redesign the product. It defines what maintainers may change after v1.0,
what users and third-party integrations may reasonably depend on, how a
Stable contract is deprecated, and what evidence is required for
compatibility-sensitive changes.

The governing release rule is:

``` text
1.0.x → compatibility-preserving fixes
1.x   → backward-compatible evolution
2.0   → intentional breaking Stable-contract changes
```

The central rule remains:

``` text
Implementation existence
        ≠
Public contract
        ≠
Stable compatibility promise
```

Only contracts explicitly classified Stable receive the full v1
compatibility commitment.

## 2. Governing Principles

### 2.1 Design First

Compatibility-sensitive behavior must be identified before
implementation changes merge. A Stable-contract change requires an
explicit compatibility decision, not an accidental decision produced by
refactoring.

### 2.2 Documentation First

Deprecation is a public communication contract. A Stable capability is
not properly deprecated merely because maintainers intend to remove it
later. The affected identity, migration path, timing, and user impact
must be documented.

### 2.3 Automation First

Mechanically verifiable guarantees should be protected by tests or CI.
Existing Step 8.2 public-contract freeze tests remain the baseline. Step
8.6 adds focused policy checks without unnecessarily freezing Internal
implementation.

### 2.4 Stable Means Dependable

Users and third-party integrations may reasonably depend on Stable
canonical names and access paths, documented semantics, validation
behavior, compatibility-sensitive failure behavior, and deterministic
behavior explicitly frozen by Step 8.2.

### 2.5 Compatibility Is Behavioral

Compatibility is not limited to whether a Python import still succeeds.
A change can be breaking if documented semantics, valid input, generated
artifacts, ordering, failure behavior, side-effect boundaries, CLI
behavior, or another Stable guarantee changes incompatibly.

### 2.6 Feature Freeze Remains Active

Step 8.6 is governance, not feature expansion. Candidate, Experimental,
Internal, or Deferred capabilities must not be silently promoted to
Stable.

### 3.2 Out of Scope

-   silently reclassify Step 8.2 contracts;
-   define Step 8.7 support-matrix or environment-support claims;
-   define Step 8.7 known-limitations policy;
-   implement Step 8.8 release publication/reproducibility automation;
-   require a generalized API-diff engine for v1.0;
-   add new CLI, Generator, Plugin, AI, or Marketplace features;
-   give Stable guarantees to Experimental, Internal, or Deferred
    behavior.

## 4. Classification Obligations

Step 8.2 established:

``` text
Stable
Candidate
Experimental
Internal
Deferred
```

### Stable

Stable contracts receive the full v1 compatibility commitment. Breaking
them normally requires backward-compatible evolution, an explicit
deprecation/migration path, or a future major release.

### Candidate

Candidate is implemented but not frozen. Promotion requires explicit
contract review, implementation evidence, tests, documentation, and
compatibility analysis. Existence alone is insufficient.

### Experimental

Experimental capabilities do not receive the full Stable guarantee. They
must remain clearly labeled, document limitations, and avoid becoming
accidental dependencies of Stable contracts.

### Internal

Internal behavior may evolve during compatible v1 releases as long as
Stable external behavior remains preserved. Python importability or
repository visibility alone does not create a public promise.

### Deferred

Deferred capabilities are outside v1.0 scope and do not receive a v1
compatibility promise unless explicitly promoted by a later reviewed
decision.

## 6. Version-Series Policy

### 6.1 v1.0.x --- Compatibility-Preserving Fixes

Patch releases are the most conservative maintenance line.

Normally allowed:

-   correctness and security fixes that preserve Stable contracts;
-   documentation corrections;
-   packaging/installability and reliability fixes;
-   deterministic test/CI improvements;
-   compatible performance improvements;
-   Internal refactoring that preserves Stable behavior;
-   additive diagnostics that do not invalidate Stable consumers.

A normal v1.0.x release must not intentionally remove or rename Stable
symbols, commands, options, Generator identities, canonical access
paths, or required installed resources; reject previously
guaranteed-valid input; incompatibly change Stable artifacts, ordering,
validation, or failure boundaries; or remove Stable behavior merely
because a replacement exists.

### 6.2 v1.x --- Backward-Compatible Evolution

Minor releases may evolve OPL while preserving existing Stable v1
behavior.

Normally allowed:

-   additive public APIs with explicit classification;
-   new optional parameters with compatible defaults;
-   new commands or optional flags;
-   new Generators or plugin capabilities;
-   additional accepted input forms;
-   new documented capabilities;
-   Stable deprecation notices.

A v1.x release must not intentionally remove or incompatibly redefine a
Stable v1 contract except through an approved emergency exception.

### 6.3 v2.0 --- Intentional Breaking Evolution

A major release may intentionally remove or incompatibly change Stable
v1 contracts, but the change must still be governed.

Required evidence includes:

-   explicit breaking-change record;
-   rationale and affected Stable identities;
-   migration/replacement guidance;
-   CHANGELOG/release-note coverage;
-   documentation updates;
-   tests for the new contract;
-   intentional review of obsolete compatibility tests.

A major version permits breaking change; it does not permit undocumented
breaking change.

## 7. Compatible Change

A change is compatible when existing consumers using documented Stable
behavior can continue without mandatory source, command, configuration,
artifact-expectation, or workflow changes.

Examples include compatible bug fixes, optional parameters with
compatible defaults, additive commands, additional accepted input,
Internal refactoring behind Stable façades, and clearly labeled
Experimental additions.

Compatibility is judged against the frozen contract, not every
incidental observable implementation detail.

## 8. Breaking Change

A breaking change requires an existing Stable consumer to modify code,
commands, configuration, expected artifacts, or operational assumptions
to retain previously documented behavior.

Examples include:

-   removing/renaming a Stable public symbol or import path;
-   removing/renaming a Stable CLI command or option;
-   incompatibly changing required arguments or accepted Stable input;
-   changing a Stable Generator identity;
-   changing Stable artifact paths/membership;
-   changing contractual deterministic ordering;
-   changing Stable domain invariants;
-   changing Stable Plugin Entry Point identity rules;
-   changing contractual installation/activation separation;
-   violating a Stable failure-before-side-effect boundary;
-   replacing a Stable exception category incompatibly;
-   removing packaged runtime resources required by installed-user
    workflows.

Internal implementation, exact non-contractual error text, test helpers,
private modules, and incidental behavior are not automatically
protected.

## 9. Deprecation Lifecycle

Deprecation means a Stable contract remains available for compatibility
while users are formally advised to migrate before a future removal or
incompatible change.

``` text
Stable
  ↓
Deprecated Stable (still functional)
  ↓
Migration period
  ↓
Eligible for major-version removal
```

Deprecation is not removal. Deprecated Stable behavior remains part of
the v1 compatibility surface.

## 10. Required Deprecation Record

Every Stable deprecation must identify:

``` text
Contract:
Canonical identity/access path:
Classification: Stable → Deprecated Stable
Deprecation introduced in:
Reason:
Replacement:
Migration path:
Behavior during deprecation:
Expected removal:
Documentation locations:
Tests protecting compatibility:
Owner:
```

If no replacement exists, say so explicitly and explain the migration
consequence.

## 11. Deprecation Notice Requirements

Where practical, notices must appear where users depend on the contract,
such as:

-   API/reference documentation;
-   English and zh-TW User Manuals;
-   CLI help or deterministic runtime warning;
-   public SDK documentation/docstrings;
-   CHANGELOG/release notes;
-   migration guidance;
-   relevant ADR/architecture/release documentation.

Runtime warnings are not mandatory for every deprecation. If used, they
must be deterministic, testable, actionable, and not excessively noisy.

## 12. Minimum Deprecation Window

The default Stable v1 rule is:

``` text
deprecate during v1.x
        ↓
preserve compatibility for the remainder of v1.x
        ↓
remove or break no earlier than v2.0
```

Normal Stable removal is therefore not permitted in v1.0.x or v1.x.

Step 8.6 intentionally defines a version-based boundary, not a
calendar-duration promise.

## 13. Migration Guidance

Migration guidance is mandatory before a deprecated Stable contract is
removed or incompatibly changed.

Where applicable, document:

1.  old usage;
2.  replacement usage;
3.  semantic differences;
4.  changed defaults;
5.  configuration changes;
6.  artifact/output differences;
7.  failure-behavior differences;
8.  plugin/integration impact;
9.  automated migration support, if any;
10. validation steps after migration.

User-facing migration guidance must preserve EN/zh-TW functional parity.

## 14. Removal Rules

Normal Stable removal requires all of the following:

-   target release is a major version;
-   deprecation was formally recorded;
-   migration guidance exists;
-   relevant documentation is updated;
-   CHANGELOG/release notes identify removal;
-   compatibility tests are intentionally updated/removed in the
    major-version review;
-   replacement behavior, if any, has explicit classification/tests;
-   Code Review records an intentional breaking change.

A major-version number alone is not sufficient evidence.

## 15. Emergency Compatibility Exception

Rare security, data-integrity, legal, or severe correctness issues may
require an incompatible change before the next major release.

Required record:

``` text
Affected Stable contract:
Severity:
Why compatibility cannot safely be preserved:
Why deprecation cannot reasonably precede the fix:
User impact:
Migration / mitigation:
Tests:
Documentation:
Release-note notice:
Approver / review record:
```

Preferred order:

``` text
preserve compatibility
    ↓ if unsafe/impossible
provide temporary bridge
    ↓ if unsafe/impossible
documented emergency break
```

Convenience, cleanup, refactoring preference, or implementation
simplification are insufficient reasons.

## 16. Special Contract Areas

### Python Public SDK

Stable `generator.sdk` access and semantics must remain compatible
through v1. Internal implementation may move behind the façade.

### CLI

Stable command identity, reviewed options, argument semantics, and
documented failure behavior are compatibility-sensitive. Tests should
not freeze parser internals unnecessarily.

### Generators / Courseware

Compatibility may include Generator identities, request/plan/result
semantics, validated inputs, reviewed artifact paths, deterministic
ordering, dry-run/overwrite behavior, domain invariants, and composition
failure semantics.

### Plugins

Stable Entry Point identity, public SDK boundary, validation, and
registration semantics must remain compatible through v1. Third-party
plugins should not be forced onto Internal APIs by a compatible upgrade.

### AI

Only provider-independent contracts classified Stable receive the v1
guarantee. Provider-specific/deferred behavior keeps its explicit
classification.

### Marketplace

Only contracts frozen Stable by Step 8.2 receive Stable treatment.
Deferred remote Marketplace, signing/publisher identity, dependency
resolution, ratings/reviews, monetization, and related features remain
outside v1.0.

### Configuration / Filesystem / Errors

Only the verified Stable subset is protected. Exact error-message text
is not Stable unless explicitly classified, while Stable exception
categories and failure/write boundaries may be compatibility-sensitive.

### Packaging / Installed Resources

Package identity, console entry point, and installed runtime-resource
expectations frozen by Steps 8.2/8.4 are compatibility-sensitive. v1
must not regress to developer-checkout, editable-only, `PYTHONPATH`,
repository-template, or untracked-file dependencies.

## 18. Automation Strategy

Step 8.6 should add focused policy tests rather than a brittle
repository-wide snapshot.

Recommended package:

``` text
tests/compatibility/
    __init__.py
    test_version_policy_contract.py
    test_deprecation_policy_contract.py
```

### Version Policy Tests

Where practical, verify:

-   governing policy exists;
-   `1.0.x`, `1.x`, `2.0` rules are explicit;
-   normal Stable removal is forbidden in v1;
-   major breaking changes require migration guidance;
-   Experimental/Internal/Deferred do not receive Stable guarantees;
-   emergency exceptions require explicit evidence.

### Deprecation Policy Tests

Where practical, verify:

-   canonical identity is required;
-   replacement or explicit no-replacement decision is required;
-   migration guidance is required;
-   deprecation and removal are distinct;
-   normal removal is no earlier than a major version;
-   documentation/CHANGELOG obligations exist;
-   EN/zh-TW parity remains required for user-facing migration guidance.

Step 8.2 contract-freeze tests remain authoritative for the exact v1.0
Stable surface. Step 8.6 must not duplicate that source of truth
unnecessarily.

A generalized semantic API/CLI/artifact diff engine is not a v1.0
acceptance requirement.

``` text

        ↓
```

# Final Principle

> Preserve what v1 users were promised. Deprecate before normal removal.
> Make migration explicit. Reserve intentional Stable-contract breaks
> for a major release.

Step 8.6 is complete only when OPL has an explicit, reviewable,
documented, and testable rule for deciding whether a change belongs in
v1.0.x, v1.x, or a future major release, and Stable-contract deprecation
can no longer occur silently.
