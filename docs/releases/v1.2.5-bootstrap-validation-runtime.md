# OpenProjectLab v1.2.5 Bootstrap Validation Runtime

> **Status:** Accepted --- Terminally Closed
> **Predecessor:** v1.2.4 Bootstrap Apply Execution --- Accepted / Implemented
> **Target Slice:** v1.2.5 --- Bootstrap Validation Runtime
> **Production Implementation:** Not Started

## 1. Purpose

Define deterministic, inspection-only validation of observable project state
after apply or when explicitly requested.

``` text
BootstrapValidationRequest
    ↓
BootstrapValidator.validate(request)
    ↓ ordered checks
BootstrapValidationFinding
    ↓
BootstrapValidationResult
```

No production validation runtime is authorized by this document.

## 2. Scope

In scope:

- immutable `BootstrapValidationRequest`;
- internal `BootstrapValidationCheck` boundary;
- immutable `BootstrapValidationFinding`;
- immutable `BootstrapValidationResult`;
- deterministic `BootstrapValidator` orchestration;
- existing read-only filesystem boundary reuse;
- explicit valid/invalid evidence and fail-closed check errors.

Out of scope:

- filesystem mutation or silent repair;
- apply execution or re-apply;
- automatic rollback;
- checkpoint/resume;
- network access or implicit plugin activation;
- parallel validation;
- Stable Bootstrap CLI syntax;
- public SDK expansion.

## 3. Core Contracts

### 3.1 BootstrapValidationRequest

Immutable input identifying the target/project state and ordered validation
context. It may reference prior apply evidence but must not mutate it.

### 3.2 BootstrapValidationCheck

An internal injected inspection contract with stable `check_id`. A check reads
observable state and returns zero or more findings. It performs no repair,
write, apply, network access, or plugin activation.

### 3.3 BootstrapValidationFinding

Immutable evidence containing stable check identity, deterministic severity,
message, and optional normalized subject/path identity. Findings describe
invalid or advisory state; they are not repair commands.

### 3.4 BootstrapValidationResult

Immutable ordered aggregate of executed check identities and findings. Its
validity is derived deterministically from accepted severity semantics.

### 3.5 BootstrapValidator

`BootstrapValidator.validate(request)` executes checks in configured order,
preserves deterministic finding order, and returns complete validation
evidence without mutating project state.

## 4. Inspection-only Boundary

``` text
Validation --- Inspection Only
Filesystem Mutation --- Forbidden
Silent Repair --- Forbidden
Apply / Re-apply --- Forbidden
Manifest / Backup / Checkpoint Writes --- Forbidden
```

Filesystem inspection must reuse existing read/existence boundaries. No
parallel filesystem abstraction or mutation path may be introduced.

## 5. Determinism

- check order is explicit and stable;
- finding order follows check order and each check's stable order;
- equivalent request and observable state produce equivalent results;
- timestamps, random IDs, and incidental enumeration order are excluded;
- duplicate check identities are rejected before inspection.

## 6. Severity and Validity

The minimum design recognizes deterministic `error`, `warning`, and `info`
severity values. A result is invalid when one or more `error` findings exist.
Warnings and informational findings remain observable but do not alone make a
result invalid.

## 7. Failure Semantics

An ordinary invalid project condition is represented by a finding. A check
infrastructure/programming failure is not converted into a normal finding.
Validation stops fail closed and exposes:

- the failed check identity;
- already completed check evidence.

``` text
Invalid State --- Finding
Check Execution Failure --- Fail Closed
Success-shaped Partial Result --- Forbidden
Automatic Repair --- Forbidden
Automatic Rollback --- Not Applicable / Not Performed
```

## 8. Apply and Rollback Boundary

Validation may inspect state produced by v1.2.4 apply.

Validation must not call apply, reverse completed mutations, or imply
transaction-wide atomicity.
Validation failure does not imply automatic rollback.
