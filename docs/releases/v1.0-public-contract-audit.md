# OpenProjectLab v1.0 Public Contract Audit

> **Status:** Proposed
> **Milestone:** 8 — v1.0 Stabilization & Release Readiness
> **Step:** 8.2 — Public Contract Audit & Freeze
> **Target Release:** OpenProjectLab v1.0.0
> **Depends On:** `docs/releases/v1.0-release-readiness.md`
> **Purpose:** Identify, classify, verify, and freeze the OpenProjectLab public compatibility surface before the v1.0 release candidate.

---

## 1. Purpose

OpenProjectLab has accumulated multiple externally visible contracts across the Generator Framework, Plugin SDK, Courseware Platform, AI Integration, Marketplace, CLI, configuration, filesystem behavior, generated artifacts, and packaging.

Before v1.0, those contracts must be distinguished from implementation details.

The purpose of Step 8.2 is to answer:

> **What may an OpenProjectLab v1.0 user, plugin author, automation system, or downstream integration safely depend on?**

The audit establishes:

- the canonical public surface;
- the intended v1.0 Stable contracts;
- Experimental boundaries;
- Internal implementation boundaries;
- Deferred capabilities;
- compatibility-sensitive behavior;
- missing contract tests;
- missing documentation;
- release blockers preventing a contract from becoming Stable.

This step does not assume that every currently importable object, CLI behavior, filesystem detail, or generated file is automatically a public contract.

---

## 2. Governing Principles

The audit follows the OpenProjectLab engineering sequence:

```text
Design First
    ↓
Documentation First
    ↓
Automation First
    ↓
Testing First
    ↓
Review
    ↓
Freeze
```

The central rule is:

```text
Implementation existence
        ≠
Public contract
        ≠
Stable v1.0 contract
```

A capability becomes Stable only through explicit review and evidence.

---

## 3. Relationship to Step 8.1

Step 8.1 defines the v1.0 release-readiness classification model:

```text
Stable
Candidate
Experimental
Internal
Deferred
```

Step 8.2 applies that classification to actual OpenProjectLab contracts.

The expected transition is:

```text
Candidate
   ↓
Audit implementation
   ↓
Audit tests
   ↓
Audit documentation
   ↓
Audit compatibility impact
   ↓
Resolve ambiguity
   ↓
Stable / Experimental / Internal / Deferred
```

Step 8.2 must not silently promote a Candidate contract to Stable merely because the capability has existed for several milestones.

# Classification Model

## 4. Stable

A Stable contract is part of the OpenProjectLab v1.0 compatibility commitment.

Users and third-party integrations may reasonably depend on it.

A Stable contract must have:

- a canonical name;
- a canonical import path or invocation path where applicable;
- documented semantics;
- defined validation behavior;
- deterministic tests;
- compatibility-sensitive behavior identified;
- no unresolved critical ambiguity;
- clear ownership;
- no accidental dependency on Internal implementation details.

After v1.0, breaking a Stable contract normally requires:

- backward-compatible evolution;
- an explicit deprecation process; or
- a future major release.

---

## 5. Candidate

Candidate means:

> Implemented and potentially suitable for v1.0 Stable status, but not yet frozen.

Candidate contracts require audit evidence before promotion.

A Candidate may become:

```text
Candidate → Stable
Candidate → Experimental
Candidate → Internal
Candidate → Deferred
```

---

## 6. Experimental

Experimental capabilities may be available in v1.0 but are excluded from the full Stable compatibility guarantee.

Experimental capabilities must:

- be clearly labeled;
- not masquerade as Stable;
- document their limitations;
- avoid becoming accidental dependencies of Stable contracts.

---

## 7. Internal

Internal means the behavior is an implementation detail.

Internal implementation may change in compatible v1.x releases as long as Stable external behavior remains preserved.

An object is not automatically public merely because Python permits importing it.

---

## 8. Deferred

Deferred capabilities are outside the v1.0 release scope.

Deferred work must not block v1.0 unless a later release-readiness decision explicitly promotes it.

---

# Audit Evidence Model

## 9. Required Evidence

Every Candidate contract should be reviewed against the following evidence.

| Evidence | Question |
|---|---|
| Canonical identity | What is the public name? |
| Canonical access | How does a user or integration reach it? |
| Implementation | Does production implementation exist? |
| Contract tests | Which tests define its behavior? |
| Integration tests | Is interaction with surrounding systems verified? |
| Documentation | Where is user/developer behavior documented? |
| ADR / architecture | Is the design boundary intentional? |
| Consumers | Who is expected to depend on it? |
| Compatibility sensitivity | What changes would break consumers? |
| Failure semantics | What errors are part of expected behavior? |
| Determinism | Is ordering/output deterministic where promised? |
| Side effects | What externally visible state can change? |
| Release blocker | What prevents Stable classification? |
| Final classification | Stable / Experimental / Internal / Deferred |

# Audit Priority

## 11. Risk-Based Audit Order

Contracts should be audited in descending compatibility risk.

### Priority 1 — External Extension Surface

```text

Plugin Entry Point
Plugin validation
Plugin registration
```

These are especially sensitive because third-party packages may depend on them.

### Priority 2 — Generator Core

```text
GenerateRequest
RuntimeOptions
GenerationOperation
GenerationPlan
GenerationResult
BaseGenerator lifecycle
```

These contracts underpin built-in and third-party Generator behavior.

### Priority 3 — CLI

```text
commands
options
input formats
list behavior

```

CLI behavior may be used directly by users and automation.

### Priority 4 — Courseware and Generated Artifacts

```text
Course / Week
built-in Generator identities
artifact paths
artifact membership
Courseware Composition
```

Generated layouts may become compatibility-sensitive even when they are not Python APIs.

### Priority 5 — AI and Marketplace

Audit provider-independent AI boundaries and accepted Marketplace contracts.

### Priority 6 — Supporting Public Behavior

```text
configuration
filesystem-visible semantics
exceptions
packaging
console entry point
```

# Part I — Generator SDK

## 12. `generator.sdk`

### Current Classification

**Candidate**

The Plugin SDK was intentionally established as a narrow public façade during Milestone 4.

Milestone 8 must verify the exact public surface before v1.0.

### Audit Questions

- Which symbols are intentionally exported?
- Are all exports covered by public-export tests?
- Are any implementation-only symbols accidentally exposed?
- Are documented import paths canonical?
- Do examples use only supported SDK imports?
- Does Marketplace code accidentally expand the SDK?
- Do built-in Generators require symbols unavailable to third-party authors?
- Are exceptions required by plugin authors exposed intentionally?

### Stable Target

The preferred v1.0 target is:

```text
small
explicit
tested
documented
backward-compatible
```

### Freeze Requirement

A deterministic test should define the complete intended v1.0 export set.

Conceptually:

```python
EXPECTED_V1_PUBLIC_SYMBOLS = frozenset(
    {
        # intentionally supported symbols only
    }
)
```

The audit must derive the actual list from production code rather than from assumptions in this document.

### Release Blocker

Any unexplained public export or missing required public symbol is a release-readiness blocker for SDK freeze.

# Part II — Generator Core Contracts

## 13. Canonical Generator Lifecycle

### Current Classification

**Candidate**

The established lifecycle is:

```text
validate_request
      ↓
plan
      ↓
execute
```

through canonical `BaseGenerator.run()` orchestration.

### Audit Goal

Confirm that this remains the single supported Generator lifecycle.

### Stable Requirements

- validation precedes filesystem mutation;
- planning remains deterministic where inputs are deterministic;
- execution consumes the canonical plan;
- built-in Generators follow the lifecycle;
- third-party Generator expectations are documented;
- no legacy second lifecycle remains supported accidentally.

### Release Blocker

Any built-in or supported third-party path that requires a conflicting execution lifecycle.

- template implementation details not externally promised;
- registry internals;
- parser implementation details;
- filesystem helper internals;
- internal test utilities.

Importability alone does not promote them to public API.

---

## 79. Deferred Areas

Existing deferred Marketplace and AI capabilities remain Deferred.

Additional capabilities discovered during audit should be deferred when:

- they are not necessary for v1.0 correctness;
- their public semantics are not mature;
- implementing them would cause scope expansion;
- they can be introduced compatibly in v1.1+.

---

# Part XVII — Release Blocker Classification

## 80. Contract Release Blockers

A contract-level issue blocks v1.0 freeze when it creates material ambiguity in a promised Stable surface.

Examples:

- undocumented public SDK exports;
- conflicting public import paths;
- two supported Generator lifecycles;
- unstable Entry Point identity;
- CLI behavior documented differently from implementation;
- generated paths changing nondeterministically;
- Stable config keys without defined semantics;
- installed package missing required templates;
- public exception behavior contradicting documentation;
- English and zh-TW documentation disagreeing about support status.

---

## 81. Non-blockers

The following do not automatically block v1.0:

- missing deferred features;
- internal refactoring opportunities;
- optional performance optimization;
- proposed future transactional generation;
- remote Marketplace absence;
- Marketplace CLI absence;
- AI Refactoring Assistant absence;
- advanced AI streaming/tool calling absence;
- cosmetic documentation improvements unrelated to correctness.

## 84. CLI Contract Tests

CLI freeze tests should verify public behavior rather than argparse implementation details.

Prefer testing:

```text
command exists
documented option works
documented input is accepted
invalid input fails
expected Generator is invoked
```

Avoid freezing:

- parser object structure;
- internal helper function names;
- irrelevant help-text whitespace.

---

## 85. Artifact Contract Tests

Where artifact paths become Stable, tests should verify exact canonical paths.

Where content is intentionally flexible, avoid freezing complete generated text unnecessarily.

Freeze semantic structure, not incidental formatting, unless formatting itself is part of the public artifact contract.

# Final Principle

The v1.0 public contract should be smaller than the complete implementation.

OpenProjectLab should promise only what it is prepared to maintain.

```text
Importable does not mean public.
Documented does not mean implemented.
Implemented does not mean Stable.
Stable means intentional, tested, documented, and maintainable.
```

> **Step 8.2 is complete when OpenProjectLab can state precisely what v1.0 users may depend on — and the repository contains enough tests and documentation to protect that promise.**
