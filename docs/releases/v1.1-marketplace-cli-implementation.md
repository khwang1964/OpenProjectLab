## 1. Purpose

This document defines the implementation architecture and delivery gates for
the accepted deterministic-local Marketplace CLI contract. It authorizes
incremental implementation work only after this baseline and its fail-closed
automation are reviewed.

The baseline is documentation and design automation. It does not register the
`marketplace` command family, add command handlers, change Marketplace domain
contracts, or claim that any v1.1.4 command is available.

## 2. Accepted Command Inventory

The production implementation is limited to:

``` text
opl marketplace versions IDENTITY --catalog FILE [--json]
opl marketplace inspect COORDINATE --catalog FILE [--json]
opl marketplace verify COORDINATE --catalog FILE --payload-root DIR [--json]
opl marketplace install COORDINATE --catalog FILE --payload-root DIR
    [--dry-run] [--json]
```

No aliases, short options, implicit catalog discovery, or `opl marketplace
list` command are part of v1.1.4.

The internal repository already supports deterministic global enumeration via
`list_artifacts()`. That internal capability is intentionally outside the
accepted CLI surface and must not leak into parser registration, help output,
JSON schemas, manuals, or demos.

## 3. Architecture

The implementation must remain an adapter over existing Marketplace domain
contracts:

``` text
argparse command family
    ↓
identity / coordinate parsers
    ↓
UTF-8 local catalog loader
    ↓
InMemoryMarketplaceRepository
    ↓
safe local payload acquirer
    ↓
verify_integrity()
    ↓
ArtifactInstaller
    ↓
human or deterministic JSON renderer
```

The CLI adapter may orchestrate these boundaries. It must not duplicate their
domain rules or create a second Marketplace execution model.

### 3.1 Module boundary

The preferred internal structure is:

``` text
generator/cli/marketplace.py
```

This module may contain:

- `add_marketplace_parser(subparsers)`;
- internal identity and coordinate parsers;
- a schema-version-1 catalog loader;
- safe payload-root containment and file acquisition;
- command orchestration;
- human and JSON result rendering;
- Marketplace CLI-specific handled error types when necessary.

`generator/cli/main.py` should only register the command family through the
adapter and preserve its existing top-level error/exit behavior. Large catalog,
filesystem, orchestration, or rendering logic must not be embedded in
`main.py`.

### 3.2 Reused domain boundaries

The implementation must reuse:

- `ArtifactIdentity`, `ArtifactVersion`, and `ArtifactCoordinate`;
- `MarketplaceArtifact` and its nested metadata models;
- `InMemoryMarketplaceRepository.find()` and `available_versions()`;
- `ArtifactAcquirer.acquire()` or a contract-compatible local implementation;
- `verify_integrity()`;
- `ArtifactInstaller.install()` and `ArtifactInstallationResult`.

It must not broaden `generator.marketplace.__all__` or `generator.sdk` merely
to make CLI implementation convenient.

## 4. Parsing and Catalog Rules

Identity and coordinate parsing must be exact and fail closed:

``` text
IDENTITY   = namespace/name
COORDINATE = namespace/name@MAJOR.MINOR.PATCH
```

The parser must reject missing components, extra separators, partial versions,
pre-release/build metadata, path semantics, and non-canonical versions before
catalog lookup or payload access.

The catalog loader must:

- read one explicit `--catalog FILE` as UTF-8 JSON;
- require catalog `schema_version` integer `1`;
- require `artifacts` to be an array;
- construct the existing immutable domain models;
- reject malformed JSON, wrong types, unknown required semantics, and duplicate
  exact coordinates;
- make catalog order irrelevant to command output;
- avoid exporting raw catalog dictionaries as public API.

## 5. Payload Safety

`verify` and `install` require one explicit `--payload-root DIR`. The selected
artifact must use `distribution.kind == "file"`.

Before reading bytes, the adapter must reject:

- absolute references;
- Windows drive-prefixed references;
- `..` traversal;
- references resolving outside the payload root;
- missing paths, directories, symlinks escaping the root, and unsupported
  distribution kinds.

No network fallback is permitted. Lookup, containment, acquisition, and
integrity failures must occur before installation.

## 6. Command Semantics

### 6.1 `versions`

- parse one exact identity;
- call `available_versions()`;
- report deterministic ascending semantic versions;
- return success with an empty result for an unknown identity;
- never acquire, verify, or install.

### 6.2 `inspect`

- perform exact coordinate lookup;
- render canonical artifact metadata;
- never acquire, verify, install, activate, or execute.

### 6.3 `verify`

- find the exact artifact;
- safely acquire local bytes;
- verify declared SHA-256 integrity;
- report digest and payload size;
- never call the installer.

### 6.4 `install`

- complete lookup, safe acquisition, and integrity verification first;
- call the selected installer only after all earlier gates pass;
- keep installation process-local, non-activating, and non-persistent;
- reject duplicate installation without replacing existing payload bytes;
- with `--dry-run`, complete verification but never call `install()`.

## 7. Output and Error Boundary

Human-readable success output goes to stdout. Diagnostics go to stderr.

With `--json`, success emits exactly one UTF-8 JSON object with
`schema_version: 1` and the accepted command-specific fields. JSON encoding
must be deterministic. A handled failure emits no success JSON document.

The accepted broad exit contract remains:

| Exit | Meaning |
| ---: | --- |
| `0` | Successful Marketplace command |
| `2` | Usage, catalog, lookup, acquisition, integrity, installation, filesystem, or other handled operational failure |

No finer Stable exit taxonomy or byte-for-byte diagnostic wording is introduced.

## 8. Failure-before-side-effect Invariants

Tests must prove that installer state is unchanged after:

- invalid CLI identity or coordinate;
- unreadable or malformed catalog;
- unsupported schema or distribution kind;
- duplicate catalog coordinate;
- missing artifact or payload;
- unsafe or escaping payload reference;
- acquisition error;
- integrity mismatch;
- `versions`, `inspect`, `verify`, or `install --dry-run`.

## 10. Test Matrix

Required automation includes:

- parser inventory and exact option shapes;
- identity/coordinate positive and negative cases;
- catalog schema, type, duplicate, and ordering cases;
- safe POSIX and Windows-style payload references;
- symlink/containment cases where supported;
- exact lookup and unknown identity/coordinate behavior;
- SHA-256 success and mismatch;
- installer call ordering and no-partial-state assertions;
- `--dry-run` no-install behavior;
- deterministic human/JSON output and stdout/stderr separation;
- exit `0`/`2` behavior;
- preservation of every v1 command and legacy `opl --list`;
- installed-wheel CLI execution;
- EN/zh-TW documentation functional parity;
- representative executable demo coverage.

The v1.1.3 contract and acceptance suites remain preserved throughout
implementation. Their pre-implementation parser assertions may change only in
the reviewed production-registration slice, together with replacement
implementation assertions.

## 11. Documentation and Demo Impact

Implementation PRs must update both:

``` text
docs/user-guide/en/marketplace.md
docs/user-guide/zh-TW/marketplace.md
```

The two manuals require functional parity rather than literal translation.
They must document exact command syntax, local catalog/payload examples,
`--dry-run`, JSON output, failure boundaries, non-activation, and Deferred
remote/trust/dependency features.

The canonical executable use-case demo remains inside the OPL repository. It
may add Marketplace CLI steps only after production registration and
installed-wheel verification. v1.1.4 does not create a separate demo
repository.

## 12. Explicit Non-goals

The implementation must not add:

- remote/network acquisition or implicit fallback;
- `opl marketplace list`;
- persistent package installation or activation;
- dependency solving, locks, or cache policy;
- signing, publisher identity, trust, or sandboxing;
- ratings, reviews, payments, or monetization;
- plugin discovery/registration or Generator execution;
- new `generator.sdk` exports;
- AI CLI functionality.

## 13. Code Review Checklist

### Architecture

- [ ] The CLI remains an adapter over existing Marketplace contracts.
- [ ] Marketplace logic is isolated from `generator/cli/main.py`.
- [ ] No second repository, integrity, or installation model is introduced.
- [ ] Internal `list_artifacts()` does not become a CLI command.

### Safety and behavior

- [ ] Catalog and coordinate parsing fail closed.
- [ ] Payload containment is validated before reading bytes.
- [ ] Integrity verification completes before installation.
- [ ] Failure and dry-run paths leave installer state unchanged.
- [ ] Human/JSON streams and exit behavior match the accepted contract.

### Tests

- [ ] Focused parser, adapter, integration, and failure-path tests pass.
- [ ] v1/v1.1 public-contract suites remain green.
- [ ] Marketplace domain and representative E2E suites remain green.
- [ ] Installed-wheel execution is verified before formal acceptance.
- [ ] Coverage and local quality gates pass without fabricated exclusions.

### Documentation and demo

- [ ] EN and zh-TW Marketplace manuals have functional parity.
- [ ] Executable examples match the installed CLI.
- [ ] The canonical use-case demo remains in the OPL repository.
- [ ] Deferred capabilities are not presented as implemented.

## 14. Acceptance Gates

v1.1.4 may become Accepted only after:

- every delivery slice is reviewed and merged;
- the exact accepted command family is registered in production;
- focused, regression, coverage, and local quality gates pass;
- installed-wheel Marketplace CLI verification passes;
- EN/zh-TW manual parity and executable documentation tests pass;
- the canonical demo exercises only implemented behavior;
- required CI, squash merge, synchronized-main verification, and terminal
  documentation alignment complete;
- Marketplace CLI implementation acceptance remains distinct from Formal v1.1
  Acceptance.
