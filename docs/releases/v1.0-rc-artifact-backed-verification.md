---

## 1. Purpose

Step 8.10.5 verifies the actual first RC artifacts from an installed-user
perspective.

Step 8.10.4 proved that the repository can build one coherent RC artifact set.
Step 8.10.5 proves that the exact verified wheel can be consumed outside the
source checkout and still satisfy the accepted v1.0 user-facing contracts.

This step answers:

> Does the exact checksum-bound `1.0.0rc1` wheel behave as the accepted
> OpenProjectLab v1.0 Release Candidate when installed and executed as a user
> would consume it?

This is an artifact-backed acceptance gate, not a source-checkout regression
substitute.

---

## 2. Governing Principle

The evidence chain is fail-closed:

```text
Approved source commit
        ↓
Fresh RC artifact set
        ↓
SHA-256 checksum manifest
        ↓
Exact configured RC wheel
        ↓
Clean environment outside source checkout
        ↓
Installed distribution identity
        ↓
Console entry point
        ↓
Packaged runtime resources
        ↓
First 15 Minutes
        ↓
Representative installed-user E2E
```

Required artifact-backed skips do not count as Step 8.10.5 completion
evidence.

## 4. Required Artifact Inputs

A completion-state Step 8.10.5 run requires all four inputs:

```text
OPL_TEST_WHEEL
OPL_TEST_DIST_DIR
OPL_TEST_CHECKSUM_MANIFEST
OPL_RELEASE_COMMIT_SHA
```

Their meanings are:

| Input | Contract |
|---|---|
| `OPL_TEST_WHEEL` | Exact current RC wheel |
| `OPL_TEST_DIST_DIR` | Directory containing the canonical RC wheel + sdist |
| `OPL_TEST_CHECKSUM_MANIFEST` | SHA-256 manifest for the exact artifact set |
| `OPL_RELEASE_COMMIT_SHA` | Full immutable source commit SHA |

Missing inputs may be represented as explicit skips in ordinary source-only
test runs, but **a Step 8.10.5 completion run requires zero required
artifact-backed skips**.

---

## 5. RC Artifact Identity

The required package/release identity is:

```text
Package version: 1.0.0rc1
RC identity:     v1.0.0-rc.1
```

The configured wheel must belong to the configured distribution directory and
must identify:

```text
openprojectlab
1.0.0rc1
```

The distribution directory must contain exactly one current wheel and one
current sdist under the accepted release artifact contract.

---

## 6. Checksum Binding

The checksum manifest must describe the exact wheel and sdist bytes used by
verification.

The manifest must:

- be readable as UTF-8 without introducing checksum data into the digest;
- contain exactly the canonical artifact filenames;
- contain canonical lowercase SHA-256 digests;
- match fresh digest computation;
- fail if either artifact changes after manifest creation.

The wheel installed during Step 8.10.5 must be the same wheel whose bytes are
bound by the manifest.

---

## 7. Source Identity

`OPL_RELEASE_COMMIT_SHA` must:

- be a full 40-character lowercase SHA;
- equal the repository commit used for the current RC build verification;
- remain the source identity associated with both wheel and sdist;
- later be the expected RC tag target if publication proceeds.

Step 8.10.5 does not create the tag.

---

## 8. Source-checkout Isolation

Installed-user evidence must not succeed because the repository checkout is on
`PYTHONPATH`, because of an editable install, or because user-site packages
shadow the tested wheel.

The representative installed-user environment must:

- exist outside the repository checkout;
- install the configured wheel;
- remove repository `PYTHONPATH` influence;
- disable user-site contamination where practical;
- import `generator` from the installed environment;
- prove the installed distribution version is `1.0.0rc1`.

---

## 9. Console Entry Point

The installed wheel must provide the accepted console entry point:

```text
opl = generator.cli.main:main
```

The installed `opl` executable must run from the clean environment and expose
the accepted built-in generator set.

Source-tree invocation does not satisfy this gate.

---

## 10. Packaged Runtime Resources

The RC wheel must carry the package-owned runtime resources accepted in
Step 8.4.

Representative installed generation must succeed without:

- repository-level legacy templates;
- editable installation;
- repository `PYTHONPATH`;
- untracked local resource files.

Successful installed generation is evidence that runtime templates/resources
are consumable from the wheel.

## 16. Failure Rules

Step 8.10.5 fails closed when:

- any required artifact input is missing in the completion run;
- the configured wheel is not the current RC wheel;
- the wheel is outside the configured artifact set;
- the checksum manifest does not match exact artifact bytes;
- source SHA is malformed or inconsistent;
- installed version differs from `1.0.0rc1`;
- source checkout contaminates installed imports;
- installed `opl` is absent or incorrect;
- packaged resources are unavailable;
- First 15 Minutes fails;
- representative installed-user E2E fails;
- any required artifact-backed test remains skipped.

---

## 17. Explicit Non-goals

Step 8.10.5 does not:

- create or move `v1.0.0-rc.1`;

- upload artifacts;
- formally accept the RC;
- accept v1.0.0 GA;

- create a second clean-install framework;
- broaden environment support claims;
- add product capabilities.

## 19. Test Strategy

The Step 8.10.5 test file is a coordination/identity contract.

It should not reimplement the clean venv and installed-user workflow already
owned by existing suites.

Tests are divided into:

### Source-only contract tests

These can run without built artifacts and verify:

- design presence;
- required suite presence;
- required environment-variable contract;
- RC identity constants;
- no-publication boundary.

### Artifact-backed tests

These require the configured RC inputs and verify:

- wheel/dist relationship;
- RC artifact filenames;
- checksum manifest;
- source SHA.

Missing artifact inputs may skip these tests during ordinary source-only runs.
Such skips are not valid Step 8.10.5 completion evidence.
