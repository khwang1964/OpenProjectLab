## 1. Acceptance Purpose

This document records the Step 8.4 acceptance evidence for the
OpenProjectLab v1.0 packaging, installation, and distribution boundary.

Step 8.4 is intended to prove that OPL works from the artifact a user
installs, not merely from a repository checkout or editable development
environment.

The accepted local path is:


## 2. Packaging Defect Closed

Step 8.2 identified a release-readiness risk: repository-level
`templates/` could not be treated as a packaged-resource guarantee until
a real built artifact and clean installation were verified.

The initial Step 8.4 Red Phase confirmed that risk:

``` text
source checkout
    had repository templates

built wheel
    did not own the runtime templates required by installed generators
```

The production fix established package-owned runtime resources:

``` text
generator/
    resources/
        templates/
```

The legacy repository-level runtime template root was removed after
isolation testing demonstrated that source tests, Generator / CLI
integration, and packaging verification no longer depended on it.

`generator/resources/templates/` is now the canonical runtime template
source.

------------------------------------------------------------------------

## 3. Accepted Resource Architecture

The local acceptance state verifies the following architecture:

``` text
generator.resources
    ↓
package_template_root()
    ↓
generator/resources/templates/
    ↓
built-in Generator template resolution
```

The CLI default template root now resolves through the package-resource
boundary rather than a repository-relative `PROJECT_ROOT / "templates"`
path.

Existing explicit template-root override behavior remains preserved.

The migration does not introduce a second Generator lifecycle and does
not change the frozen v1.0 command identities or Generator public
contracts.

## 7. Contract Preservation

Step 8.4 changes packaging/resource ownership, not the frozen public
product surface.

The following remain preserved:

-   v1 CLI command identities;
-   `opl` console entry point;
-   canonical `BaseGenerator.run()` lifecycle;
-   Generator request / plan / result contracts;
-   Plugin SDK / Entry Point contracts;
-   Courseware Domain contracts;
-   Courseware Composition semantics;
-   provider-independent AI contracts;
-   Marketplace contracts;
-   explicit template-root override behavior.

No generalized transaction framework, second Generator lifecycle, or new
public SDK hierarchy was introduced.
