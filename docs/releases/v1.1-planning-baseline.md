## 1. Purpose

This document establishes the governing baseline for OpenProjectLab v1.1.
It selects a deliberately small, backward-compatible direction without
turning every v1.0 Deferred capability into committed work.

The v1.1 theme is:

``` text
Operational CLI Expansion
```

The release extends the existing Stable provider-independent AI and
deterministic Marketplace boundaries through additive CLI workflows. It does
not create a remote Marketplace, generalized package manager, or mandatory
live-provider dependency.

## 2. Governing Principles

All v1.1 work follows:

``` text
Design First
    ↓
Documentation First
    ↓
Automation First
    ↓
Testing / Acceptance
```

The governing compatibility rule remains:

``` text
1.0.x → compatibility-preserving fixes
1.x   → backward-compatible evolution
2.0   → intentional breaking Stable-contract changes
```

## 3. Accepted v1.0 Baseline

The v1.0 lifecycle is terminal and immutable:

``` text
v1.0.0 GA lifecycle --- Completed
Formal v1.0.0 GA Acceptance --- Accepted
Published tag --- v1.0.0
Published artifact/source identity --- Immutable
```

v1.1 must preserve the verified Stable subset frozen by Step 8.2, including:

- the narrow `generator.sdk` façade;
- Generator lifecycle and reviewed request/plan/result semantics;
- Plugin Entry Point, validation, and registration behavior;
- the reviewed v1.0 CLI surface;
- Courseware Domain and Composition behavior;
- provider-independent AI contracts;
- reviewed deterministic Marketplace contracts;
- verified Configuration, Filesystem, and public-error subsets;
- distribution identity, `opl` entry point, and installed resources.

## 4. Compatibility Boundary

v1.1 changes must be additive or otherwise backward compatible. Existing
Stable names, inputs, outputs, artifact layouts, deterministic ordering,
failure boundaries, and installed-user behavior must remain valid.

No Deferred capability becomes Stable merely by appearing in this plan.
Promotion requires an explicit contract decision, implementation, focused
tests, integration evidence, documentation, and compatibility review.

## 5. Committed Scope

The planning baseline commits v1.1 to designing and evaluating these slices:

1. additive Marketplace CLI workflows over the existing deterministic local
   Marketplace contracts;
2. additive AI CLI workflows over the existing provider-independent AI
   boundary;
3. CLI compatibility automation for new commands and failure behavior;
4. EN/zh-TW documentation parity and executable onboarding coverage;
5. built-artifact and installed-user verification on evidence-backed
   environments.

Implementation remains `Not Started` until each dedicated contract slice is
accepted.

## 6. Marketplace CLI Boundary

The Marketplace CLI may expose deterministic local operations such as:

- artifact listing and inspection;
- exact-coordinate lookup;
- acquisition;
- SHA-256 integrity verification;
- deterministic installation results.

It must reuse the existing Marketplace contracts and keep distribution,
validation, acquisition, integrity, installation, activation, and execution as
separate responsibilities.

It must not imply a remote service, public repository hosting, generalized
package manager, automatic Plugin/Generator activation, signing, trust,
dependency solving, ratings, payment, or AI Provider Marketplace.

## 7. AI CLI Boundary

The AI CLI may expose provider-independent request, structured-response
validation, and Courseware-generation workflows.

Normal tests and acceptance must remain deterministic, credential-free, and
network-independent. A fake provider is the canonical core-test boundary.

Live provider invocation remains Experimental and opt-in. Provider SDK types,
credentials, network availability, paid invocation, and provider-specific
operational behavior must not leak into Stable application contracts.

## 8. Explicit Non-goals

The following remain Deferred and are not v1.1 commitments:

- remote Marketplace service or Community Repository hosting;
- real package-manager integration;
- automatic Plugin or Generator activation;
- artifact signing, publisher identity, sandboxing, or trust enforcement;
- general dependency resolution or lock-file/cache policy;
- ratings, reviews, monetization, payment, or AI Provider Marketplace;
- AI Refactoring Assistant;
- streaming or tool calling;
- grading, scoring, submission, or LMS backends;
- PPTX/PDF/HTML slide rendering;
- Website hosting, deployment, CMS, or dynamic runtime;
- generalized cross-Generator transaction rollback.

Removing an item from this list requires a separately reviewed planning
decision; implementation alone is insufficient.

## 9. Network and External-service Boundary

Core verification must not require public network access, external credentials,
paid accounts, remote Marketplace availability, or third-party service
stability. Operational integration tests must be explicitly marked and kept
outside normal deterministic CI unless a later accepted design changes that
boundary.

## 10. Documentation and Support Evidence

Every user-facing v1.1 workflow requires:

- English and Traditional Chinese (Taiwan) functional parity;
- CLI/reference documentation;
- architecture or ADR coverage when a boundary changes;
- CHANGELOG and HISTORY alignment;
- executable First 15 Minutes or representative installed-user verification;
- support-matrix updates only after direct evidence exists.

No new Python version or operating system may be called Supported based only on
expectation or one-off observation.

## 11. Automation Strategy

Planning automation must fail closed. It should verify:

- the accepted v1.0 baseline is preserved;
- Formal v1.1 Acceptance remains `Not Accepted` during planning;
- Marketplace CLI and AI CLI remain `Not Started` before contract approval;
- committed scope and explicit non-goals are present;
- remote Marketplace and live AI are not described as required core behavior;
- EN/zh-TW parity and artifact-backed verification are required gates;
- Roadmap, HISTORY, and CHANGELOG agree on the planning state;
- no future test count, coverage, PR, CI, commit, tag, checksum, or release
  evidence is fabricated.

## 13. Acceptance Gates

Formal v1.1 acceptance eventually requires:

- all committed contract and implementation slices completed;
- v1.0 Stable contract tests preserved;
- focused v1.1 contract, integration, and reliability tests passed;
- EN/zh-TW functional parity passed;
- built wheel and sdist verification passed;
- clean-install and installed-user workflows passed;
- full regression and coverage gate passed;
- local quality gates passed;
- required GitHub Actions / CI passed;
- release identity and post-publication evidence completed;
- formal acceptance PR, merge, main synchronization, and post-merge
  consistency completed.

## 14. Code Review Checklist

- [ ] Affected v1.0 contracts and classifications are identified.
- [ ] Existing Stable v1 behavior remains compatible.
- [ ] No second Generator, Plugin, AI, or Marketplace execution framework is
  introduced.
- [ ] New CLI behavior is additive and deterministic.
- [ ] Failure-before-side-effect boundaries remain explicit.

### Scope

- [ ] Work belongs to the committed v1.1 scope.
- [ ] Deferred items remain Deferred unless separately promoted.
- [ ] Marketplace CLI does not imply remote services or activation.
- [ ] AI CLI does not require live provider access for core verification.
- [ ] No speculative support claim is introduced.

### Tests and Documentation

- [ ] Focused contract tests precede implementation.
- [ ] Integration and failure-path tests are present.
- [ ] EN/zh-TW user-facing documentation remains functionally aligned.
- [ ] Built-artifact behavior is verified where applicable.
- [ ] Roadmap, HISTORY, and CHANGELOG are aligned.
