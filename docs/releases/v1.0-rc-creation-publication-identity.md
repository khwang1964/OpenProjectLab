# OpenProjectLab v1.0 RC Creation / Publication Identity

> **Status:** Design / Contract Definition — In Progress
> **Milestone:** 8 — v1.0 Stabilization & Release Readiness
> **Step:** 8.10.8 — RC Creation / Publication Identity
> **Date:** 2026-08-19
> **Predecessor:** Step 8.10.7 — RC GitHub Actions / CI — Completed
> **Target RC:** `v1.0.0-rc.1`
> **Canonical package version:** `1.0.0rc1`

---

## 1. Purpose

Step 8.10.8 is the first Step 8.10 slice that permits creation of the actual
Release Candidate publication identity.

All prior Step 8.10 slices were pre-publication verification.

This step answers:

> Can the already-verified RC source, tag, artifacts, checksums, and GitHub
> Release be created as one immutable and auditable publication identity?

The step remains fail-closed. A publication identity is valid only when all
components agree.

---

## 2. Required Identity

The first RC has two equivalent representations:

```text
Python package version
    1.0.0rc1

Human-facing release identity
    v1.0.0-rc.1
```

The canonical tag for this RC is exactly:

```text
v1.0.0-rc.1
```

The tag must point to exactly one approved source commit.

---

## 3. Publication Identity Graph

```text
Approved source commit
        ↓
Canonical package version = 1.0.0rc1
        ↓
RC tag = v1.0.0-rc.1
        ↓
Verified wheel + sdist
        ↓
SHA256SUMS.txt
        ↓
GitHub Release draft
        ↓
Identity validation
        ↓
GitHub prerelease publication
```

No later node may silently redefine an earlier identity.

---

## 4. Approved Source Commit

Before creating the tag, the maintainer must identify the exact approved
publication commit.

The source commit must:

- be a full immutable Git SHA;
- be reachable from the synchronized release branch / `main`;
- include all Step 8.10.1–8.10.7 accepted repository changes;
- be the source from which the final RC artifacts are built;
- become the exact target of `v1.0.0-rc.1`.

Floating refs such as `HEAD`, `main`, or `origin/main` are not sufficient as
recorded release evidence.

---

## 5. Final Publication Build

Because Step 8.10.8 may follow a merge that changes the source commit, the
publication artifacts must be freshly rebuilt from the approved publication
commit.

The final publication artifact set must contain exactly:

```text
openprojectlab-1.0.0rc1-py3-none-any.whl
openprojectlab-1.0.0rc1.tar.gz
SHA256SUMS.txt
```

The final build must re-run:

- wheel/sdist build;
- Twine metadata validation;
- artifact-set identity verification;
- wheel metadata verification;
- checksum generation;
- checksum verification;
- required artifact-backed release tests.

Earlier Step 8.10.4 or 8.10.5 artifact bytes are historical evidence and must
not be uploaded if the approved publication source commit has changed.

---

## 6. Tag Creation Contract

The RC tag must be created only after:

- synchronized `main` is confirmed;
- working tree is clean;
- approved publication commit is recorded;
- fresh artifact-backed verification passes;
- Step 8.10.7 CI is green.

Required tag:

```text
v1.0.0-rc.1
```

Required target:

```text
<approved publication commit SHA>
```

If the tag already exists:

- exact matching target may be inspected and reused only if publication has not
  created a conflicting immutable state;
- a different target is a release blocker;
- the tag must not be force-moved.

Published RC tags are immutable.

---

## 7. GitHub Release Draft-first Contract

The GitHub Release must be created as a draft first.

Expected draft identity:

```text
tag              v1.0.0-rc.1
target commit    <approved publication SHA>
prerelease       true
draft            true
```

The draft must reference the same tag and approved commit as the RC identity.

The draft stage is the last safe point for validation before publication.

---

## 8. GitHub Release Assets

The draft Release must contain exactly the verified asset set:

```text
openprojectlab-1.0.0rc1-py3-none-any.whl
openprojectlab-1.0.0rc1.tar.gz
SHA256SUMS.txt
```

No stale `0.6.0` artifact, old RC artifact, duplicate wheel/sdist, or unrelated
distribution may be attached.

Asset filenames are not enough. Their bytes must match the final checksum
manifest.

---

## 9. Checksum Publication Contract

`SHA256SUMS.txt` must describe exactly the uploaded wheel and sdist bytes.

The release is invalid if:

- an uploaded artifact digest differs;
- the manifest contains missing or extra release artifacts;
- the checksum file is regenerated from different bytes after upload;
- an asset is replaced under the same release identity.

The same RC identity must not be used to publish replacement bytes.

---

## 10. RC Prerelease Classification

The GitHub Release must satisfy:

```text
prerelease = true
```

It must not be published as a stable / GA release.

`v1.0.0-rc.1` publication does not authorize `v1.0.0` GA.

---

## 11. Release Title and Notes Boundary

The release title must identify the RC unambiguously.

The release notes must:

- identify this publication as the first v1.0 Release Candidate;
- point users to v1.0 documentation / known limitations as appropriate;
- avoid claiming v1.0 GA acceptance;
- avoid expanding support commitments beyond the accepted support matrix;
- avoid inventing future RC acceptance evidence.

Release-note prose is documentation; tag/artifact/checksum identity remains the
technical authority.

---

## 12. Existing Release Conflict Rules

Existing GitHub state must fail closed when any of the following differs from
the expected publication specification:

- tag;
- target commit;
- release asset names;
- prerelease classification;
- published/draft state where mutation would be unsafe.

An already-published release must never be silently mutated by release
automation.

---

## 13. No Retarget / No Replacement Rule

After publication:

- do not force-move `v1.0.0-rc.1`;
- do not replace wheel bytes;
- do not replace sdist bytes;
- do not replace checksum data while claiming the same artifact identity;
- do not silently delete/recreate the release to change immutable identity.

If a published RC is materially wrong, issue a subsequent RC identity such as:

```text
v1.0.0-rc.2
```

rather than rewriting `v1.0.0-rc.1`.

---

## 14. Abort Boundary

Before final publication, abort Step 8.10.8 if any of these occurs:

- source SHA changes;
- repository becomes dirty;
- tag target mismatch;
- artifact rebuild differs without explanation;
- Twine fails;
- artifact-backed tests fail or require invalid skips;
- checksum verification fails;
- GitHub Release draft conflicts with expected identity;
- required CI evidence is no longer green.

A draft may be deleted/recreated before publication if needed, provided no
published immutable identity has been created and the final state is
revalidated.

---

## 15. Publication Ordering

Required sequence:

```text
sync main
    ↓
record approved publication SHA
    ↓
fresh build
    ↓
twine check
    ↓
artifact identity verification
    ↓
checksum generation / verification
    ↓
artifact-backed verification
    ↓
create tag v1.0.0-rc.1 at approved SHA
    ↓
verify tag target
    ↓
create GitHub Release draft
    ↓
upload exact verified assets
    ↓
validate draft identity
    ↓
publish as prerelease
    ↓
re-read published GitHub state
    ↓
record publication evidence
```

Do not publish before draft identity validation.

## 17. Existing Production Authorities

Step 8.10.8 must reuse:

```text
generator/release/identity.py
generator/release/artifacts.py
generator/release/github_release.py
```

In particular:

- `ReleaseIdentity` owns version/tag/commit coherence;
- artifact contracts own wheel/sdist/checksum coherence;
- `GitHubReleaseSpec` owns expected GitHub Release publication state;
- `validate_existing_github_release()` owns fail-closed comparison with
  existing GitHub Release state.

No second release/publication domain model is required.

---

## 18. Test Strategy

The Step 8.10.8 test file is an offline publication-identity contract.

It verifies:

- governing design exists;
- canonical RC package/tag identity remains fixed;
- GitHub Release spec is draft-first;
- RC is marked prerelease;
- asset set contains wheel, sdist, and checksum manifest exactly;
- publication spec binds one full source SHA;
- published-state mutation is rejected;
- tag/commit/asset/prerelease conflicts are rejected;
- contract explicitly prohibits retargeting and artifact replacement;
- contract requires post-publication identity re-read;
- contract does not pre-accept RC or GA.

Actual tag creation and GitHub Release creation are operational actions after
the contract tests pass.

## 19. Code Review Checklist

### Architecture

- [ ] Existing `generator.release` authorities are reused.
- [ ] No second publication framework is introduced.
- [ ] Step 8.10.8 remains an RC publication slice, not GA acceptance.
- [ ] No product capability is added.

### Source / Tag

- [ ] Approved publication SHA is full and immutable.
- [ ] `v1.0.0-rc.1` points exactly to that SHA.
- [ ] Existing conflicting tag fails closed.
- [ ] No force-retagging is permitted.

### Artifacts

- [ ] Final artifacts are freshly built from the approved publication SHA.
- [ ] Exactly one wheel and one sdist are present.
- [ ] Package version is `1.0.0rc1`.
- [ ] Twine passes.
- [ ] Final checksums match exact uploaded bytes.
- [ ] Stale/replacement artifacts are rejected.

### GitHub Release

- [ ] Release is draft-first.
- [ ] Release is marked prerelease.
- [ ] Tag is `v1.0.0-rc.1`.
- [ ] Target commit matches approved publication SHA.
- [ ] Assets are exactly wheel + sdist + `SHA256SUMS.txt`.
- [ ] Existing published state is never silently mutated.
- [ ] Published state is re-read and verified.

### Evidence / Boundaries

- [ ] Actual final digests are recorded.
- [ ] Actual GitHub Release URL is recorded.
- [ ] Required artifact-backed skips are zero.
- [ ] Step 8.10.8 does not claim formal RC acceptance.
- [ ] Step 8.10.8 does not claim GA acceptance.
- [ ] A defective published RC advances to a new RC identity instead of
      rewriting `rc.1`.

---

## 20. Completion Boundary

Step 8.10.8 completion means:

> `v1.0.0-rc.1` exists as one immutable tag + artifact + checksum + GitHub
> prerelease identity and has been re-verified after publication.

It does **not** mean formal RC Acceptance is complete.

Formal acceptance remains Step 8.10.9.

---

> Publish once, verify twice, and never rewrite an immutable RC identity.
