## 1. Purpose

This document proposes the additive v1.1 AI CLI boundary over the existing
provider-independent AI application services. It defines command shapes,
input and response sources, output, errors, network and credential isolation,
and failure-before-side-effect rules before production implementation begins.

This contract does not register `opl ai`, add handlers, define provider
credentials, invoke a live provider, or claim implementation evidence.

## 2. Governing Sources

The contract is governed by:

- `docs/releases/v1.1-planning-baseline.md`;
- `docs/releases/v1.1-cli-public-contract.md`;
- `docs/architecture/ai-integration.md`;
- `generator.ai.AIRequest`, `AIResponse`, and `AIProvider`;
- `AICourseGenerationService`, `AIReviewService`,
  `AIDocumentationService`, and `AITemplateCompletionService`;
- the existing structured response mappers and domain validation;
- `FakeAIProvider` as the canonical deterministic core-test boundary;
- the accepted v1 CLI public-contract automation.

Provider SDK objects, credentials, and vendor exceptions do not govern the
Stable CLI surface.

## 3. Exact Proposed Command Inventory

The complete proposed command family is:

``` text
opl ai course --request FILE (--response FILE | --provider NAME) [--json]
opl ai review --request FILE (--response FILE | --provider NAME) [--json]
opl ai document --request FILE (--response FILE | --provider NAME) [--json]
opl ai template --request FILE (--response FILE | --provider NAME) [--json]
```

No aliases, short options, implicit default command, or additional AI
subcommand is part of this contract. In particular, this contract does not
invent `opl ai chat`, `opl ai providers`, `opl ai refactor`, `opl ai apply`,
or `opl ai agent`.

## 4. Common Arguments and Conflicts

All four commands use the same common shape:

| Element | Required | Meaning |
| --- | --- | --- |
| `--request FILE` | yes | One explicit UTF-8 JSON request document |
| `--response FILE` | exactly one source | Deterministic local AI response document |
| `--provider NAME` | exactly one source | Explicit Experimental live-provider selection |
| `--json` | no | Emit the accepted machine-readable result document |

`--response` and `--provider` are mutually exclusive, and exactly one is
required. There is no implicit provider, environment-selected provider,
network fallback, or interactive prompt.

Paths must identify readable regular files. Directories, missing paths,
undecodable UTF-8, malformed JSON, and unsupported shapes fail before provider
invocation or result emission.

## 5. Request Document

The common request schema is versioned explicitly:

``` json
{
  "schema_version": 1,
  "instructions": "Produce a structured result.",
  "context": {},
  "response_contract": "courseware.course.v1"
}
```

Rules:

- the root is an object;
- `schema_version` is exactly integer `1`;
- `instructions` is a non-empty string;
- `context` is an object;
- `response_contract` is a non-empty string when present;
- unknown root fields are rejected in v1.1;
- JSON numbers, booleans, strings, arrays, objects, and null values inside
  `context` remain provider-independent input data;
- secrets must not be embedded in the request document.

The handler assigns a command-specific internal task identity rather than
trusting a caller-supplied task:

``` text
course   → courseware.generate
review   → courseware.review
document → documentation.generate
template → template.complete
```

## 6. Deterministic Local Response Source

`--response FILE` is the Stable core execution source. The file is one UTF-8
JSON object representing `AIResponse.content`; CLI-owned metadata identifies
the source as local and deterministic. It is passed through the same
command-specific mapper and domain validation used after provider invocation.

The local path:

- performs no network access;
- reads no credentials or provider configuration;
- invokes no paid account;
- remains deterministic and suitable for normal tests and required CI;
- does not bypass structured response or domain validation.

It is not a mock success switch: invalid content fails normally.

## 7. Experimental Live-provider Source

`--provider NAME` is Experimental and opt-in. It may resolve a separately
configured provider adapter during v1.1.6 implementation, but this contract
does not stabilize:

- provider names or discovery mechanisms;
- model names, endpoints, timeouts, retries, or sampling parameters;
- environment-variable or configuration-key names;
- credential storage or acquisition;
- provider SDK request/response types;
- pricing, quotas, rate limits, or network availability;
- provider-specific diagnostic wording.

Missing provider configuration, authentication, rate limits, timeouts,
unavailability, or invalid responses are handled failures. There is no
fallback from a failed live provider to another provider or to local data.

## 8. Command-specific Results

The commands reuse existing application boundaries:

| Command | Application boundary | Result classification |
| --- | --- | --- |
| `course` | `AICourseGenerationService` | Validated `Course` projection |
| `review` | `AIReviewService` | Structured advisory findings |
| `document` | `AIDocumentationService` | Structured documentation draft |
| `template` | `AITemplateCompletionService` | Structured template context |

Results are advisory or structured domain values only. The AI CLI does not
write generated files, update manifests, mutate a repository, register a
plugin or Generator, execute generated content, commit, push, open a PR, or
activate Marketplace artifacts.

## 9. Output and JSON

Successful human-readable output goes to stdout. Diagnostics go to stderr.
Handled failures emit no successful result on stdout.

With `--json`, success emits exactly one UTF-8 JSON object followed by one
newline. The top-level fields are deterministic:

``` text
schema_version
command
source
result
```

`schema_version` is integer `1`; `command` is one of the four accepted
subcommands; `source` is `local-response` or `live-provider`; and `result` is
the command-specific validated projection. Object keys use deterministic
ordering and collections preserve domain-defined order.

Provider metadata is not included in the Stable result unless a later
contract defines a redacted, provider-independent schema.

## 10. Exit Contract

The preserved broad boundary is:

| Exit | Meaning |
| ---: | --- |
| `0` | Successful validated AI CLI operation |
| `2` | Usage, file, JSON, request, provider, response, mapping, or domain failure |

No finer Stable taxonomy is claimed. Argparse usage diagnostics and handled
operational diagnostics go to stderr.

## 11. Failure-before-side-effect Boundary

Every request file, source choice, response, mapper, and domain invariant is
validated before success is reported. Failure must leave:

- the filesystem unchanged;
- manifests and project configuration unchanged;
- Generator and Plugin registries unchanged;
- Marketplace installer state unchanged;
- no success JSON document on stdout;
- no implicit provider retry or fallback beyond adapter-internal Experimental
  behavior.

## 12. Compatibility and Classification

- The reviewed v1 command inventory remains Stable and unchanged.
- The accepted `marketplace` family remains unchanged.
- The four AI command names and common option shapes are Proposed until this
  contract is accepted and remain unavailable until v1.1.6 implementation.
- Deterministic `--response FILE` behavior is proposed Stable core behavior.
- Live `--provider NAME` behavior is Experimental and opt-in.
- Human-readable wording and provider-specific diagnostics are not Stable.

## 13. Deferred Scope

The following remain Deferred:

- chat or conversational session state;
- provider listing, installation, marketplace, or automatic selection;
- AI Refactoring Assistant and automatic code application;
- streaming, tool calling, agents, memory, RAG, vector databases, or
  fine-tuning;
- filesystem generation, repository mutation, Git operations, or autonomous
  PR workflows;
- grading, scoring, submission, or LMS integration;
- credential persistence and generalized provider configuration schema;
- billing, budgets, quota management, or paid-account guarantees.

## 14. Documentation and Verification Gates

Before AI CLI implementation acceptance:

- exact parser and option-conflict tests must pass;
- local response-file success and every invalid-input path must be covered;
- live-provider tests must use deterministic adapters in normal CI;
- core tests must require no network, credential, or paid account;
- all four mappers and domain failures must be covered;
- stdout, stderr, JSON, exit `0`/`2`, and no-side-effect behavior must be
  executable contracts;
- the v1 and Marketplace CLI contracts must remain green;
- EN and zh-TW manuals must reach functional parity;
- installed-wheel behavior must be verified;
- full regression, coverage, local quality gates, and required CI must pass.

## 15. Acceptance Gates

This proposed contract may be accepted only after:

- the exact four-command inventory and source conflict are reviewed;
- provider independence and credential isolation are preserved;
- deterministic no-network automation passes;
- production `ai` registration remains absent;
- AI CLI implementation remains Not Started;
- trackers agree on the proposed state;
- focused and full regression, coverage, quality, and required CI pass;
- the governing PR merges, `main` synchronizes, post-merge verification
  passes, and a separate terminal documentation alignment completes.
