## 1. Purpose

Step 8.2 defines what OpenProjectLab v1.0 intends to keep compatible.

Step 8.3 asks:

> **Do the frozen v1.0 contracts remain reliable under failure, repetition, boundary input, and partial-progress conditions?**

The goal is not feature expansion. The goal is to harden accepted behavior so expected failures are deterministic, side effects are bounded, and repeated execution does not corrupt user-visible state.

```text
Design First
    ↓
Documentation First
    ↓
Automation First
    ↓
Testing First
    ↓

    ↓

    ↓

```

## 2. Scope

Step 8.3 focuses on:

- Filesystem and write-policy behavior;
- Generator lifecycle failure boundaries;
- Courseware Composition preflight and fail-fast semantics;
- Plugin loading / validation / registration;
- Marketplace lookup / acquisition / integrity / installation;
- AI structured-input and provider-independent failures;
- CLI input and expected operational failures;
- Configuration edge cases;
- representative repeatability and failure-before-side-effect E2E.

## 3. Non-Goals

Step 8.3 must not introduce new product scope merely because a robustness test suggests a possible architecture.

Out of scope unless required to preserve an existing Stable contract:

- cross-Generator rollback;
- generalized multi-file transactions;
- new rollback/staging framework;
- remote Marketplace;
- Marketplace CLI;
- new AI application features;
- AI streaming/tool calling;
- new Generator families;
- new public SDK exports;
- new package-manager semantics;
- new trust/signing infrastructure.

```text
fail-fast
    ≠
transactional rollback
```

# Reliability Risk Model

## 4. Severity

### P0 — Critical
Data loss, security-boundary failure, Stable contract corruption, credential leakage, or a fundamentally unusable release artifact. P0 blocks v1.0.

### P1 — High
Stable operation leaves avoidable partial state, dry-run mutates persistent state, Plugin transactional registration breaks, invalid AI input reaches filesystem mutation, Marketplace integrity failure occurs after installation, or deterministic behavior becomes nondeterministic. P1 normally blocks v1.0.

### P2 — Medium
Inconsistent error conversion, nondeterministic repeated execution, cleanup defects, or edge-case validation drift. P2 requires explicit disposition before RC.

### P3 — Low
Diagnostic robustness and low-risk defensive checks. P3 may be fixed or documented.

### Deferred
Outside the frozen v1.0 contract and safely introducible in v1.1+.

# Reliability Principles

## 5. Failure Before Avoidable Side Effects

```text
invalid request
    ↓
no planning/execution side effect

missing composed Generator
    ↓
no Generator executes

integrity mismatch
    ↓
no installation

invalid AI response
    ↓
no Courseware/filesystem mutation
```

## 6. Preserve Existing State on Failed Writes

A failed overwrite must not silently destroy the previous file. The current filesystem uses a temporary file followed by replacement; tests should verify the external reliability property without freezing temporary-file naming.

## 7. Dry-Run Is Side-Effect Free

Dry-run may calculate, validate, and report, but must not persist files, directories, manifests, or related state.

## 8. Determinism

Equivalent deterministic inputs should preserve ordering, artifact destinations, status calculation, composition execution order, and other already-contractual output.

## 9. Specific Failure Types

Prefer the narrowest production-defined exception type. Avoid blanket `pytest.raises(Exception)` when a specific error is known.

## 11. Step 8.3.2 — Filesystem / Write-Policy Hardening

Initial test:

```text
tests/core/test_v1_filesystem_reliability.py
```

Coverage:

- destination-is-directory rejection;
- dry-run does not create parent directories;
- CREATE_ONLY preserves existing content on rejection;
- SKIP_EXISTING preserves existing content;
- identical overwrite returns UNCHANGED;
- failed atomic replacement preserves existing content;
- failed atomic replacement removes temporary file where practical;
- Unicode and empty-content writes remain valid;
- nested destination creation;
- remove-file dry-run non-persistence;
- strict missing remove raises `FileSystemError`.

Use deterministic failure injection instead of OS-permission behavior as the primary proof.

## 12. Step 8.3.3 — Generator Lifecycle Hardening

Initial test:

```text
tests/generators/test_v1_generator_reliability.py
```

Required behavior:

```text
validate fails
→ plan not called
→ execute not called

plan fails
→ execute not called

execute fails
→ original exception propagates
```

Also verify deterministic repeated successful execution without adding new `GeneratorState` promises.

## 13. Step 8.3.4 — Courseware Composition Hardening

Initial test:

```text
tests/courseware/test_v1_composition_reliability.py
```

Required behavior:

- resolve all Generator classes before execution;
- missing Generator raises `PluginError`;
- failure in Generator N prevents Generator N+1;
- successful work before Generator N is not falsely rolled back;
- identified exception preserves original type;
- anonymous exception is wrapped with Generator context;
- wrapped failure preserves original cause;
- execution/result ordering stays deterministic.

```text
preflight resolution
    ↓
sequential execution
    ↓
fail fast
```

not cross-Generator transactionality.

## 16. Step 8.3.7 — Representative Reliability E2E

Planned:

```text

```

Representative cases:

```text
valid input → generate → repeat → stable semantics
invalid input → validation failure → no unexpected persistent state
A succeeds → B fails → C does not execute
```

Do not assert rollback of A.

# Architecture Constraints

## 17. Generator Boundary

Canonical lifecycle remains `validate_request → plan → execute`.

## 18. Filesystem Boundary

Shared filesystem behavior remains the source of write semantics; avoid Generator-specific write rules.

## 19. Plugin Boundary

Existing transaction direction remains `load → validate → preflight → register`. Do not restore the legacy PluginManager.

## 20. AI Boundary

```text
AI proposes.
Domain validates.
Generator plans.
Filesystem commits.
```

## 21. Marketplace Boundary

```text
Marketplace distributes.
Contracts validate.
Existing OPL pipelines execute.
```

Installation remains separate from activation.

# Test Strategy

## 22. Test Types

Use focused edge tests, deterministic injected failures, representative integration tests, repeatability tests, negative-path tests, and final full regression.

Avoid public network, paid APIs, developer-local state, timing dependence, and OS permission behavior as the sole failure proof.

## 23. Failure Injection

Preferred techniques:

- test Generator subclasses raising specific exceptions;
- monkeypatching replace/copy boundaries;
- fake providers;
- in-memory Marketplace implementations;
- controlled malformed fixtures.
