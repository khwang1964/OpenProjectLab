## 1. Purpose

Step 8.5 defines the documentation contract for OpenProjectLab v1.0.

The objective is not merely to increase documentation volume. The
objective is to make the frozen and verified v1.0 product understandable
and usable from the perspective of an installed user.

The v1.0 documentation must be:

-   aligned with the frozen v1.0 public contracts;
-   usable without relying on a developer checkout;
-   available as formal English and Traditional Chinese (Taiwan) User
    Manuals;
-   functionally equivalent across the two languages;
-   explicit about concepts as well as commands;
-   executable where practical;
-   protected against structural and behavioral documentation drift by
    automation.

Step 8.5 follows the Milestone 8 feature-freeze boundary. Documentation
work must describe the verified product. It must not silently promote
experimental, internal, deferred, or unimplemented architecture into a
Stable v1.0 promise.

## 2. Governing Principles

### 2.1 Design First

Define information architecture, ownership boundaries, parity rules,
automation, and acceptance criteria before bulk User Manual authoring.

### 2.2 Documentation First

User-facing behavior must be explainable through a coherent
documentation model. If a Stable v1.0 capability cannot be documented
accurately, treat that as a release-readiness finding rather than
inventing behavior.

### 2.3 Automation First

Mechanically verifiable guarantees should be automated. At minimum Step
8.5 should automate required chapter presence, EN/zh-TW structural
parity, deterministic internal-link checks where practical, and the
First 15 Minutes onboarding smoke path.

### 2.4 Installed-User First

Step 8.4 established that release validation must exercise the artifact
users install. Quick Start and executable documentation must not depend
on editable installation, repository-only runtime resources,
`PYTHONPATH`, untracked files, or developer-checkout assumptions.

### 2.5 Contract Accuracy Before Completeness

Documentation must distinguish verified behavior from proposed behavior
and must not turn unimplemented architecture into a v1.0 guarantee.

## 5. Documentation Ownership

-   Repository `README.md` is an entry point, not a duplicate full
    manual.
-   `docs/user-guide/en/` and `docs/user-guide/zh-TW/` own user-facing
    v1.0 guidance.
-   ADRs and architecture documents remain engineering sources of truth
    for design decisions.
-   `docs/releases/` owns release-readiness contracts, acceptance
    evidence, and later compatibility/support/release policy documents.

## 6. Bilingual Documentation Contract

English and Traditional Chinese (Taiwan) are both formal v1.0
documentation surfaces.

Functional parity means equivalent user capability, not
sentence-for-sentence translation.

For every required chapter:

-   the corresponding file exists in both roots;
-   the same Stable v1.0 capabilities are covered;
-   documented CLI commands represent the same command surface;
-   examples represent equivalent workflows;
-   user-visible warnings and limitations appear in both;
-   navigation exposes equivalent major topics;
-   neither language introduces a stronger compatibility/support
    promise.

The zh-TW manual should use natural Taiwan technical terminology while
preserving canonical command names, option names, module/type names,
Entry Point names, paths, configuration keys, and artifact identifiers.

## 7. Concepts Contract

Both manuals must contain a Concepts chapter explaining, at a
user-appropriate level:

-   OpenProjectLab as a project engineering / generation platform;
-   Generator responsibilities and canonical lifecycle concepts;
-   request, validation, planning, execution, and result where relevant;
-   built-in Generator families;
-   package-owned runtime resources;
-   Course / Week and courseware concepts;
-   Plugin SDK / Entry Point extension model;
-   provider-independent AI integration boundary;
-   Marketplace artifact / installation boundary;
-   Stable versus non-Stable behavior where Step 8.2 classification
    matters.

Internal implementation details must not become required user knowledge
unless they are part of the frozen public contract.

## 8. Installation Contract

Installation documentation must be consistent with Step 8.4 and describe
an installed-artifact path rather than editable installation as the
primary user workflow.

The documented path must support:

``` text
install artifact
    ↓
import generator
    ↓
resolve package-owned runtime resources
    ↓
invoke opl
    ↓
run a representative workflow
```

Developer installation may be documented separately and clearly labeled.

## 9. First 15 Minutes / Quick Start Contract

Quick Start is a release-readiness workflow, not merely prose.

Representative flow:

``` text
fresh environment
    ↓
install OPL
    ↓
verify CLI availability
    ↓
inspect available generators
    ↓
run one representative generation workflow
    ↓
inspect the generated artifact
```

Exact commands and expected artifacts must be derived from the frozen
v1.0 CLI and Generator contracts during implementation; this governing
contract does not invent unverified commands.

The workflow must be automated to the extent practical and must not rely
on repository root, editable installation, hidden developer environment
variables, or pre-existing generated files.

## 10. CLI and Generator Documentation

The CLI chapter must document the verified v1.0 command surface only.
For documented commands it should cover purpose, invocation, required
arguments, important options, representative examples, expected results,
and user-relevant failure behavior.

Generator documentation must preserve the canonical lifecycle and
explain identities, inputs, validation, planning, execution, generated
artifacts, and user-visible dry-run/overwrite behavior where applicable.
Examples must not bypass the canonical lifecycle.

## 11. Courseware, Plugins, AI, and Marketplace

Courseware documentation must reflect the verified Course/Week Domain
and Composition semantics and must not imply generalized rollback beyond
established fail-fast behavior.

Plugin documentation must describe the established extension boundary:

``` text
third-party distribution
    ↓
openprojectlab.generators Entry Point
    ↓
discovery / loading
    ↓
validation
    ↓
registry
```

AI documentation must remain within the verified provider-independent
boundary and preserve Experimental classification where applicable.

Marketplace documentation must describe only implemented/verified v1.0
behavior and must not imply deferred capabilities such as a public
remote marketplace, community hosting, generalized dependency solving,
ratings/reviews, or monetization.

## 12. Troubleshooting and Upgrading

Troubleshooting should use a consistent pattern: observable symptom →
documented cause → diagnostic check → corrective action →
reference/escalation path.

The v1.0 upgrading chapter must remain conservative. It may document
version identification, supported reinstall/replacement procedures, and
existing migration information, but must not define
compatibility/deprecation guarantees owned by Step 8.6.

## 13. Documentation Automation Architecture

Recommended test ownership:

``` text
tests/documentation/
├── test_user_manual_structure.py
├── test_user_manual_parity.py
├── test_user_manual_links.py
├── test_documented_cli_contract.py
└── test_first_15_minutes.py
```

Exact filenames may change, but responsibilities must remain explicit.

Structural tests verify both roots, required chapters, navigation entry
points, and paired-file symmetry.

Parity tests should compare normalized contracts rather than translated
prose. Candidate parity keys include chapter IDs, documented command
names, Generator identifiers, required workflow IDs, warning/limitation
IDs, and navigation targets.

Internal links should be checked deterministically where practical.
External-link availability should not become a flaky mandatory CI
dependency without a deterministic strategy.

Executable documentation tests must use Stable v1.0 behavior and
controlled temporary directories. The First 15 Minutes workflow is the
minimum required executable path.

## 14. CI Contract

Step 8.5 is not complete when documentation passes only locally.

GitHub Actions must run deterministic documentation checks:

``` text
checkout
    ↓
install required dependencies
    ↓
verify manual structure
    ↓
verify EN / zh-TW parity
    ↓
validate deterministic internal links
    ↓
execute documentation smoke tests
    ↓
execute First 15 Minutes workflow
```

Where onboarding specifically verifies installed-user behavior, CI
should use the built artifact or reuse the Step 8.4
artifact-verification boundary rather than substituting editable
installation.

## 16. Documentation Source-of-Truth Rules

When authoring the manuals, use this precedence:

``` text
Accepted v1.0 public contract / acceptance evidence
    ↓
current production implementation
    ↓
automated tests
    ↓
accepted ADR / architecture documentation
    ↓
historical documentation
```

Historical documentation is context, not authority over current accepted
behavior. If sources disagree, record and resolve the inconsistency
through the appropriate contract owner rather than silently selecting a
convenient statement.

# Final Principle

> Document the product we ship. Test the instructions users follow. Keep
> both languages functionally equivalent.

Step 8.5 is complete only when an installed v1.0 user can learn and
execute the documented representative workflow from either formal User
Manual, and CI can detect material documentation drift.
