## 1. Purpose

This document defines the release-automation and reproducibility
contract for OpenProjectLab v1.0.

The goal of Step 8.8 is not merely to produce a wheel or create a GitHub
Release. The goal is to make a release a controlled, auditable,
repeatable, and internally consistent operation.

For a v1.0 release, the following identities must describe the same
release:

``` text
Canonical Version
        ↕
Source Commit SHA
        ↕
Git Tag
        ↕
Built Artifacts
        ↕
Artifact Checksums
        ↕
GitHub Release
```

A release is valid only when these identities are mutually consistent
and the required verification gates pass.

Step 8.8 therefore establishes:

-   the canonical release identity;
-   version / commit / tag consistency rules;
-   artifact build and integrity rules;
-   GitHub Release consistency rules;
-   clean-install and installed-user verification;
-   reproducibility expectations;
-   the maintainer release procedure;
-   failure, abort, correction, and recovery rules;
-   automation ownership and permission boundaries;
-   contract tests and acceptance criteria.

------------------------------------------------------------------------

## 2. Governing Principles

OpenProjectLab release engineering follows the project-wide principles:

``` text
Design First
Documentation First
Automation First
Evidence First
Fail Closed
```

For release work these mean:

### 2.1 Design First

The release contract is defined before release automation is
implemented.

Automation must implement this document rather than invent release
policy implicitly inside workflow YAML or shell commands.

### 2.2 Documentation First

A maintainer must be able to understand the release procedure, required
inputs, expected outputs, failure behavior, and recovery path without
reverse-engineering CI.

### 2.3 Automation First

Any release invariant that can be checked mechanically should be checked
mechanically.

Manual inspection may supplement automation but must not replace a
reliable machine-checkable invariant.

### 2.4 Evidence First

A release claim must be backed by evidence produced by the release
workflow or by an explicitly documented maintainer verification step.

### 2.5 Fail Closed

If release identity, artifacts, checksums, tests, installation
verification, or publication consistency cannot be established, the
release must stop.

The release process must not "best effort" its way through an
inconsistent state.

## 4. Release Identity Contract

A release has one logical identity.

The identity tuple is:

``` text
ReleaseIdentity(
    version,
    commit_sha,
    tag,
    artifacts,
    checksums,
    github_release
)
```

Every member must refer to the same release state.

### 4.1 Required Invariants

For a valid release:

``` text
canonical version == artifact version
canonical version == tag-derived version
tag target == approved release commit
GitHub Release tag == release tag
GitHub Release artifacts == verified build artifacts
published checksums == checksums of attached artifacts
```

No component may silently disagree with another.

### 4.2 No Floating Release Identity

A release must not depend on a floating branch name such as `main` as
its final identity.

`main` may be the source branch used to select the release commit, but
the release itself must bind to an immutable commit SHA and release tag.

------------------------------------------------------------------------

## 5. Canonical Version Source

OpenProjectLab must have exactly one authoritative mechanism for
determining the package/release version.

Step 8.8 automation must discover and validate the repository's actual
canonical version source before release publication.

The release workflow must not maintain a second independent version
value inside workflow YAML, shell scripts, release notes, or manual
commands.

### 5.1 Version Consistency

The resolved version must agree with:

-   built wheel metadata;
-   source-distribution metadata;
-   release tag;
-   GitHub Release identity;
-   any user-visible version command or package metadata that is part of
    the frozen public surface.

### 5.2 Version Changes

A release version change must be reviewable as repository state.

A maintainer must not be required to edit a hidden CI-only version
variable to create the release.

------------------------------------------------------------------------

## 6. Release Candidate and GA Versioning

Step 8.8 must distinguish release-candidate identity from general
availability identity.

Conceptually:

``` text
v1.0.0 release candidate
        ↓
verification
        ↓
v1.0.0 general availability
```

The exact version syntax must follow the repository's canonical
packaging rules and must be validated by automation.

### 6.1 RC Rules

A release candidate:

-   is not equivalent to the final GA release;
-   must be identifiable as a pre-release;
-   must bind to an immutable commit;
-   must use artifacts built for that RC identity;
-   must not reuse GA artifact names while containing different bytes;
-   may be discarded if verification fails.

### 6.2 GA Rules

The GA release:

-   must use the final approved v1.0 version;
-   must bind to the approved GA commit;
-   must use freshly verified GA artifacts;
-   must not silently reuse an RC artifact if the source identity
    differs;
-   must satisfy all required Step 8.8 and later release-readiness
    gates.

------------------------------------------------------------------------

## 7. Git Tag Contract

The release tag is an immutable identity boundary.

### 7.1 Tag Requirements

A release tag must:

-   encode the canonical release version using the repository's chosen
    naming convention;
-   point to exactly one approved release commit;
-   be created only after required pre-tag verification passes;
-   not be moved to another commit after publication;
-   agree with the GitHub Release tag.

### 7.2 Tag Verification

Automation must verify at least:

``` text
expected version
expected tag
tag exists or is intentionally about to be created
tag target commit
current release commit
version/tag agreement
```

### 7.3 Incorrect Tag

If a tag is created incorrectly and has not been publicly released, the
maintainer must stop and follow the documented correction procedure.

If an incorrect tag has already become part of a public release, the tag
must not be silently moved. A corrective release or other explicitly
documented recovery path is required.

------------------------------------------------------------------------

## 8. Commit SHA Contract

Every release must record the exact source commit SHA.

The SHA provides the immutable source identity from which artifacts were
built.

### 8.1 Required SHA Evidence

Release evidence must make it possible to answer:

``` text
Which exact commit produced this release?
```

without inference from branch history.

### 8.2 Clean Source State

Release automation must operate from a clean, committed repository
state.

Uncommitted local modifications must never become an implicit part of an
official release artifact.

### 8.3 Main Synchronization

Before a maintainer initiates the final release flow, the local
repository must be synchronized with the intended remote release state.

Where `main` is the approved release source:

``` text
HEAD == main == origin/main
working tree == clean
```

must be verified before release execution.

------------------------------------------------------------------------

## 9. Artifact Contract

The v1.0 release artifact set must be explicit.

At minimum, where supported by the repository's packaging contract:

``` text
wheel
source distribution
checksum manifest
```

The exact artifact set must be derived from the actual packaging
configuration and Step 8.4 packaging contract.

### 9.1 Build Isolation

Release artifacts must be built through the documented packaging
mechanism, not assembled manually.

The build should start from a clean output state so stale files cannot
be mistaken for current release artifacts.

Conceptually:

``` text
clean build/dist state
        ↓
build
        ↓
enumerate produced artifacts
        ↓
inspect metadata
        ↓
verify installability
        ↓
generate checksums
```

### 9.2 Artifact Metadata

Automation must inspect built artifact metadata and verify that it
agrees with the canonical release identity.

At minimum:

-   project/package name;
-   version;
-   expected artifact type;
-   metadata readability;
-   absence of unintended stale artifacts.

### 9.3 Artifact Set Must Be Deterministic in Meaning

The workflow must know which files constitute the release.

A glob that accidentally collects artifacts from an earlier build is not
an acceptable release contract.

------------------------------------------------------------------------

## 10. Checksum and Integrity Contract

Every published binary/source release artifact must have an integrity
checksum.

A cryptographic checksum such as SHA-256 should be generated from the
exact bytes that are attached or published.

### 10.1 Checksum Invariants

``` text
checksum generated after final build
checksum corresponds to final artifact bytes
checksum manifest names exact release artifacts
GitHub Release receives the same verified artifacts
```

If an artifact changes, its checksum must change and the release
verification must be repeated.

### 10.2 No Post-Verification Mutation

Artifacts must not be modified after checksum generation and then
published under the old checksum.

------------------------------------------------------------------------

## 11. Clean-install Verification

Release artifacts are not accepted merely because they can be built.

They must be installable and usable as installed-user artifacts.

Step 8.8 builds on the wheel-backed verification established earlier in
Milestone 8.

### 11.1 Required Model

``` text
build release artifact
        ↓
create isolated clean environment
        ↓
install artifact
        ↓
exercise supported entry points
        ↓
run release smoke / contract verification
```

### 11.2 `OPL_TEST_WHEEL`

Where the repository uses `OPL_TEST_WHEEL` for installed-artifact tests,
release automation must point it at the exact wheel produced by the
current release build.

It must not resolve to an older wheel left in `dist/`.

### 11.3 Installed-user Boundary

A source-checkout success does not substitute for clean-install success.

Release verification must exercise the artifact in the way a supported
user receives it.

------------------------------------------------------------------------

## 12. GitHub Release Contract

A GitHub Release is a publication record for an already verified release
identity.

It is not the place where release identity is invented.

### 12.1 Required Consistency

The GitHub Release must agree with:

-   canonical version;
-   release tag;
-   tag target commit;
-   release artifacts;
-   artifact checksums;
-   release notes for the same release.

### 12.2 Release Assets

Only artifacts that passed the release verification pipeline may be
attached.

A maintainer must not manually substitute locally rebuilt files after CI
verification without rerunning the required verification.

### 12.3 Draft-first Publication

Where supported by the implementation, a draft-first model is preferred:

``` text
verified release identity
        ↓
draft GitHub Release
        ↓
attach verified artifacts/checksums
        ↓
verify release contents
        ↓
publish
```

This reduces the chance of exposing a partially assembled release.

------------------------------------------------------------------------

## 13. Release Notes Contract

Release notes must describe the same version represented by the release
tag and artifacts.

They should reference the governing v1.0 release documentation rather
than silently redefining support or compatibility policy.

Release notes must not:

-   advertise unsupported environments;
-   promote Experimental behavior to Stable;
-   omit material Known Limitations when doing so would misrepresent
    v1.0;
-   claim Deferred functionality;
-   redefine compatibility or deprecation guarantees.

The canonical support and limitation sources remain:

``` text
docs/reference/support-matrix.md
docs/releases/v1.0-known-limitations.md
docs/releases/v1.0-compatibility-deprecation-policy.md
```

------------------------------------------------------------------------

## 14. Reproducibility Contract

For Step 8.8, reproducibility means that the release can be
reconstructed from documented source identity, build inputs, and release
procedure with predictable semantic output.

Two levels must be distinguished.

### 14.1 Semantic Reproducibility

Required for v1.0.

A rebuild from the same approved source identity and supported build
process must reproduce:

-   the same project identity;
-   the same version;
-   the same expected artifact types;
-   equivalent package metadata;
-   equivalent installed behavior;
-   the same release contract results.

### 14.2 Byte-for-byte Reproducibility

Byte-identical artifacts are stronger than semantic reproducibility.

Step 8.8 must not claim byte-for-byte reproducibility unless automation
actually proves it.

Timestamps, archive ordering, build-backend behavior, generated
metadata, or other nondeterministic build inputs may prevent byte
equality even when the release is semantically reproducible.

If byte reproducibility is not demonstrated, it is a non-claim rather
than a release failure unless a later policy explicitly requires it.

------------------------------------------------------------------------

## 15. Rebuild Verification

The release process should provide an automated verification path that
can rebuild from the release source identity and compare the result
against the release contract.

At minimum, rebuild verification should compare:

``` text
package name
version
artifact types
metadata contract
installability
supported smoke behavior
```

If byte-for-byte comparison is implemented, it must be reported
separately from semantic reproducibility.

------------------------------------------------------------------------

## 16. Release Workflow Architecture

The intended release pipeline is:

``` text
Maintainer selects approved release commit
        ↓
Preflight repository-state verification
        ↓
Resolve canonical version
        ↓
Validate version / tag / commit relationship
        ↓
Clean build outputs
        ↓
Build release artifacts
        ↓
Inspect artifact metadata
        ↓
Run clean-install / installed-user verification
        ↓
Run required regression / release checks
        ↓
Generate checksums
        ↓
Create / verify release tag
        ↓
Create draft GitHub Release
        ↓
Attach exact verified artifacts + checksums
        ↓
Verify GitHub Release consistency
        ↓
Publish
        ↓
Post-release verification
```

Implementation may split these responsibilities across jobs or
workflows, but the logical ordering and invariants must remain intact.

------------------------------------------------------------------------

## 17. Preflight Contract

Before irreversible publication actions, automation must verify the
release preconditions.

Preflight should fail if any required condition is false.

Candidate checks include:

``` text
working tree / source state is valid
release commit is explicit
canonical version resolves
version is release-appropriate
expected tag is derivable
tag does not conflict with another commit
required governing files exist
required tests / gates are available
build tooling is available
release credentials/permissions are sufficient
```

Publication must not begin if preflight fails.

------------------------------------------------------------------------

## 18. Separation of Verification and Publication

Verification and publication are different trust boundaries.

Whenever practical:

``` text
build + verify
```

should occur before:

``` text
tag + publish
```

The workflow must minimize irreversible actions before all feasible
checks have passed.

This is especially important for:

-   immutable tags;
-   public GitHub Releases;
-   externally published package artifacts.

------------------------------------------------------------------------

## 19. Maintainer Release Procedure

The maintainer-facing procedure must be documented and
automation-backed.

The expected high-level sequence is:

### Phase A --- Prepare

1.  synchronize the approved release branch;
2.  verify a clean working tree;
3.  verify Step 8.8 prerequisites;
4.  verify version/release notes/support documentation;
5.  identify the exact release commit.

### Phase B --- Verify

1.  resolve canonical version;
2.  derive expected tag;
3.  build artifacts from clean state;
4.  inspect artifact metadata;
5.  configure wheel-backed verification;
6.  run required tests and release checks;
7.  generate checksums;
8.  record evidence.

### Phase C --- Publish

1.  create or validate release tag;
2.  create draft GitHub Release;
3.  attach exact verified artifacts;
4.  attach checksum manifest;
5.  verify release metadata and assets;
6.  publish only after consistency checks pass.

### Phase D --- Post-release

1.  verify the public tag;
2.  verify GitHub Release identity;
3.  verify downloadable artifact/checksum agreement;
4.  perform any required clean-install smoke check;
5.  record release outcome;
6.  synchronize repository documentation if publication creates new
    evidence.

The detailed commands must be documented when the implementation path is
finalized.

------------------------------------------------------------------------

## 20. Failure and Abort Policy

Release automation must define safe stopping points.

### 20.1 Before Tag Creation

If verification fails before a tag is created:

``` text
abort
fix repository/workflow
rerun from clean state
```

No public release correction is required because publication has not
begun.

### 20.2 After Tag, Before Public Release

If a tag exists but the GitHub Release has not been published, stop
publication and follow the documented tag-correction policy.

A tag must never be silently repointed after it has become part of a
public release.

### 20.3 After Public Release

If a published release is materially incorrect:

-   do not overwrite history silently;
-   preserve auditability;
-   document the issue;
-   use a corrective release/version where appropriate;
-   update release notes or Known Limitations when the correction is
    documentary rather than binary;
-   follow compatibility/deprecation policy for user-visible
    corrections.

------------------------------------------------------------------------

## 21. Rollback Semantics

"Rollback" must not imply that a public immutable release can simply be
erased.

Step 8.8 distinguishes:

``` text
workflow abort
draft release deletion/correction
unpublished tag correction
published release correction
corrective follow-up release
```

Each has different consequences.

The maintainer documentation must use precise terminology.

------------------------------------------------------------------------

## 22. Permissions and Credential Boundary

Release publication requires stronger permissions than ordinary CI.

The release workflow must use the minimum permissions necessary.

### 22.1 Principles

-   verification jobs should not require publication credentials;
-   secrets must not be exposed to untrusted pull-request execution;
-   publication permissions should be scoped to the release job;
-   workflow permissions should be explicit rather than relying on broad
    defaults;
-   a failed verification job must prevent publication jobs from
    running.

### 22.2 Human Authorization

If the repository uses a protected environment, approval gate, or
equivalent mechanism for publication, Step 8.8 automation should
preserve that boundary.

Automation should reduce manual error without removing intentional
release authorization.

------------------------------------------------------------------------

## 23. CI Workflow vs Release Workflow

Normal CI and release automation have related but distinct
responsibilities.

### CI owns

-   pull-request quality gates;
-   routine regression testing;
-   lint / format / pre-commit checks;
-   packaging verification appropriate to ordinary development;
-   deterministic contract tests.

### Release automation owns

-   immutable release identity;
-   version / tag / SHA agreement;
-   final release artifact set;
-   checksums;
-   release-specific clean-install verification;
-   GitHub Release assembly;
-   publication consistency;
-   post-release verification.

Release automation may reuse CI components, but must not assume that a
normal CI pass alone constitutes a release.

## 24. Automation Architecture

Step 8.8 should prefer small, testable release primitives over one
opaque script.

Conceptually:

``` text
resolve_release_identity()
validate_release_identity()
build_release_artifacts()
inspect_release_artifacts()
verify_clean_install()
generate_checksums()
validate_tag_binding()
assemble_release()
verify_release_assets()
```

The exact implementation language and module structure should follow the
repository's established conventions.

Business rules should be testable without requiring a real public
release.

------------------------------------------------------------------------

## 25. Idempotency

Safe release operations should be idempotent where practical.

Repeated verification must not create duplicate releases or mutate
release identity.

Publication steps that are inherently non-idempotent must detect
existing state and fail safely rather than creating ambiguity.

Examples:

``` text
existing tag points to expected SHA
    → validation may succeed

existing tag points to different SHA
    → fail

existing GitHub Release matches expected identity
    → verify / report

existing GitHub Release conflicts with expected identity
    → fail
```

## 26. Auditability and Evidence

Step 8.8 must leave enough evidence to reconstruct what happened.

Evidence should include, as applicable:

-   canonical version;
-   source commit SHA;
-   tag;
-   workflow/run identity;
-   artifact names;
-   checksums;
-   verification results;
-   regression result;
-   coverage result;
-   clean-install result;
-   GitHub Release identity;
-   publication outcome.

The evidence must be understandable without relying solely on transient
terminal output.

## 28. Version / Tag / Commit Contract Tests

Tests must verify at least:

-   canonical version can be resolved;
-   expected release tag is derived deterministically;
-   version and tag agree;
-   tag target and release commit must agree;
-   a conflicting existing tag is rejected;
-   a release cannot use an unspecified/floating source identity;
-   release identity does not depend on an unrelated manual version
    value.

Where GitHub access would make a unit test nondeterministic, the pure
validation logic must be separated from the external API call.

------------------------------------------------------------------------

## 29. Artifact Contract Tests

Tests must verify at least:

-   expected artifact types are produced;
-   artifact metadata contains the expected project/version;
-   stale artifacts cannot silently enter the release set;
-   the selected wheel is the current build artifact;
-   checksum generation covers every release artifact;
-   checksum verification detects modified artifact bytes;
-   clean-install verification uses the built artifact rather than the
    source checkout.

Step 8.4 packaging tests should be reused where appropriate instead of
duplicated without reason.

------------------------------------------------------------------------

## 30. GitHub Release Contract Tests

Tests should verify the release assembly logic without requiring
publication during ordinary test execution.

At minimum:

-   release tag must equal expected tag;
-   release title/version identity must be consistent;
-   only verified artifacts may become release assets;
-   checksum manifest must correspond to those assets;
-   conflicting existing release state fails closed;
-   publication cannot run if verification has failed.

External GitHub API integration may be tested through controlled
automation, but ordinary local tests should remain deterministic.

------------------------------------------------------------------------

## 31. Reproducibility Contract Tests

Tests must distinguish semantic reproducibility from byte
reproducibility.

Required semantic checks should cover:

-   same source identity resolves same release version;
-   repeated clean builds produce the expected artifact classes;
-   rebuilt metadata remains contract-equivalent;
-   rebuilt artifact remains clean-installable;
-   supported smoke behavior remains equivalent.

Byte equality must not be asserted unless the build system is
intentionally made byte reproducible.

------------------------------------------------------------------------

## 32. Release Workflow Tests

Workflow-level tests or static contract checks should protect:

-   expected release trigger;
-   minimum permissions;
-   verification-before-publication ordering;
-   artifact handoff between jobs;
-   no publication from ordinary untrusted PR execution;
-   failure propagation;
-   required checksum and artifact-verification steps;
-   release identity inputs.

Workflow YAML is production release code and must receive contract
coverage.
