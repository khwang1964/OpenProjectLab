## 1. Purpose

This document establishes the governing Design First baseline for OpenProjectLab
v1.2.

The purpose of this slice is to convert the accepted post-v1.1 roadmap boundary
into an executable v1.2 development plan before product implementation begins.

The lifecycle is:

``` text

        ↓

        ↓
v1.2 Planning Baseline --- In Progress
        ↓
workstream priority accepted
        ↓
first Design First workstream contract
        ↓
implementation may begin
```

No v1.2 product implementation is authorized by this document.

## 2. Governing Principles

v1.2 continues to follow:

- Design First;
- Documentation First;
- Automation First;
- Testing First;
- backward-compatible Stable v1.x evolution;
- fail-closed contract changes;
- explicit mutation boundaries;
- reproducible acceptance evidence;
- immutable historical release / acceptance records;
- explicit human merge approval.

## 3. v1.2 Product Goal

v1.2 should strengthen OpenProjectLab as a Project Engineering Platform rather
than expand unrelated feature breadth.

The primary goal is to make multi-step project creation, inspection, validation,
and evolution more deterministic, inspectable, and automatable while preserving
existing Stable contracts.

## 4. Prioritized Workstreams

### Priority 1 --- Bootstrap Framework maturity

This is the first recommended v1.2 workstream.

Candidate outcomes:

- deterministic multi-step bootstrap orchestration;
- explicit plan / dry-run / apply boundaries;
- generated-project validation;
- inspectable bootstrap results;
- resumable or checkpointed bootstrap execution only where justified;
- stronger composition over existing generators without bypassing their
  lifecycle contracts;
- no second filesystem mutation pipeline.

Reason for priority:

Bootstrap is the strongest common execution substrate for later AI-assisted and
Marketplace-driven workflows.

### Priority 2 --- Developer / Release Automation

Candidate outcomes:

- reduce manual governance bookkeeping;
- automate release identity and acceptance consistency checks;
- improve branch / PR / CI / post-merge reproducibility;
- automate evidence collection without automating human merge approval;
- reduce duplicated terminal-alignment scripts.

Reason for priority:

Automation improves every later workstream and reduces acceptance-process risk.

### Priority 3 --- AI-assisted Project / Course Generation

Candidate outcomes:

- higher-level AI-assisted workflow composition;
- inspect-before-apply mutation model;
- deterministic local-response workflows remain first-class;
- live provider access remains explicit and opt-in unless separately promoted;
- generated changes use existing Domain / Generator / Filesystem boundaries.

Reason for priority:

AI workflows should build on a mature bootstrap orchestration layer rather than
introduce a parallel execution path.

### Priority 4 --- Marketplace Production Workflow

Candidate outcomes:

- richer local discovery and inspection;
- stronger provenance visibility;
- stronger installation planning;
- explicit trust boundaries;
- no implicit activation;
- no remote marketplace service unless separately designed.

Reason for priority:

Marketplace evolution should reuse stable bootstrap / installation planning
contracts before expanding external distribution behavior.

## 5. First v1.2 Implementation Slice

The first implementation slice is expected to be:

``` text
v1.2.1 --- Bootstrap Framework Design Baseline
```

This selection is not accepted until this planning baseline passes its
acceptance process.

The v1.2.1 design must define, before implementation:

- bootstrap public contract boundary;
- orchestration responsibilities;
- plan / dry-run / apply semantics;
- mutation and failure boundaries;
- state / checkpoint model, if any;
- generator composition rules;
- compatibility constraints;
- CLI impact;
- documentation impact;
- test strategy;
- acceptance gates;
- explicit non-goals.

## 6. Explicit Non-goals

The v1.2 planning baseline does not approve:

- v2.0 breaking Stable-contract changes;
- remote Marketplace service;
- ratings / reviews / monetization;
- silent network access;
- implicit AI provider selection;
- automatic credential discovery in Stable local workflows;
- arbitrary repository mutation by AI;
- automatic plugin activation;
- generalized dependency solving;
- generalized transaction rollback across every generator;
- generalized streaming / tool-calling guarantees;
- replacing existing generator lifecycle contracts;
- implementation before Design First approval.

## 7. Architecture Guardrails

Every v1.2 implementation slice must:

- reuse existing Stable public contracts wherever practical;
- introduce a new public contract only with explicit compatibility analysis;
- preserve deterministic local / offline testability;
- define failure behavior before execution behavior;
- keep filesystem mutation explicit;
- avoid parallel orchestration infrastructure;
- document migration impact;
- provide executable acceptance evidence;
- update architecture, tests, docs, and Code Review Checklist together.
